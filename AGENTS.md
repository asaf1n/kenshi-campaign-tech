# Контракт проекта Kenshi Campaign Tech

Проект: локальная инженерная обработка сохранений Kenshi, парсинг скриншотов и публикация подтверждённого состояния (`published/`) для внешнего репозитория игрового компаньона `asaf1n/Kenshi-Compain`. Читай `README.md`; предметные требования в `docs/requirements.md`, данные в `docs/data-contract.md`, архитектурные границы в `docs/architecture.md`, приёмку в `docs/acceptance.md`. При наличии установленного AI-Orchestrated-Workflow следуй привязке `orchestrate_workflow/method.md`. Не копируй глобальные роли/skills в этот проект.

## Неподвижные правила

| Область изменений | Обязательный источник | Проверка |
|---|---|---|
| Извлечение, diff, рендер и границы публикации (`tools/`) | `docs/architecture.md`, `docs/data-contract.md`, `docs/kenshi-settings.md` | `python -m unittest discover -s tests`; `python tests/run_evidence.py` |
| Картография: геометрия мира, соседство регионов, доставка артефактов и проверка просмотрщика (`tools/cartography.py`, `assets/cartography/`) | `docs/cartography.md` | `python -m unittest tests.test_cartography`; `python -m tools.cartography --verify-geometry --local` |
| Схемы и примеры (`contracts/`, `examples/`) | `docs/data-contract.md` | `python -m tools.campaign check-schemas`; `python -m unittest discover -s tests` |
| Структура и документация | `README.md`, `docs/requirements.md`, `docs/acceptance.md`, `docs/kenshi-settings.md` | `python tests/check_seed.py`; `git diff --check` |

1. **Сначала инвентаризация.** Проверяй действующие модули чтения сохранений, входные форматы, контракты и тесты. Версии форматов определяются схемами и `docs/data-contract.md`; несовместимые изменения допускаются только после обоснованной миграции.
2. **Не изменяй сейвы.** Входной каталог сохранений и скриншоты read-only. Все результаты — в другой папке; подтверждай хеши, не удаляй и не переименовывай исходные сейвы.
3. **Единственный источник чисел — код и файлы.** Не восстанавливай характеристики, снаряжение, баланс или статистику из текста чата. Не скрывай недоступные поля и неопределённость.
4. **Не связывай персонажей по имени**, если существует устойчивый ID. В одном составе могут быть одноимённые животные и персонажи. Отсутствие стабильного ID — явное ограничение.
5. **Diff и публикация детерминированны.** Повторный запуск по одним входам не меняет содержательные данные. Ошибки, неполные извлечения и невалидные сравнения не помечаются успешными.
6. **Таймлайн не равен diff.** Игровые события получают источник и статус подтверждения. Вывод модели не становится фактом без подтверждения.
7. **Перезагрузка — не потеря.** Кампания ведётся одной линией; загрузка старого сохранения распознаётся по откату игрового времени и не трактуется как хронологическая потеря предметов, навыков или участников. Идентичность снимка — содержимое сейва и параметры разбора, родитель назначается индексом ([ADR](docs/adr/campaign-line.md)).
8. **Граница записи.** Генерируемое состояние `published/` изменяется только через конвейер и не коммитится в `kenshi-campaign-tech` (каталог в `.gitignore`, из индекса удалён); доставка только через `deliver-companion`. Конвейер запускать только на этой машине: `git pull` на другом клоне удалит там рабочую копию `published/`. Авторские документы кампаний и хроники вынесены в отдельный репозиторий `asaf1n/Kenshi-Compain` и в этом техническом репозитории отсутствуют.
9. **Защита данных и доставка.** Не отправляй в Git сырой save, пользовательские абсолютные пути, ключи или токены. Публикация скриншотов игры выполняется автоматически через конвейер в `published/screenshots/`: из установленного каталога скриншотов (`_screens`) за последние 7 суток публикуются 20–30 ключевых кадров, уменьшенных до 1600 px; полный уменьшенный набор хранится локально в `data/screenshots_archive/` вне git; изображения старше 7 суток удаляются из актуальной публикации. Исходный каталог скриншотов является строго read-only. `published/` в `asaf1n/kenshi-campaign-tech` не коммитится. Для проверенного `published/` действует постоянное разрешение на одностороннюю доставку в `asaf1n/Kenshi-Compain` через `deliver-companion`. Перед записью проверяй diff и целевые пути, после — удалённый коммит и чтение. Не применяй force-push, не создавай remote и не меняй доступ без отдельного решения. Команда `pipeline` сама Git не вызывает.
10. **Процесс.** Сохраняй существующие изменения и инструкции; тестируй реальные сценарии; явно указывай, что проверено и что нет. Не заменяй аудит заявлением о выполнении.

## Разделение ответственности и двухрепозиторная архитектура

Репозиторий `kenshi-campaign-tech` содержит исключительно код технического конвертера, парсеров, валидаторов и схем контрактов.

Все авторские документы кампаний, хроники, билды, методики сопровождения и системные инструкции для чат-ИИ моделей (ChatGPT, Claude) вынесены в специализированный игровой репозиторий:
🔗 **Канонический игровой репозиторий:** `https://github.com/asaf1n/Kenshi-Compain`

В техническом репозитории запрещено размещать литературные хроники, сюжетные описания или инструкции ведения диалога с игроком.

`published/` — генерируемое состояние. Проверяй `manifest.json`, валидацию и принадлежность публикации нужной кампании; не изменяй его вручную. Доставка проверенного бандла в игровой репозиторий выполняется через `python -m tools.campaign deliver-companion`.

## Граница инструментов

Antigravity — предпочтительный управляющий интерфейс, если фактическая интеграция подтверждена. Codex — возможный implementer. Claude Code — локальная обработка и/или независимый reviewer. Не поручай реализацию и её приёмку одному контексту/агенту. Для простых изменений достаточно исполнителя и тестов по риску; значимые контракты и изменения данных требуют независимой проверки.

Стандартизованные этапные формы и роли принадлежат **внешнему** `AI-Orchestrated-Workflow` (`main`). Здесь — только предметные требования, пути, способы проверки и отклонения.
