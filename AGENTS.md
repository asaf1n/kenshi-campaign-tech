# Контракт проекта Kenshi Campaign

Проект: локальная обработка сохранений Kenshi и публикация подтверждённого состояния для ChatGPT. Читай `README.md`; предметные требования в `docs/requirements.md`, данные в `docs/data-contract.md`, архитектурные границы в `docs/architecture.md`, приёмку в `docs/acceptance.md`. При наличии установленного AI-Orchestrated-Workflow следуй привязке `orchestrate_workflow/method.md`. Не копируй глобальные роли/skills в этот проект.

## Неподвижные правила

| Область изменений | Обязательный источник | Проверка |
|---|---|---|
| Извлечение, diff, рендер и границы публикации (`tools/`) | `docs/architecture.md`, `docs/data-contract.md` | `python -m unittest discover -s tests`; `python tests/run_evidence.py` |
| Схемы и примеры (`contracts/`, `examples/`) | `docs/data-contract.md` | `python -m tools.campaign check-schemas`; `python -m unittest discover -s tests` |
| Структура и документация | `README.md`, `docs/requirements.md`, `docs/acceptance.md` | `python tests/check_seed.py`; `git diff --check` |

1. **Сначала инвентаризация.** Ищи и анализируй существующий конвертер, выгрузки, реальные сейвы и тесты. Форматы `kenshi-session/10` и `kenshi-session-diff/5` являются наблюдаемыми существующими контрактами; несовместимые изменения — только после обоснованной миграции.
2. **Не изменяй сейвы.** Входной каталог сохранений и скриншоты read-only. Все результаты — в другой папке; подтверждай хеши, не удаляй и не переименовывай исходные сейвы.
3. **Единственный источник чисел — код и файлы.** Не восстанавливай характеристики, снаряжение, баланс или статистику из текста чата. Не скрывай недоступные поля и неопределённость.
4. **Не связывай персонажей по имени**, если существует устойчивый ID. В одном составе могут быть одноимённые животные и персонажи. Отсутствие стабильного ID — явное ограничение.
5. **Diff и публикация детерминированны.** Повторный запуск по одним входам не меняет содержательные данные. Ошибки, неполные извлечения и невалидные сравнения не помечаются успешными.
6. **Таймлайн не равен diff.** Игровые события получают источник и статус подтверждения. Вывод модели не становится фактом без подтверждения.
7. **История ветвится.** Загрузка старого сохранения и альтернативные ветки не трактуются автоматически как хронологическая потеря предметов, навыков или участников.
8. **Граница записи.** Генерируемое состояние `published/` изменяется только через конвейер. Авторские события/решения — отдельно. Генерируемые Markdown-файлы не редактируются вручную. Четыре постоянных авторских файла в `Campaign/Хроники Хот Лон/` обновляются отдельно по подтверждениям игрока и не входят в `published/`.
9. **Защита локальных данных и доставка.** Не отправляй в Git сырой save, локальные пути пользователя, неотобранные скриншоты, ключи или токены. Для `asaf1n/kenshi-campaign-tech` действует постоянное разрешение пользователя: после успешной сверки коммить и выполняй обычный push проверенного `published/` без повторного запроса, затем проверяй удалённый выпуск. Это разрешение включает согласованное уточнение правил доставки; не включает посторонние коммиты, force-push, создание remote и изменение прав доступа. Порядок доставки — в `README.md`; команда `pipeline` сама Git не вызывает.
10. **Процесс.** Сохраняй существующие изменения и инструкции; тестируй реальные сценарии; явно указывай, что проверено и что нет. Не заменяй аудит заявлением о выполнении.

## Постоянные документы кампании

В `Campaign/Хроники Хот Лон/` хранятся `Kenshi_Хроника.md`, `Kenshi_Отряд.md`, `Kenshi_Текущая_арка.md`, `Kenshi_Режимы_и_методика.md`. Это версии действующих документов из локального корня `Kenshi Compain`, а не автоматически генерируемые артефакты. При явной задаче изменения вносятся в эти же файлы после проверки актуального Git-коммита и подтверждённых фактов; сохранённые билды не пересматриваются без решения игрока. Проверяй состав коммита и удалённое чтение; без force-push. GitHub, локальный корень, Project Sources и Library — независимые места хранения; об обновлении каждого судят только по выполненной записи.

## Граница инструментов

Antigravity — предпочтительный управляющий интерфейс, если фактическая интеграция подтверждена. Codex — возможный implementer. Claude Code — локальная обработка и/или независимый reviewer. Не поручай реализацию и её приёмку одному контексту/агенту. Для простых изменений достаточно исполнителя и тестов по риску; значимые контракты и изменения данных требуют независимой проверки.

Стандартизованные этапные формы и роли принадлежат **внешнему** `AI-Orchestrated-Workflow` (`main`). Здесь — только предметные требования, пути, способы проверки и отклонения.
