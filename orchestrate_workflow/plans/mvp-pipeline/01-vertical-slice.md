# 01-vertical-slice

## Цель

Получить первую самостоятельно работающую цепочку P0: входной сейв либо существующий экспорт → неизменяемый снимок → совместимый diff → проверенные JSON → русские `brief.md` и `squad.md` → согласованный пакет `published/`. Числа берутся из JSON, участники связываются по ID, отказ сохраняет предыдущую успешную публикацию.

## Решения

- Дата исходных требований не установлена. Источники: [требования](../../../docs/requirements.md), [архитектура](../../../docs/architecture.md), [контракт данных](../../../docs/data-contract.md), [приёмка](../../../docs/acceptance.md), [стартовое поручение](../../../prompts/01-START-AGENT.md) и [поручение на исполнение](../../../prompts/02-EXECUTE-APPROVED.md). Их P0-границы сохраняются; это не подтверждение выполнения критериев.
- 2026-11-01, подтверждено чтением. Во внешнем `kenshi-platoon-export` существуют `tools/session_export.py` с `FORMAT = "kenshi-session/10"`, `build_snapshot`, `collect_stable`, `run`; `tools/session_diff.py` с `DIFF_FORMAT = "kenshi-session-diff/5"`; `tools/saves.py` с чтением файлов и поиском по времени `quick.save`. Реальный `kenshi-session.json` содержит эти версии, `characters`, `squads`, `world`, `supplies`, `research`, `property`, `warnings`, `meta` и вложенный `changes`; обнаружена группа одноимённых участников с разными `ps:*`. Это наблюдение структуры файла, а не актуальное состояние игры.
- 2026-11-01, подтверждено чтением. `char_key` предпочитает `portrait_serial`, затем нестабильный `h:*`; экспортёр может продолжить работу после ошибки `quick.save` и лишь предупредить о расхождении счётчиков или дубликатах ID. `collect_stable` проверяет размеры/mtime, а не SHA-256. `run` выбирает предыдущую выгрузку по имени файла, добавляет `changes.history` и последовательно пишет несколько выходов. Кэш `session_export.CACHE_DIR` расположен внутри конвертера; явный `--out` перенаправляет результаты, но не кэш. Эти свойства требуют проектного адаптера, не замены GameData-парсера.
- 2026-11-01, подтверждено чтением. `session_diff.diff` безусловно вызывает `_match_by_name`; сортировка общих участников использует только имя; `skills`, `equipment`, `prosthetics`, `inventory`, `health`, `roster.squad_changed`, `roster.status_changed` теряют ID; `transfers` сводит дельты по имени. Существующие тесты включают сопоставление сменившихся ID по имени, поэтому прохождение старого набора само по себе не доказывает проектный инвариант.
- 2026-11-01, предложение плана. Подключать внешний код через `KENSHI_CONVERTER_DIR`, не редактировать его каталог. В проекте реализовать узкий адаптер извлечения и сравнения; бинарные `.platoon`, `quick.save`, `.zone` и справочник `gamedb` читает существующая реализация. Вызывать библиотечный `build_snapshot` в отдельном процессе `python -I -B` с явно перенаправленным `CACHE_DIR`; не использовать `run` как готовый publisher. Совместимый diff формировать до потери ID, переиспользуя доступные функции сравнения; восстановление ID по имени из готового legacy diff недопустимо.
- 2026-11-01, предложение плана. Сохранить `format` и семантику игровых полей исходных форматов. Добавления ID и ссылок на снимки документировать как профиль публикации; переименование либо удаление смысловых полей требует отдельного обоснования миграции. Не переносить числовую логику в Markdown-рендер. В `changes.json` (`kenshi-session-diff/5`) `research`/`property`, координаты и другие неотслеживаемые legacy diff категории явно обозначать как не сравниваемые; пространственное разрешение локаций и геометрическое смещение между совместимыми снимками подключаются отдельными профильными артефактами в задаче [02-world-geography](02-world-geography.md) без ломки `kenshi-session-diff/5` и `manifest.json`.

## Этапы задачи

1. **1.1 — Уточнение проектных схем, Windows-конфигурация, read-only extract и нормализация.** Зависимость: план прошёл независимое ревью, утверждён и отдельно передан на исполнение. Область будущих правок: `contracts/`, `examples/`, проектный Python CLI/адаптер в `tools/`, профильные проверки в `tests/`, `.env.example`, `.gitignore` при необходимости, `docs/data-contract.md`, `docs/architecture.md`, `README.md` и маршрутизация `AGENTS.md`. Конкретные имена новых модулей фиксируются в задании этапа; это будущие файлы, не существующий runtime.

   Уточнить только обнаруженные пробелы черновых схем: в `contracts/timeline-event.schema.json` добавить необязательный `snapshot_id` и `corrects_event_id` с обязательностью для `kind="correction"`; в `contracts/manifest.schema.json` (при сохранении `additionalProperties: false`) — совместимые необязательные поля верхнего уровня `parent_snapshot_id`, `branch_id`, `game_time`, `world_ref_id` (`string | null`), а также необязательные поля `artifacts.locations` и `artifacts.world_reference` (`$ref: "#/$defs/relativePath"`), чтобы единая схема `manifest.json` не требовала несовместимой правки при подключении географической подсистемы в задаче [02-world-geography](02-world-geography.md). До подключения задачи `02` поле `world_ref_id` в `manifest.json` опускается либо равно `null`. Корень допускает `parent_snapshot_id: null`, игровое время — явно описанное значение либо `null`, а не mtime. Старые `examples/*` должны оставаться валидными; новые примеры покрывают родителя, неизвестное время и коррекцию. Реальная проверка JSON Schema Draft 2020-12 обязательна: `tests/check_seed.py` лишь проверяет стартовый комплект. Выбор валидатора и новая зависимость обосновываются в документации. Полный формат GameData или несуществующая полная схема legacy-экспорта здесь не объявляются реализованными.

   Настроить CLI и переменные `KENSHI_CONVERTER_DIR`, `KENSHI_SAVE_DIRS`, `KENSHI_DIR`, `KENSHI_WORKSHOP_DIR`, а также выбор фракции игрока `--faction-sid` / `KENSHI_FACTION_SID` с умолчанием `204-gamedata.base`. Приоритет: явный CLI → окружение/локальная конфигурация → документированные значения по умолчанию. Эффективный `faction_sid`, включая значение по умолчанию, передаётся в `build_snapshot` и входит в отпечаток снимка. Для `KENSHI_SAVE_DIRS` определить разделитель Windows `;`; штатный пользовательский корень — `%LOCALAPPDATA%\kenshi\save`, дополнительный — каталог `save` установленной игры. `.env.example` содержит шаблоны без имени пользователя; способ загрузки `.env` должен быть явным, а не подразумеваемым. Автопоиск предлагает вход, но не устанавливает его логического родителя. Все выходы, staging и кэш размещаются вне сейвов и каталога внешнего конвертера; проверка разрешённых путей учитывает нормализацию, вложенность и ссылки/junctions.

   Реализовать два режима `extract`: `source_kind="save"` вызывает существующий конвертер по read-only входу; `source_kind="export"` читает готовый JSON строго `kenshi-session/10`, не требует установки игры и не запускает конвертер. Неизвестный формат получает явный отказ. Для `export` `source_sha256` — SHA-256 исходных байтов JSON до очистки. Для `save` определить SHA-256 канонического перечня относительных имён и хешей файлов сохранения; набор файлов, его добавление/удаление и байты проверяются до/после всего извлечения. Входные записи открываются только на чтение; изменение в ходе обработки означает отказ без регистрации снимка. Тест отказа записи выполняется на контролируемой копии или через перехват файловых операций, без пробной записи в настоящий сейв.

   Нормализовать `kenshi-session/10`: удалить `save.path`, исключить исходный `changes` целиком, включая историю и возможные пути; очистить персональные абсолютные пути и секреты также во вложенных метаданных/предупреждениях. Не удалять предупреждения о неполноте ради успешной проверки. `meta.exported_at`, `meta.timings_ms` и диагностическое состояние кэша не участвуют в содержательной эквивалентности или формировании новых версий при повторе одного сейва. Игровые значения сохраняют доступную исходную точность; дополнительное округление допустимо лишь при отображении. Неизвестное остаётся неизвестным, пустой известный список отличается от отсутствующего поля.

   Определить детерминированный `snapshot_id` по идентичности источника, явному контексту кампании/ветки и версии преобразования. Для save повтор конвертации того же источника с теми же настройками/модами не зависит от времени запуска; зафиксировать отпечаток используемого конвертера, эффективного `faction_sid` и данных модов. По наблюдению из ревью `kenshi-platoon-export` не является Git-репозиторием: для AC-01 и отпечатка конвертера использовать SHA-256 содержимого фактически используемых исходников `tools/*.py`, сохраняя их относительные пути и индивидуальные хеши; общий отпечаток вычислять по отсортированному перечню этих пар, без зависимости от Git HEAD конвертера. Для export исходный байтовый хеш сохраняется даже при содержательной эквивалентности двух разных файлов. Хранить нормализованный JSON и метаданные происхождения в `data/snapshots/`; существующий ID не перезаписывать и при несовпадении содержимого завершать с ошибкой. Поля родителя/ветки закладываются сейчас, полный реестр развивается в 3.1 (прежний этап 2.1). Повтор одного входа в том же контексте не создаёт нового снимка.

   Для `source_kind="save"` успешный extract требует чтения `quick.save`; для `source_kind="export"` файл `quick.save` не требуется. Повреждение или пропуск обязательных данных `.platoon`, повреждённая обязательная структура и любой повтор значения `characters[].id` (включая повтор одного ID в нескольких отрядах) блокируют успешный extract; допустимое число дубликатов ID — 0. Расхождения агрегатных `quick.save_counts` и предупреждения по `player_towns` или частичному чтению `zone/` сами по себе не блокируют выпуск: их сохраняют в `warnings`, показывают в диагностике и сводке, явно отмечая неполноту соответствующих необязательных категорий, без замалчивания или автоматического исправления состава. Основание уточнения — предоставленные пользователем результаты обследования 96 реальных сейвов: дубликатов `characters[].id` не выявлено, в 6 сейвах есть расхождение «quick.save: squads=5, а в .platoon найдено 4», в 32 — предупреждения по `player_towns` или частичному чтению `zone/` (город числится за фракцией игрока, но здания игрока там в `zone/` не найдены). Это внешнее наблюдение, повторный прогон в рамках правки плана не выполнялся. Недоступные необязательные категории, неизвестные моды/`sid` сохраняют явную диагностику и статусы проверки; неизвестные поля не теряются молча. `h:*`, имя вместо ID и отсутствие устойчивого ID обозначаются как ограничения, без автоматического связывания между снимками.

   **Готово:** для **AC-01** документированы версия внешнего конвертера по SHA-256 используемых `tools/*.py`, команды с `python -I -B`, доступные поля, ограничения модов и точки записи; проверены приоритет `--faction-sid` / `KENSHI_FACTION_SID` / умолчания и включение эффективного значения в отпечаток снимка. Для **AC-02** входы `save`/`export` не меняются, хеши до/после совпадают, отрицательная проверка записи проходит; для **AC-07** два одинаковых запуска дают тот же `snapshot_id` и канонические данные, существующий снимок остаётся неизменным; для **AC-10** фактические выходы не содержат путей пользователя/секретов, а `changes` и volatile-поля не влияют на факты. Табличные проверки неполноты различают обязательный `quick.save` только для save, повреждение/пропуск обязательных данных `.platoon`, блокирующий extract повтор `characters[].id` (включая повтор одного ID в нескольких отрядах) и допустимые агрегатные расхождения и предупреждения по `player_towns` или частичному чтению `zone/` с сохранёнными предупреждениями и явной маркировкой неполноты соответствующих необязательных категорий. Обновлённые схемы (включая необязательные `world_ref_id`, `artifacts.locations` и `artifacts.world_reference` в `manifest.schema.json`) и прежние примеры проходят JSON Schema; контрольные ошибочные варианты отвергаются. Все 6 проверок этапа (check_seed, check-schemas, check_converter, check_live, unittest 10/10, git diff --check) выполнены с кодом 0; доказательства зафиксированы в tests/.evidence/. Принят 2026-11-01.

2. **1.2 — Совместимый diff, validate, render и публикация полного пакета.** Зависимость: принят 1.1. Область будущих правок: проектный адаптер diff и CLI в `tools/`, профильные `contracts/`, `tests/`, `docs/data-contract.md`, `docs/architecture.md`, `README.md`, маршрутизация `AGENTS.md`; данные создаются только конвейером в `data/diffs/` и `published/`. Внешний конвертер остаётся read-only.

   Реализовать `diff` по явно выбранным неизменяемым снимкам. Сохранить `kenshi-session-diff/5`, добавить устойчивый `id` во все записи `skills`, `equipment`, `prosthetics`, `inventory`, `health`, `roster.squad_changed`, `roster.status_changed`; для одного имени использовать сортировку `(name, id)` с определённым порядком пустых имён. `transfers` агрегировать по ID отправителя/получателя и `sid` предмета, имена оставлять метками. Не объединять предметы только по переведённому названию и не заявлять о движении конкретного экземпляра, когда экспорт содержит лишь сводные количества.

   Запретить автоматическое связывание разных `ps:*` по имени для форматов `v3+`; смена устойчивого ID означает разные сущности или невалидность пары, не `id_changed` по имени. Поддержка legacy-перехода v2 не нужна для P0-входа v10; её возможное расширение не ослабляет этот запрет. Недостающий или повторённый ID не заменяется именем. Исправления выполняются в сравнении исходных записей, а не добавлением ID в уже потерявший различия результат.

   В `from`/`to` сохранить допустимые legacy-сведения и добавить `snapshot_id`; не выдавать `file`/`saved_at` за родительство. Сохранять детерминированный diff в `data/diffs/` по паре снимков и версии профиля. Минимальная защита уже в вертикальном срезе: проверка форматов, обязательных данных, ID, заявленного родителя, контекста ветки и неубывания игрового времени. Полный выбор ветки и индекс добавляются в 3.1 (прежний этап 2.1). Первая публикация без базы содержит `from: null`, `valid: false` и явный `reason`/`problems`; это валидное описание отсутствующего сравнения. Неполные категории дают `not_compared`/причину, не нули. Пустой либо несравнимый diff нельзя маркировать успешным сравнением; отсутствие изменений допустимо только при `valid: true` и реально ненулевом `compared`. Ошибка чтения ожидаемого baseline отличается от явно выбранного первого снимка и блокирует выпуск.

   `validate` проверяет схемы manifest/event, документированный профиль current/diff, обязательные типы и взаимные ссылки: `to.snapshot_id` совпадает с manifest, `from` соответствует выбранному родителю либо причине отсутствия; список `artifacts` разрешается строго внутри пакета, без абсолютных путей, traversal, ссылок наружу и отсутствующих файлов. Для legacy JSON определить минимальный совместимый профиль схемы и семантические проверки, не отбрасывая неизвестные необязательные поля. Проверить персональные строки во всех публикуемых артефактах. Статус успешной валидации пакета не равен `diff.valid`; технически повреждённый или неполный пакет не публикуется.

   Генерировать `brief.md` и `squad.md` только из проверенных JSON. Обязательное содержимое `brief.md` по [контракту данных](../../../docs/data-contract.md): `snapshot_id`, игровой день (и доступное время), состав по `characters.id` и `squad_id`, деньги, доступные местоположения, ключевые изменения при валидном сравнении и ссылки на детальные `current.json` и `changes.json`. До этапа 2.2 `brief.md` выводит доступные непосредственно из `current.json` сведения о расположении без догадок (подтверждённые города построек `property` / сырые координаты либо явную пометку до подключения гео-разрешения; при отсутствии сведений указывать «не получено», как и для других недоступных значений); полное географическое разрешение по справочнику мира подключается в задаче [02-world-geography](02-world-geography.md) (этап 2.2). При невалидном сравнении явно показывать статус и причину вместо вымышленных изменений. Сохранить доступные характеристики и предупреждения из JSON, включая агрегатные расхождения и предупреждения по `player_towns` или частичному чтению `zone/`, с явной маркировкой неполноты соответствующих необязательных категорий. Повтор `characters[].id`, включая повтор одного ID в нескольких отрядах, блокирует extract и не допускается как предупреждение успешной публикации. `squads.members` с именами не служит ключом соединения. Сводка изменений не выводит причины, смерти, продажи или потери из отсутствия данных. Повтор рендера даёт идентичные байты, все значения прослеживаются до соответствующих полей JSON. События пока не подставляются из `changes.history`; их обработка принадлежит 3.2 (прежний этап 2.2).

   `build`/`publish` создаёт полный `published/{manifest.json,current.json,changes.json,brief.md,squad.md}` в staging на том же томе. Отслеживаемый `published/.gitkeep` переносится в staging без изменения байтов и сохраняется после переключения и восстановления; замена каталога на Windows не должна удалять его из рабочего дерева. Валидация, рендер и проверка ссылок завершаются до переключения. Один writer удерживает блокировку; подготовленный пакет и последняя успешная версия не смешиваются. Предложенный минимальный Windows-протокол: подготовка → сохранение предыдущего каталога в backup → переключение готового каталога → завершение операции; сохраняются локальное состояние операции и проверенный backup для восстановления. Два переименования каталогов не объявляются одной атомарной операцией ОС: возможный разрыв доступности трактуется читателем как ошибка загрузки, не как частичная свежая версия. При обычном исключении вернуть прежний `published/` до завершения команды; после обрыва процесса следующий запуск сначала восстанавливает согласованный пакет. Проверить это на Windows, включая занятый файл. Если выбранный механизм не обеспечивает критерии, этап не принимается. Backup не удаляется до подтверждения успешного переключения. Ссылки manifest указывают на файлы одной версии; копирование/передача пакета выполняется после окончания выпуска. `generated_at` меняется только при новой публикации, повтор/dry-run не создаёт версию.

   **Готово:** **AC-04** — одна табличная fixture с двумя одноимёнными участниками доказывает раздельные изменения и передачу предмета по ID, перестановка входного порядка не меняет результат; смена разных `ps:*` не склеивается. **AC-05** — есть рабочий числовой diff, `from`/`to`, первый снимок без базы, пропуск поля и неверный родитель с понятной причиной, отсутствуют ложные нулевые изменения. **AC-08** — fault injection до записи, при рендере/валидации и переключении сохраняет последнюю успешную версию; частичный пакет не выдаётся за успех, `published/.gitkeep` сохраняется без изменения после выпуска и восстановления. **AC-09** — все JSON и ссылки валидируются, отсутствующий artifact отвергается. **AC-10**, **AC-11** — фактический пакет очищен, повтор рендера совпадает и числа сверены с JSON; автоматическая проверка состава `brief.md` и выборочная сверка значений подтверждают соответствие обязательному перечню `docs/data-contract.md:26`, включая доступные из `current.json` сведения о расположении/«не получено» до этапа 2.2, ключевые изменения только при валидном сравнении и работающие ссылки на `current.json`/`changes.json`. Срез проходит `extract(save/export) → diff → validate → build/publish` на двух доступных реальных сейвах и их экспортах; первичная сверка состава/денег/выбранных навыков выполняется с источником того же игрового момента. При недоступности сейва/сверки это блокировка соответствующей проверки, а не перенос доказательства на синтетику. Полная повторная приёмка и итоговая таблица AC относятся к 4.1 (прежний этап 3.1). ## Проверки и восстановление

Подтверждённые по README конвертера команды: `python -m unittest discover -s tests`, `python tools/check_session.py <копия-сейва>`, `python tools/verify_ui.py <снимок.json> <совпадающая-UI-fixture.json>`. Они не запускались при планировании. Исполнитель уточняет побочные эффекты каждого entry point и выполняет проверки с отдельными выходами/кэшем, без записи во внешний репозиторий. Команды нового CLI фиксируются после реализации и реально прогоняются; документация не должна выдавать предполагаемый синтаксис за проверенный.

Регрессии группируются по инвариантам: неизвестные поля/неполнота; identity и порядок; границы сравнения; согласованность пакета. Новые тесты нужны для конкретного ложного факта или отказа, который не ловит существующий набор; обычно 1–3 теста на новую функцию, превышение обосновывается. Повтор в отдельных процессах с разным `PYTHONHASHSEED` проверяет порядок, тест доступной точности — отсутствие дополнительного округления перед сравнением. Исходный SHA-256 и хеши окончательных артефактов связываются с командой, exit code и результатом проверки в локальном отчёте.

При неудаче extract/validate незавершённый выход не регистрируется как снимок; при неудаче publish сохраняются предыдущий пакет и диагностируемое состояние восстановления. Исправления не выполняются вручную в генерируемых Markdown/JSON. Независимый reviewer проверяет окончательный diff схем, identity и publisher до приёмки этапа по [правилам проекта](../../../docs/multiagent.md).
