# screenshot-hud-index: Машинная разметка и индексация скриншотов Kenshi

Статус плана: черновик

## Контекст

Сейчас текст с кадров получают только через Gemini API. В последней публикации `annotations.jsonl`, `feed.md` и `index.md` отсутствуют, есть лишь `index.json`, то есть OCR пуст, хотя `GEMINI_API_KEY` задан. Причину не проверял: кадр уменьшается до 800 px, таймаут 2.5 с, модель зашита в код. По кадрам нельзя искать игровой день или персонажа.

Цель: локальная разметка без LM, один лёгкий модуль и индекс для поиска. LM остаётся опцией на потом (раздел «Варианты LM»), в базовый план не входит.

## Что проверено на реальных кадрах

Все проверки шли только на чтение: 435 кадров в `_screens`, 346 в архиве.

| Факт | Результат |
|---|---|
| Windows OCR (WinRT) | есть, языки `ru` и `en-US`, ставить ничего не нужно; из Python 3.14 напрямую недоступен, вызывается через PowerShell 5.1 |
| Прочие средства | есть PIL, numpy, PyAV, onnxruntime; нет cv2, tesseract, RapidOCR |
| Разрешения кадров | 2880×1800 (360), 2560×1600 (34), 1680×1050 (27), 1920×1080 (14) |
| Оформление интерфейса | минимум два варианта (тёмный и пергаментный), панели расположены по-разному, поэтому фиксированные рамки не работают: на 2560×1600 день разобран в 26 кадрах из 34 |
| Поиск по подписям в правой нижней четверти кадра | разбор дня 113/145 (78%), времени 122/145 (84%), 244 мс на кадр, весь каталог примерно за 2 минуты |
| Качество источника | оригиналы читаются лучше архива 1600 px (суммы и цифры на архиве искажаются), OCR нужно делать по оригиналу |
| Слабое место | серия кадров дня 129–131 в пергаментном оформлении не разобрана, хотя глазом читается; вероятно, нужен второй проход с инверсией (не проверено) |
| dHash | медиана расстояния между соседними кадрами 26 при пороге 14, сливается 28 пар из 345; обрезка интерфейса не помогает (медиана 30), серии почти не группируются |

78% — это доля разбора, а не точность. Точность цифр пока не измерена. Единичные значения вроде `1` или `196` в начале каталога могут быть ошибками или другой кампанией, это не проверялось.

## Базовый план

### 1. `tools/winocr.ps1` (новый, около 60 строк)

- Принимает список путей через stdin, отдаёт JSONL: `{path, width, height, words: [{text, x, y, w, h}]}`.
- Один процесс на весь пакет, кадры только читаются, кропы в памяти.
- Распознаёт левую панель и нижнюю полосу. Если день не найден, делает второй проход с инверсией.

### 2. `tools/screenshot_hud.py` (новый, около 150 строк)

- `parse_hud(words, width, height)`: ищет поля по подписям, а не по координатам: «День», «Деньги», «Состояние», «Цель». Отдельно берёт строки задач и имя выбранного персонажа.
- Что не разобрано, остаётся `null`. Значения не исправляются по соседним кадрам: загрузка старого сейва законно откатывает день (правило 7).
- `update_hud_index(items)`: инкрементальный индекс по SHA-256 оригинала в `data/screenshots_archive/hud_index.jsonl`. Каталог уже в `.gitignore`, новых настроек не нужно.
- Строка индекса: файл, sha256, mtime, разрешение, день, время, деньги, выбранный персонаж, состояние, цель, задачи, сырой текст.
- Если PowerShell или OCR недоступны, поля остаются пустыми и публикация продолжается как сейчас.

### 3. Подключение к `tools/screenshot_extractor.py`, `tools/publisher.py`, `tools/campaign.py`

- Индекс строится по всем кадрам окна до даунскейла, ключевые кадры берут данные по `source_sha256`.
- В аннотацию идут существующие поля: `game_day`, `game_time`, `characters` (выбранный персонаж), `items_or_tasks`. `provenance.source = "ocr"` уже есть в схеме, поэтому **контракт не меняется**.
- Деньги, состояние и цель остаются только в локальном индексе.
- `annotations.jsonl`, `feed.md` и `index.md` начнут публиковаться без доработки, это уже обеспечивает `has_ocr_content`.
- Gemini вызывается только при `KENSHI_SCREENSHOT_VLM=gemini`. Сейчас он срабатывает от самого наличия ключа и отправляет кадры наружу.
- Исправление кэша: запись `provenance.source = "metadata"` больше не считается попаданием, иначе кадр без OCR навсегда останется пустым.
- `extracted_at` берётся из индекса, чтобы повторный запуск не менял данные (правило 5).

### 4. Две команды в `tools/campaign.py`

```powershell
python -m tools.campaign screenshots-index [--screens-dir ...] [--all]   # по умолчанию окно 7 суток, --all весь каталог
python -m tools.campaign screenshots-find --day 120 --text "Хот Лон"     # линейный поиск по JSONL
```

Без SQLite: для сотен строк он не нужен.

### 5. Документация и тесты

- Обновить `docs/screenshots.md` (§6–7), упоминания OCR в `docs/data-contract.md`, команды в `README.md`.
- Один табличный тест `parse_hud` на записанных списках слов обоих оформлений: ловит поломку поиска по подписям и подмену пропуска значением.
- Один тест кэша: ловит вечную пустую запись `metadata`.

### Что не входит в базу

- Локация и реплики: в постоянном интерфейсе локации нет, текст над головами накладывается друг на друга.
- Список отряда: имена под портретами обрезаны. Сопоставление с персонажами сейва по имени запрещено правилом 4.
- Новая группировка серий и отбор кадров. Группировать лучше по игровому дню вместо dHash, но это меняет состав публикации, поэтому идёт следующим шагом после оценки индекса.

## Варианты LM (после базы, отдельным решением)

**Важное уточнение.** Локальная модель — `Qwen3-30B-A3B-Instruct` (3B активных параметров). Она **только текстовая**: в `LocalLLM/models` один GGUF, `mmproj` нет. Картинки она не видит, ей можно передать лишь текст после OCR.

| Вариант | Что даёт | Ограничения | Статус |
|---|---|---|---|
| A. Qwen3-30B-A3B по тексту OCR | чистка сырого текста, нормализация строк задач | модель заполняет пропуски правдоподобными значениями; занимает 16.5 ГиБ, поэтому запуск после сессии, а не во время игры; вызов `http://127.0.0.1:8080/v1`, сервер сейчас не запущен | дёшево, но польза мала: поля и так разбираются регулярками |
| B. Локальная модель со зрением (класс Qwen-VL 3–4B + `mmproj`) | чтение кадра без сети | нужна загрузка модели; `llama-mtmd-cli` и `llama-qwen2vl-cli` есть; ОЗУ тесное (15.8 ГБ при VGM); скорость и качество на мелком русском тексте не измерены; конкретную модель выбрать по каталогу при загрузке | гипотеза, нужен замер на 10 кадрах |
| C. Codex CLI | кадры через `codex exec -i <файл> -s read-only -o <файл>` | кадры уходят наружу, тратится квота, запуск сессии на каждый вызов; подходит для 20–30 ключевых кадров, не для всех | флаг проверен (0.166), реальный вызов нет |
| D. Gemini CLI | `gemini -p ... --approval-mode plan` | флага для изображений в `--help` нет, передача файла через `@` не проверена | нужна проверка |
| E. Claude Code CLI | `claude -p --permission-mode plan`, изображение читается инструментом Read | только нужные инструменты чтения, расход подписки | нужна проверка в неинтерактивном режиме |
| F. Antigravity CLI | `agy -p --json-schema` даёт структурный ответ | в `--help` нет опции изображений | годится только для текста |

Ollama в PATH указан, но каталог пуст: не установлен.

**Правила из `/orchestrate`, применимые к C–F:**

- `$null | <CLI>`, stdout и stderr раздельно, код выхода сразу после вызова, UTF-8 без BOM.
- Только режимы чтения, без флагов обхода подтверждений и песочницы.
- Ненулевой код выхода означает, что результата нет.
- Перед использованием сверять `--help` и каталог моделей, замену модели называть явно.
- Локальная LLM — только по явному разрешению, для извлечения и предобработки со ссылками на источник.
- Роли, `spec.md` и независимое ревью для этой утилиты не нужны.

**Общее ограничение.** Вывод LM хранится отдельно с пометкой кандидата и не попадает в `ocr` (правило 6). Описание сцен сейчас запрещено `docs/screenshots.md` §1 и схемой, поэтому для него нужно отдельное решение об изменении этого правила.

**Рекомендация.** «На ходу» сначала делать без LM: `screenshots-index --watch` с опросом каталога, около 20 строк, 0.25–0.7 с на кадр. Если понадобится понимание сцены, подключить вариант C для ключевых кадров одной командой вручную. Вариант B имеет смысл только после замера.

## Проверка

1. `python -m tools.campaign screenshots-index --all` на реальном `_screens`: число кадров, доля разбора дня и времени по разрешениям и оформлениям. Цель — не меньше 90% дня на кадрах с интерфейсом.
2. Сверка глазами 30 случайных кадров с индексом. Если день неверен в двух кадрах и более, `game_day` не публикуется и остаётся только в локальном индексе.
3. SHA-256 файлов `_screens` до и после совпадают.
4. Повторный запуск не меняет индекс и аннотации, второй запуск без OCR-вызовов.
5. `python -m unittest discover -s tests`, `python tests/run_evidence.py`, `python -m tools.campaign check-schemas`, `git diff --check`.
6. Содержимое публикации меняется, поэтому результат проверяет независимый reviewer только на чтение.

В `published/` сейчас много незакоммиченных изменений. Реальный `publish` и коммит состояния выполняются отдельно и не смешиваются с коммитом кода.
