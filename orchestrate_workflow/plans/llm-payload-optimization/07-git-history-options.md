# 07-git-history-options: Анализ и подготовка вариантов оптимизации git-истории

## Цель
Подготовить для игрока взвешенное техническое предложение по оптимизации размера git-хранилища игрового репозитория `Kenshi Compain`.
На текущий момент каталог `.git/objects/pack` в `Kenshi Compain` занимает ~174 МБ из-за начального коммита `88c9268`, содержащего 343 несжатых скриншота. Текущие оптимизации конвертера предотвращают разрастание будущих коммитов, но уже зафиксированные в истории git объекты автоматически не уменьшаются.

> [!WARNING]
> **Стоп-условие 3**: Любые операции перезаписи истории git (squash, rebase, filter-repo) и `git push --force-with-lease` производятся СТРОГО по прямому явному указанию игрока. Эта задача носит исключительно аналитический характер (подготовка вариантов и последствий).

## Варианты решения для игрока

### Вариант 1: Оставить историю как есть (Консервативный, нулевой риск)
- **Суть**: В `origin/main` сейчас находится ровно 1 коммит (`88c9268`, объем пака 174 МБ). Локальный репозиторий сохраняет текущую историю. Новые коммиты добавляют только легковесные keyframes (по ~150 КБ).
- **Плюсы**: Нулевой риск расхождения веток, полная прозрачность git log, отсутствие необходимости force-push.
- **Минусы / Компромисс**: Клонирование репозитория продолжит скачивать 174 МБ. Gemini Web UI импорт всего репозитория целиком будет заблокирован (лимит 100 МБ), доступен только выборочный импорт файлов или использование `chat-pack/`.

### Вариант 2: Пересоздание начального коммита до первого боевого push (Рекомендуемый)
- **Суть**: В удаленный репозиторий `origin/main` пока отправлен только 1 начальный коммит `88c9268`, а наработки компаньона еще не пушились: сформировать чистый базовый коммит публикации снимка Day 131 с оптимизированными ключевыми кадрами (<25 МБ вместо 187 МБ).
- **Плюсы**: Физический размер репозитория падает со 174 МБ до <35 МБ. Импорт в Gemini полностью разблокируется для всего репозитория.
- **Минусы / Риски**: Требует одного согласованного `git push --force-with-lease origin main` поверх начального коммита.

### Вариант 3: Очистка через git filter-repo / переход на Git LFS (Специализированный)
- **Суть**: Применение `git filter-repo` для удаления тяжелых исторических blob скриншотов из истории коммита `88c9268` с сохранением остальных файлов, либо перевод каталога `published/screenshots/` под управление Git LFS (хранение бинарников на внешнем сервере LFS).
- **Плюсы**: Полное удаление исторических бинарных блобов из локального репозитория git.
- **Минусы / Риски**: Изменение SHA-хэшей коммитов. Для Git LFS требуется поддержка LFS на стороне сервера и отдельная квота хранилища (в бесплатных аккаунтах GitHub лимит LFS — 1 ГБ трафика в месяц). Избыточная сложность для однопользовательской кампании по сравнению с Вариантом 2.

## Результат задачи
Сформированный документ сопоставления вариантов для демонстрации игроку в точке остановки 1. Решение о применении того или иного варианта принимает игрок.
