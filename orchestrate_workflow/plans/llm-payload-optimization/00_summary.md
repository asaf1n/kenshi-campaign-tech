# llm-payload-optimization: Оптимизация объема и структуры выпуска published/ для LLM

Статус плана: в работе (этап 00 выполнен)
Репозиторий: `kenshi-campaign-tech`  
Дата обновления: 2026-11-03

## Цель плана
Оптимизировать артефакты выпуска `published/` технического конвертера `kenshi-campaign-tech` для эффективного потребления моделями в чат-интерфейсах (ChatGPT, Gemini, Claude) и автономными агентами (Codex, Claude Code, Antigravity).
Устранить критические блокеры:
1. Провести фактологический аудит тестов, зафиксировать реестр допустимых `skip` и выявить причину расхождения численности бойцов (14 vs 30) (Этап 00).
2. Сократить физический объем скриншотов в публикации (до <30 МБ для ключевых кадров) с сохранением полного даунскейленного архива локально вне git и согласованным обновлением контракта (Этап 01).
3. Подавить генерацию пустых OCR-артефактов при сохранении обязательного `index.json` с эпизодами (Этап 02).
4. Очистить публичную проекцию `current.json` в публикаторе от сырых словарей `raw` (с нормализацией статуса кражи `is_stolen`), скрыть `hidden_stats_raw` и дефолтные навыки строго `== 1.0` (сокращение на ~370 тыс. символов / ~35%), внедрить шардирование и ограничение объёма стартового набора выгрузки (Этап 03; «chat-pack» — название задачи, отдельного пакета нет, меняется сама выгрузка `published/`).
5. Вынести тяжелый RLE-растр и исходные хеши из публикуемого `world_reference.json` с сохранением полного кэша в `data/world` (Этап 04).
6. Очистить технические sha256-заголовки из Markdown-сводок и настроить валидатор на передачу предупреждений (`validation.warnings` со строгим значением `"artifact:timeline: empty"`) со статусом `passed` (Этап 05).
7. Обеспечить детерминированную сборку цепочки `timeline.jsonl` в контракте `kenshi-event/1` на основе истории снимков и фиксацию `branch_switch` в манифесте при смене веток/откатах (Этап 06).
8. Подготовить для игрока взвешенные варианты оптимизации накопленной git-истории `Kenshi Compain` (Этап 07).

## Инварианты и архитектурные границы
1. **Строгий read-only для оригинальных сейвов и скриншотов**: входной каталог `_screens` и файлы сохранений игры не изменяются.
2. **Детерминированность вывода**: повторный прогон конвейера на тех же входных данных не приводит к искажению числовых показателей отряда.
3. **Обратная совместимость контрактов**: обязательные поля манифеста `kenshi-publication/1` и схемы `contracts/` сохраняются. Опциональные поля и предупреждения (`validation.warnings`) вводятся без нарушения существующих клиентов.
4. **Служебные данные за кадром**: читаемые человеком и LLM документы (`brief.md`, `squad.md`) не содержат сырых sha256-хэшей в заголовках.
5. **Синхронность документации**: при расширении схем и публикации синхронно обновляются `docs/data-contract.md`, `docs/architecture.md`, `AGENTS.md`, `README.md`, `docs/screenshots.md` и `docs/chatgpt-interface.md`.
6. **Обязательные проверки**: каждый этап валидируется локальными unit-тестами, `python tests/check_seed.py` и полным прогоном `python tests/run_evidence.py` без немотивированных пропусков.

## Корректировки по обсуждению (2026-11-03)
1. **Один процесс выгрузки**: сохранение и скриншоты -> `pipeline` -> `published/` -> доставка в Kenshi Compain -> push. Параметры и режимы сверх этого процесса не добавляются.
2. **Задача «chat-pack»** — название этапа 03, а не отдельный артефакт: изменяется сама выгрузка `published/` (очищенный `current.json`, шарды `current/`, ключевые кадры, лимит объёма стартового набора). Команда `build-chat-pack` и каталог `chat-pack/` не создаются: процесс выгрузки один. Читатель записи хроники — любая LLM с доступом к GitHub-репозиторию Kenshi Compain и методологическим инструкциям.
3. **Скриншоты**: прежний архив из Kenshi Compain удалён по решению игрока; в выпуск идут только ключевые кадры (этап 01), полный архив остаётся локально вне git.
4. **Родитель снимка** входит в идентичность снимка, поэтому в `pipeline` задаётся явно (автовывод ломает детерминизм: тест `test_native_extraction_preserves_identity_and_extended_fields`). `Initialize-Pipeline.ps1` передаёт голову ветки из `data/index.json`; без этого `changes.json` выпуска не имел базы сравнения.
5. **Полный доступ к обоим репозиториям и работа через `git push`** подтверждены игроком; доставка в Kenshi Compain выполняет push.
6. **Граница конвертера**: он ничего не читает из Kenshi Compain, а только записывает туда выгрузку. Дельта от сверенной точки собирается из накопительного `timeline.jsonl` (этап 06), а не из watermark арки.
7. **Крупные файлы** (полный архив скриншотов, расширенная выгрузка) хранятся вне git на локальном диске; его можно разместить на диске, синхронизируемом с Drive (каталог `data/screenshots_archive/` может быть junction на такой диск). Драйв-интеграции и новых параметров в конвертере нет.
8. **Критерий отбора данных**: из выгрузки убирается то, что не используется ни одним режимом (мусорный контекст), но данные не урезаются в ущерб свободным генеративным запросам (рассказ, сценарий, диалог, описание): границей остаются подтверждённые данные. Инструкции Kenshi Compain сохраняют гибкость формы и объёма.
9. **История и таймлайн**: цепочка снимков, индекс и накопительный таймлайн хранятся в папке конвертера; в `published/` попадает только срез, нужный LLM (объём окна определяется в этапе 06 по периоду между сверками). Предупреждение `"artifact:timeline: empty"` (этап 05) относится только к случаю, когда таймлайн включён в выгрузку.
10. **Диск `G:\Мой диск\Kenshi Compain. Docs`** (Drive for desktop) подключён 2026-11-03; под крупные файлы конвертера (архив скриншотов, расширенная выгрузка) создаётся подкаталог на этом диске; каталог архива в репозитории конвертера связывается с ним junction.
