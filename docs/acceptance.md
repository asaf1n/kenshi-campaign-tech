# Критерии приёмки

Результат должен быть воспроизводим на ПК и оцениваться по фактическим доказательствам, а не по сообщению агента.

| ID | Проверка | Минимальное доказательство |
|---|---|---|
| AC-01 | Описаны действующий парсер, входные и выходные контракты и поддерживаемые форматы | пути, команды запуска, список полей и ограничений |
| AC-02 | Сейвы доступны только на чтение и не изменились | SHA-256 до/после на двух примерах; тест на отказ записи |
| AC-03 | По двум реальным сейвам созданы воспроизводимые результаты | команды, пути артефактов, хеши, ручная сверка минимум состава, денег и выбранных навыков с игрой |
| AC-04 | Идентичность участников стабильна при одинаковых именах | fixture двух одноимённых персонажей + тест |
| AC-05 | Diff указывает правильные from/to и invalid case | тест изменения, отсутствующих данных и неверного родителя |
| AC-06 | Reload/ветвление не трактуется как обычная потеря ресурсов | тест сравнения после загрузки раннего сейва |
| AC-07 | Повторная обработка не даёт новых фактических изменений | два последовательных запуска, сравнение нормализованных выходов |
| AC-08 | Неудача обработки не перезаписывает последний успех | fault injection / тест атомарного обновления |
| AC-09 | Все опубликованные JSON и ссылки manifest валидны | автоматический валидатор, JSON Schema, тест отсутствующих файлов |
| AC-10 | Из публикации удалены локальные абсолютные пути и секреты | автоматическая проверка и просмотр фактического output |
| AC-11 | Генерируемые Markdown воспроизводятся из JSON | diff результатов повторной генерации и выборочная сверка значений |
| AC-12 | События имеют происхождение и статус, нет дублирования | тест import/append, примеры observed/confirmed/inferred |
| AC-13 | Доступ чат-ИИ моделей (LLM) подтверждён либо документирован fallback | реальный запрос актуального snapshot ID, отметка о подключении или инструкция ручной загрузки |
| AC-14 | Изменения прошли независимый audit для контрактов и pipeline | reviewer verdict, замечания, проверки финального commit/working tree |
| AC-15 | Есть краткая эксплуатационная инструкция для Windows | команды настройки, одно обновление, диагностика ошибки и восстановление предыдущей публикации |
| AC-16 | `published/tables/` соответствует контракту и числам приёмки | `validate_publication`, сверка значений таблиц со снимком (раздел «Приёмка табличных выгрузок») |
| AC-17 | Публикация одного снимка и доставка идемпотентны | два `publish` в разные каталоги: хеши всех файлов `tables/`, `brief.md`, `squad.md` совпадают; повтор `deliver-companion --no-commit` и `sync-drive` ничего не записывает (нативные файлы Диска: `written: 0`, `conflicts: 0`, `drive_modified_time` в sync-state равен значению Диска после записи); Диск - копия `main`, не источник истины ([docs/gdrive-sync.md](gdrive-sync.md)) |

## Отрицательные сценарии

- Нет или повреждён файл сейва, неизвестный `format`, парсер возвращает неполную структуру.
- Старое сохранение выбрано «новым» (перезагрузка по игровому времени), одинаковое время, два одинаковых имени, неизвестный ID.
- Неподдерживаемый мод добавляет неизвестные поля; состояние не должно пропасть из-за попытки оптимистической нормализации.
- Имеется JSON, но нет соответствующего diff; нельзя выводить нулевые изменения.
- GitHub-подключение чат-ИИ модели возвращает устаревшую версию; интерфейс должен сообщить `snapshot_id` и невозможность доказать свежесть.
- Ошибка Git/сети не блокирует локальную публикацию и не удаляет ранее опубликованный пакет.

## Старые снимки

Снимки, созданные до удаления аналитики, не переписываются: поля `standing`, `*_calculated` и `state_detail` в них сохраняются и при пересборке публикации таких снимков попадают в `extended/current.json`; чтение и diff их терпят. Актуальные выпуски (новые извлечения) этих полей не содержат.

## Граница принятия

Нельзя считать P0 выполненным по синтетическим примерам или только JSON Schema. Для полного закрытия необходимы реальные сейвы, сверка с игрой и проверка канала доступа чат-ИИ моделей (LLM ассистентов). Проверка доставки включает удалённое чтение опубликованного выпуска; при недоступности GitHub фиксируется непроверенный этап и применяется документированный ручной сценарий.
