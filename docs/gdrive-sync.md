# Синхронизация с Google Диском

Выгрузка доставляется двумя каналами: GitHub (`deliver-companion`) и Google Диск. Основная среда работы - проекты ChatGPT, читающие GitHub `main`; Диск - односторонняя резервная копия `main` и выгрузки в нативных форматах Google и источники блокнотов Gemini Notebook (NotebookLM) на случай возврата к Gemini. Направление одно: `main` и `published/` -> Диск. На Диск попадают только Markdown, CSV и PDF из allowlist двух профилей (раздел «Профили»); JSON и отдельные `.jpg` не копируются.

## Нативные файлы

| Источник | На Диске | Запись |
|---|---|---|
| `.md` | один Google Doc, имя файла без расширения | Docs API: текст `.md` вставляется как обычный текст (способ (б)) |
| `.csv` | один Google Sheet, имя без расширения | Sheets API: `values.clear` + `values.update`, `valueInputOption=RAW` |
| `.pdf` | PDF | смонтированный Диск, запись на месте |

Пути (каталоги) на Диске совпадают с путями репозитория; каталоги создаются через Drive API. Файл создаётся при первом запуске, затем обновляется на месте с сохранением `file_id`; неизменённое не трогается (сравнение sha256 источника с `tmp/sync-state.json`).

Почему способ (б), а не импорт `text/markdown` (способ (а)): оба способа сохраняют `file_id`, но (а) не обратим без потерь (относительные ссылки превращаются в `http://...`, frontmatter разрушается, смежные строки сливаются; 15 из 27 проверенных файлов), а (б) хранит текст исходника как обычные абзацы и восстанавливается байт в байт. Цена (б): структуры Docs нет (`#`, `**`, `|---|` остаются литералами; заголовки не навигируются). Sheets - `RAW`: значения остаются строками (`001234`, `true`, `1e5`, `=SUM(1,2)` не преобразуются); числовой тип ячеек не создаётся.

Запас до лимита 50 источников: 17 на `game`, 41 на `chronicle`; Doc и Sheet считаются источниками как файлы.

Ориентир - не более 30 файлов на профиль (лимит Gemini Notebook - 50 источников); при превышении отчёт содержит `over_limit` и `WARNING` в stderr, синхронизация не прерывается. Отчёт `sync-drive` выводит по каждому профилю `count`, `files`, `over_limit`, `files_chars` (`{path, chars[, note]}`, по убыванию символов UTF-8; PDF и отсутствующие локально - `chars: null`, вне суммы) и `total_chars`; в stderr - топ-10 по символам. `desktop.ini` и `Thumbs.db` игнорируются полностью. `root_dir` профиля (по умолчанию пусто) позволяет позже разнести профили по каталогам Диска: файлы профиля получают новые `file_id`, их пути перечислены в `relink`.

### Список переподключения источников

При возврате к Gemini Notebook источники подключаются по списку `reconnect` отчёта `sync-drive`: по каждому профилю `{path, name, kind, file_id, url}` нативных файлов (путь на Диске без расширения). Тот же `file_id` хранится в `tmp/sync-state.json`. Файл набора подключается к блокноту один раз и далее обновляется на месте.

## Запись и `file_id`

Нативные файлы обновляются только на месте: Docs - `deleteContentRange` на весь текст (если не пуст) и `insertText` одним `batchUpdate`; Sheets - очистка первого листа (имя листа берётся из метаданных, локализовано) и `values.update` (`RAW`, значения строками, разбор `csv`, UTF-8). Файл не пересоздаётся: пересоздание меняет `file_id` и разрывает источники блокнота. После записи в `appProperties` файла ставятся `sha256` и `trailing_lf` (дубль данных sync-state на случай его потери).

PDF и `tmp/` пишутся на смонтированном Диске: `write_in_place` перезаписывает существующий файл открытием на запись и не трогает файл с совпадающими байтами; `os.remove`, `unlink` и `os.replace` создают новый файл и разрывают `file_id`. Запись на месте не атомарна: при обрыве файл может остаться неполным до следующей синхронизации. PDF собирается в `%TEMP%`; если в окне нет кадров, PDF не собирается и на Диске остаётся прежний. Повторный запуск при совпадающем содержимом ничего не пишет. Файл, удалённый или перенесённый в корзину на Диске, создаётся заново (новый `file_id`, имя в `recreated`).

## sync-state

`tmp/sync-state.json` (смонтированный Диск; чужие секции сохраняются):

| Ключ | Содержимое |
|---|---|
| `native_root_id` | id каталога «Kenshi Compain. Docs» |
| `native` | путь файла в репозитории с расширением (`docs/x.md`) -> `file_id`, `kind` (`doc` \| `sheet`), `source_sha256` (после CRLF -> LF), `drive_modified_time` (время изменения после нашей записи), `eol_final`, `trailing_lf` (число хвостовых LF источника), `chars`, при наличии `head_revision_id` |
| `origin_main`, `files` | SHA `origin/main` и sha256 набора `docs/`, `templates/` |
| `synced` | файлы смонтированного Диска, записанные прежними синхронизациями (основание для `--prune`) |

Пустой `source_sha256` означает прерванную запись: следующий запуск перепишет файл.

## Пределы

- Google Doc: вставка до 1 500 000 символов (проверено 1,5 млн принято, 2 млн отказ); длиннее - отказ с сообщением в `refused`. Сейчас крупнейший `.md` около 54 тыс. символов.
- Google Sheet: ячейка до 50 000 символов (50 001 отказ API); ячейка длиннее или запрос больше 12 МБ - отказ в `refused`; остальные файлы продолжают синхронизироваться. Экспорт листа ограничен 10 МБ (`exportSizeLimitExceeded`): таблица, превышающая предел, записывается, но не восстанавливается `gdrive-export`. Экспортируется только первый лист: таблица - один лист.
- Отказ файла даёт `status=partial` и не блокирует удаление остальных; сам файл не удаляется.
- Лимит 10 млн ячеек Sheets и точная граница Doc между 1,5 и 2 млн не проверялись.

## Нормализация экспорта и восстановление

Экспорт `text/plain` Google Doc отличается от исходника детерминированно: BOM, CRLF, каждая пустая строка исходника - две пустые строки, финальный LF не выводится. Обратная нормализация (`normalize_doc_export`): снять BOM, CRLF -> LF, серии пустых строк разделить пополам, хвостовые переводы строк снять и вернуть в числе `trailing_lf` (экспорт не различает исходник с финальным LF и без него; число берётся из sync-state, иначе из `appProperties`). Результат побайтно равен исходнику после CRLF -> LF (CRLF-исходник хранится как LF; BOM исходника не сохраняется). Экспорт `text/csv` Sheet (`normalize_csv_export`): CRLF -> LF, хвостовые переводы строк заменить числом `trailing_lf`; перевод строки CRLF внутри ячейки возвращается как LF.

```powershell
python -m tools.campaign gdrive-export <путь-в-репозитории.md|.csv> [--output файл] [--gdrive-dir <путь>]
```

Команда находит файл по `file_id` из sync-state, иначе по именам каталогов Диска, и пишет восстановленный исходник в `--output` (без него - в stdout). Проверка нормализации - на всех `.md` клона `Kenshi-Compain` и `published/` в `tests/test_gdrive_native.py` (модель прямого преобразования по опытам 2026-11-07).

## Команды

```powershell
python -m tools.campaign pipeline ... --sync-drive           # после публикации и доставки: session + docs + chronicle (Campaign/)
python -m tools.campaign sync-drive [--scope all|session|docs|chronicle] [--gdrive-dir <путь>] [--dry-run] [--prune]
python -m tools.campaign gdrive-export <путь> [--output файл]
python -m tools.campaign ingest-inbox [--companion-dir <путь>] [--gdrive-dir <путь>] [--accept <файл>]... [--no-push]
.\Save-Packet.ps1 [-Accept <файл>[]] [-NoPush]   # буфер обмена -> tmp/inbox -> ingest-inbox -> отчёт
```

`--scope all` = `session` + `docs` + `chronicle`. `--dry-run` ничего не пишет и не удаляет (также не создаёт `tmp/`, каталоги и файлы Google и не меняет клон, кроме `fetch`), использует только чтение API и печатает план. `--prune` включает удаление. `pipeline --sync-drive` удаление не выполняет. `Initialize-Pipeline.ps1` (хоткей) передаёт `--sync-drive`. Google API или токен недоступны (нет пакетов, токена, корня) - `status=failed`, `reason=gdrive_api_unavailable`, сообщение в `error` и `WARNING`; автономный `sync-drive` завершается кодом 1, в `pipeline` сбой остаётся предупреждением. Шаг Диска в `pipeline` (по умолчанию в `Initialize-Pipeline.ps1`) не влияет на код возврата: Диск не смонтирован, нет токена или сети, исключение Drive API - предупреждение `WARNING: drive: ...` в stderr и поле `drive` результата (`synced` либо `skipped|failed|partial (причина)`); код 0 при успешной публикации и доставке. Отказом остаются ошибки публикации, доставки (`partial`) и проверки принадлежности сейва. Несостоявшийся push доставки даёт `companion_delivery.status=partial` и код 1, но Диск при этом синхронизируется; автономные `sync-drive` и `ingest-inbox` завершаются кодом 1, если синхронизация неполная или пакет отклонён. Функция `sync_chronicle(companion_dir, root, entries, dry_run, native, now)` вызываема отдельно (синхронизация `Campaign/` после приёма пакета).

## Диск - копия main (Campaign/, docs/, templates/, published/)

Правок Диска в GitHub конвертер не переносит (обратный перенос отменён). Для `Campaign/`, `docs/`, `templates/` и `published/` правило одно: нативный файл, изменённый на Диске после нашей последней записи (`modifiedTime` не совпадает с `drive_modified_time` из sync-state), сохраняется как `.md` (текст документа после нормализации) или `.csv` в `tmp/conflicts/<путь без расширения>-<UTC>.<расширение>` и перезаписывается версией из `main`. Если содержимое Диска уже равно источнику (правка отменена), копия не создаётся. Файл, найденный на Диске без записи в sync-state (например, при потере состояния), принимается тем же способом: пустая заготовка не считается правкой.

- Файлы `Campaign/` только на Диске (например, новые `S-*`, созданные Gemini) не трогаются и перечисляются в `only_on_drive` (по `.md` и ярлыкам `.gdoc`). Ничего не удаляется. Файлы клона с незакоммиченными правками пропускаются (`skipped_uncommitted`).
- Источник `Campaign/` - рабочее дерево клона без незакоммиченных файлов; источник `docs/`, `templates/` - `origin/main` (клон переносится rebase, отставший клон с незакоммиченными правками получает отказ).
- `prompts/` на Диск не копируется. `ingest-inbox` отклоняет пакет с путём в `docs/`, `prompts/`, `templates/` (причина в `rejected`); принимаются только `.md` внутри `Campaign/`.

## Отчёт и удаление

Отчёт `sync-drive`: `profiles` (число и список файлов профилей), `reconnect`, `summary`: `planned` (только `--dry-run`: `create`/`write`/`delete <путь>`), `written`, `unchanged`, `deleted`, `conflicts` (`{path, copy}`), `refused`, `to_delete` (выпали из набора и не удалены), `legacy_to_delete` (прежние `.md`/`.csv` на смонтированном Диске с созданной нативной копией, не удалены), `legacy_waiting_native` (прежние файлы без нативной копии), `native_outside_set` (нативные файлы sync-state, выпавшие из набора; не удаляются), `outside_set` (на Диске вне набора, не удалены), `only_on_drive`, `missing_in_repo` (точные пути профилей, которых нет ни в выпуске, ни в клоне; для `feed.md` и PDF это норма).

Удаление выполняется только с `--prune` и без ошибок записи (отказ по лимиту ошибкой не считается). Два вида файлов смонтированного Диска:

- Прежние `.md`/`.csv` из набора профилей (файлы репозитория, в том числе `Campaign/`): удаляются, только если нативная копия этого файла записана в sync-state и существует по API в этом запуске. Файл, нативная копия которого не создана или отклонена, остаётся. Файлы `Campaign/` вне репозитория не удаляются.
- Выпавшие из набора файлы `published/`, `docs/`, `templates/`: не входят ни в один профиль и известны репозиториям (есть в `published/` технического репозитория, в клоне `Kenshi-Compain` на `HEAD`/`origin/main`, среди кадров `data/screenshots_archive/`, записаны в секции `synced` или в перечне прежних файлов выгрузки: `manifest.json`, `changes.json`, `timeline.jsonl`, `annotations.jsonl`, `screenshots/index.json`). Остальное (`.gdoc` вне sync-state, ручные файлы) только перечисляется в `outside_set`. `Campaign/` как выпавшая область не удаляется никогда. Область без единого файла набора (нет выпуска или клона) не чистится.

Файл удаляется штатно на смонтированном Диске (Drive for desktop переносит его в корзину, не стирает окончательно). Нативные файлы API не удаляет.

## Приём входящих пакетов

`ingest-inbox` запускается только явно: пакет меняет авторские документы. Просматриваются `*.md` и `*.txt` верхнего уровня `tmp/inbox/`. Клон должен быть на `main`, иначе приём не начинается. Отставший клон переносится на `origin/main` через rebase; конфликт отменяет rebase и останавливает приём. Механика общая с `deliver-companion` (`tools/git_sync.py`), autostash не используется: отставший клон с незакоммиченными правками получает явный отказ.

- `=== ФАЙЛ: <путь>.md ===` ... `=== КОНЕЦ ===` — запись файла. Допустимы только `.md` внутри `Campaign/`. Путь без префикса `Campaign/` отсчитывается от единственного каталога кампании. Блок закрывает только `КОНЕЦ`.
- `=== ВЫГРУЗКА S-YYYYMMDD-n ===` — артефакт сессии в `Campaign/<campaign>/archive/sessions/`; кампания берётся из поля `campaign:`. Существующий файл `archive/sessions/S-*` с другим содержимым не перезаписывается никаким блоком.
- `=== СТРОКА ХРОНОЛОГИИ ===`, `=== ПРАВКИ: ... ===` автоматически не применяются и перечисляются в отчёте в поле `manual`, а имя перенесённого пакета получает суффикс `-manual`.

Пакет применяется целиком: отсутствие завершающего `=== КОНЕЦ ===`, текст или неизвестный маркер вне блоков, блок внутри незакрытой выгрузки, недопустимый путь, неизменяемый артефакт, незакоммиченные правки в целевом файле или сбой записи отклоняют его, записанное откатывается, файл остаётся во входящих. Цель с совпадающими байтами считается применённой. Файлы без маркеров игнорируются.

Принятый пакет коммитится и отправляется в `origin main` игрового репозитория; только после успешного push он переносится в `tmp/processed/` со штампом времени UTC. При отказе commit или push пакет остаётся в `tmp/inbox/`, а повторный запуск доводит его до конца, в том числе если `origin/main` за это время ушёл вперёд без конфликта.

### Защиты приёма

Пакет, в котором хотя бы один записываемый файл нарушает защиту, отклоняется целиком до записи: клон не меняется, коммита нет, пакет остаётся во входящих, код возврата 1. Отказ перечисляет по каждому файлу причины (`rejected[].files[] = {path, reasons, accepted}`). Файл, совпадающий с main побайтно, не проверяется.

| Защита | Условие отклонения |
|---|---|
| Усечение | файл короче версии в `HEAD` клона (после синхронизации - `main`) более чем на 20 % по символам либо потерял заголовки второго уровня (`## ...`), которые были в версии main; новые файлы не проверяются |
| Ссылки | обёртка Google (`google.<домен>/search`, `google.<домен>/url`) либо абсолютный URL на файл самого репозитория (`https://github.com/<владелец>/<репозиторий>/...`, `https://raw.githubusercontent.com/<владелец>/<репозиторий>/...`; репозиторий - из remote `origin` клона и канонический `asaf1n/Kenshi-Compain`) |
| `S-*` | файл `archive/sessions/S-*.md` без frontmatter (`---` ... `---`) с полем `campaign:` |

`--accept <файл>` (повторяемый) снимает защиты для названного файла пакета: значение сравнивается с полным путём в клоне (`Campaign/<кампания>/...`), окончанием пути или именем файла. Остальные файлы пакета проверяются по-прежнему; если непринятый файл остаётся, весь пакет отклоняется. Принятые с флагом нарушения попадают в `processed[].guards` (`accepted: true`).

После принятого пакета с успешным push `ingest-inbox` вызывает `sync_chronicle` для `Campaign/` (состав - allowlist профилей, источник - клон). Недоступный Диск или Google API даёт предупреждение и `drive_sync.status=failed` в отчёте; приём остаётся успешным (код 0). Отчёт приёма содержит `commit` (короткий SHA) по каждому принятому пакету. `--no-push`: коммит в клон без push, пакет остаётся во входящих (`committed_not_pushed`), Диск не синхронизируется; повторный запуск без флага отправляет коммит и переносит пакет.

### Save-Packet.ps1

Сценарий для хоткея: `Get-Clipboard -Raw` -> снятие внешнего обрамления ``` (первая строка ```, ```markdown или ```md и последняя ```) -> LF -> запись в `tmp/inbox` Диска (UTF-8 без BOM; каталог - `KENSHI_GDRIVE_DIR` или `G:`, как в `ingest-inbox`) -> `ingest-inbox` -> отчёт.

- В буфере есть маркеры пакета (`=== ФАЙЛ: ... ===`, `=== ВЫГРУЗКА ... ===`): записывается как есть.
- Маркеров нет, но в первых 40 строках (frontmatter или заголовок) есть `S-YYYYMMDD-N`: текст оборачивается в `=== ВЫГРУЗКА S-YYYYMMDD-N ===` и принимается как `Campaign/<campaign>/archive/sessions/S-YYYYMMDD-N.md` (`campaign:` из frontmatter).
- Иначе ошибка (путь назначения неизвестен), файл не пишется.
- Имя во входящих: `S-YYYYMMDD-N.md` либо `packet-<UTC>.md` (без идентификатора, пакет с маркерами); занятое имя получает суффикс `-<UTC>`.
- Вывод: `принят, SHA <коммит>` (код 0) либо `отклонён: <файл>: <причины>` (код 1). Пакет, отклонённый защитой, удаляется из `tmp/inbox` (повтор с `-Accept`); отклонённый из-за сбоя git остаётся.
