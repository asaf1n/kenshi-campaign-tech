# Требования к Kenshi Campaign — MVP

## Цель

Автоматизировать локальное извлечение проверенных данных из сохранений Kenshi и их публикацию в предсказуемом текстовом формате, чтобы ChatGPT выступал интерфейсом просмотра состава, прогресса, изменений и планирования прохождения. Подтверждённая история игрового процесса хранится отдельно и переживает смену чатов.

## Потребитель и границы

- Основной пользовательский интерфейс — существующий проект ChatGPT, в том числе Android. Не требуется собственное веб-приложение.
- Рабочее место — ПК, на котором установлены Kenshi, существующие инструменты выгрузки и агенты Claude Code / Codex / Antigravity; реальная конфигурация устанавливается агентом.
- Git-репозиторий — история изменений и возможный канал доставки; способ доступа ChatGPT проверяется, резервный способ — ручная загрузка одного пакета артефактов.
- Литературная хроника вторична: достаточно корректных событий, последовательности и минимального рендера Markdown.

## P0 — обязательно для первой рабочей цепочки

1. **Инвентаризация:** найти существующие парсер, конвертер, файлы `kenshi-session/10`, `kenshi-session-diff/5`, текущие тесты и команды запуска. Описать поддерживаемые/неподдерживаемые поля и ограничение по модам.
2. **Безопасная обработка:** read-only доступ к оригинальным сейвам; исходные файлы сохраняются нетронутыми; входы идентифицируются хешами; сбои не портят предыдущий успешный результат.
3. **Импорт/нормализация:** сохранять реальные ID персонажей/предметов, если экспорт их предоставляет. Обработать одинаковые имена, пустые/неизвестные значения, отсутствующие поля. Использовать имеющийся формат без миграции либо предоставить совместимый адаптер с тестами.
4. **Снимок:** подготовить машиночитаемые данные для текущего состава, навыков, состояния, экипировки, денег, времени игры и доступных данных о мире. Отсутствующие категории указывать явно; не требовать их выдумывать.
5. **Изменения:** сравнивать только совместимые контрольные снимки; указывать пары snapshot IDs, числовые изменения и статус сравнения. При невалидности или неподдерживаемой категории показывать reason, а не «0 изменений».
6. **Публикация:** создавать `published/manifest.json`, `current.json`, `changes.json`, `brief.md`, `squad.md`. В `manifest` записывать schema/format, ссылки на артефакты, исходный снимок, время сборки и статус проверок. Генерировать atomically; при ошибке не менять последнюю успешную публикацию.
7. **Git/ChatGPT:** обеспечить проверяемый сценарий доступа ChatGPT к опубликованной версии через GitHub **или** документированный ручной перенос пакета. Проверить версию по commit/SHA или идентификатору снимка. `push` не выполняется без отдельного разрешения.
8. **Тесты:** покрыть повторный запуск, повторяющиеся имена, отсутствующие поля, invalid diff, reload/branch, сбой записи, отсутствие изменений и сортировку/округление. Сверить минимум два настоящих сохранения с отображаемыми в игре значениями.
9. **Сессия:** игровые сессии могут содержать несколько снимков. События/решения вводятся отдельно и не генерируются из diff как достоверные факты.

## P1 — после P0

- Маршруты и координаты, если извлечение действительно возможно.
- Индекс скриншотов и связывание с событиями.
- Исторические сводки по дням, группам, персонажам.
- Импорт заметок/подтверждений из ChatGPT в `timeline/events.jsonl`, с защитой от дубликатов и конфликтов.
- Генерация автономных HTML-таблиц для локального просмотра; не подменяет ChatGPT.

## Не входит в MVP

- Модификация сохранений, чит-коррекция, автоматическая игра и управление Kenshi.
- Собственная база данных, сервер, REST API, RAG, MCP-сервер, Docker, Kubernetes или полноценный frontend, пока недостаточность файлового обмена не доказана.
- Массовая повторная обработка сотен прошлых скриншотов до запуска цепочки на новых сейвах.
- Автоматическая генерация литературных глав и тотальный сбор лора из веба.
- Полное мультиагентное workflow ради каждой мелкой правки.

## Принятые правила при разногласиях

Приоритет: реальный сейв → проверенный результат существующего конвертера → подтверждённое пользовательское событие → вывод модели. Факты разных классов не смешивать. Несовместимые изменения старого формата и новые обязательные зависимости требуют письменного обоснования.
