# Одна линия кампании и идентичность снимка без внешних значений

Решение принято 2026-11-09 по заданию игрока. Понятие ветки удалено. Кампания ведётся одной линией. Идентичность снимка строится только из содержимого сейва и параметров разбора. Связи между снимками хранит индекс.

## Исходные данные

Обследованы `origin/main` на `e69a44e` в `kenshi-campaign-tech` и `9760d9d` в `Kenshi-Compain`.

До решения `snapshot_id` был хешем девяти полей: `source_kind`, `source_sha256`, `faction_sid`, `converter_sha256`, `mods_sha256`, `transform_sha256`, `campaign_id`, `branch_id`, `parent_snapshot_id`. Последние три задаёт оператор. Ветка — произвольная строка, унаследованная из последнего манифеста. Она определяла выбор родителя, допустимость diff, цепочку реестра и таймлайна, применимость ручных отметок.

Локальный `data/index.json` содержал 122 снимка: 87 `e2e-real` в ветке `main`, 34 `hot-lon` в ветке `hot-lon-chapter-x-final` и одну запись `hot-lon` в `main` (`sha256-bff01b59…`, Day 128 15:36, без родителя). Ручные отметки смешиваются с автостатусом только в итоговом поле `status` реестра; источник фиксирует `status_source`.

## Решение

Нормативное описание — [контракт данных](../data-contract.md#реестр-снимков-kenshi-index2). Здесь — выбор и его основания.

- Идентичность снимка — хеш шести полей источника и разбора (`source_kind`, `source_sha256`, `faction_sid`, `converter_sha256`, `mods_sha256`, `transform_sha256`). `provenance.json` получает формат `kenshi-snapshot/2` без внешних полей. Пересчёт `snapshot_id` по полям provenance в коде отсутствует: валидаторы, `rebuild_index` и проверка публикации используют его как непрозрачную строку. Старые идентификаторы остаются действительными. `transform_sha256` и раньше менял идентификатор при каждой правке `tools/*.py`, поэтому смена формулы нового класса несовместимости не создаёт.
- Родитель — голова кампании в индексе. Оператор родителя не задаёт: `--parent-snapshot-id`, `--branch-id`, `-BranchId` и команды `branch …` удалены.
- Повторная регистрация существующего снимка не меняет ни запись, ни голову. Перевод головы на старый снимок молча исключил бы из цепочки все более поздние снимки, их события и свидетельства реестра. Настоящая перезагрузка в игре даёт новый файл сохранения с откатом времени и распознаётся по нему.
- Перезагрузка — регрессия игрового времени относительно родителя, отдельной сущности нет. Правило исключения отменённых снимков уже действовало в `_history` реестра; теперь оно общее (`tools/index.py: campaign_chain`). Исключение из правила «невалидный diff прерывает публикацию» действует, только если других проблем сравнения нет.
- Формат события таймлайна не повышается. `branch_id` был необязательным, его генерировал только конвертер для автособытий, которые пересоздаются при каждой публикации. Локальный журнал `timeline/events.jsonl` таких событий не содержит. Остальные форматы повышены: `kenshi-index/2`, `kenshi-publication/2`, `kenshi-location-registry/2`, `kenshi-location-progress/2`.

## Миграция и обратная совместимость

`python -m tools.campaign index migrate [--apply]` переводит `kenshi-index/1` в `kenshi-index/2`. Без `--apply` печатается план. С `--apply` создаётся резервная копия `index.json.v1-<UTC>.bak`, затем выполняется атомарная запись и проверка схемы и связей. Записи снимков сохраняются вместе с `parent_snapshot_id`. Голова кампании — голова ветки, содержащей последний по `registered_at` снимок кампании. Записи без `campaign_id` отклоняются. Повторный запуск на `kenshi-index/2` ничего не меняет.

Связи не восстанавливаются автоматически. Сшивка отрезков Day 127–131 детерминированно возможна. Правило: корень без родителя связывается с предыдущим по `registered_at` снимком той же кампании, если его игровое время не больше и `compare_with_parent` подтверждает состав. На локальных данных правило даёт `d6c01ae2 → 35ff6ca4 → 1de8a2d8` и полную цепочку от Day 127 20:18. `c1fa9791` и `bff01b59` становятся боковыми листьями Day 128 15:36. Provenance старых снимков фиксирует `parent_snapshot_id = null` как параметр прежнего запуска, а не как утверждение об игре, поэтому связь в индексе ему не противоречит. Решение о сшивке принимает игрок; команда в этой задаче не реализована.

Чтение старых данных:
- `provenance.json` `kenshi-snapshot/1` читается. `index rebuild` берёт связи из существующего индекса, иначе из `parent_snapshot_id` provenance `/1`;
- просмотрщик карты и `tools/cartography.py` принимают манифесты `kenshi-publication/1` и `/2`, реестры `/1` и `/2`. Поле `branch_id` старых выпусков игнорируется;
- ручные отметки `kenshi-location-progress/1` читаются: запись приводится к ключу `instance_id`, при повторе берётся высший статус. История файла в Git остаётся базой проверки «не удалено и не понижено»;
- закрытые сессии `archive/sessions/` не меняются.

Порядок на машине игрока: очистка тестовых записей индекса (`.tmp\cleanup_test_index.py`), `index migrate --apply`, обычный запуск `Initialize-Pipeline.ps1` с доставкой.

## Что не делается

- Параллельные линии одной кампании не поддерживаются. Альтернативная линия — отдельная кампания с явным `--allow-new-campaign`, начатая с нового сохранения. Сейв, уже зарегистрированный в одной кампании, в другую не регистрируется: при той же версии конвертера он даёт тот же `snapshot_id`, и регистрация отклоняется.
- Diff перезагрузки с предполагаемым загруженным состоянием (ближайшим предком с меньшим временем) не строится: совпадение с загруженным сейвом не доказано.
- Существующие снимки не переименовываются, provenance `/1` не переписывается.
- Сшивка отрезков Day 127–131 не выполняется без решения игрока.
