# Архитектурные границы

## Цепочка

```text
Kenshi saves [read-only] / imported JSON exports
        |
native reader (tools/) / JSON importer
        |
normalizer + validator + diff (supported contracts)
        |
immutable snapshots / campaign line index / events ledger
        |
locator + renderer + screenshots collector + atomic publisher
        |
published/{manifest.json,extended/current.json,changes.json,locations.json,
           world_reference.json (без regions_map и source_hashes),location_registry.json,unique_entities_registry.json,timeline.jsonl,brief.md,squad.md,changes.md,
           tables/{index.md + 24 CSV: отряд, экипировка, инвентари, расы, склады, постройки, исследования, каталог строительства, ресурсы биомов, цены, торговые записи, NPC,
                   уникальные сущности, Town Overrides, дипломатия, реакции мира, справочник юнитов},
           screenshots/{index.json,index.md,*.jpg; annotations.jsonl, feed.md при содержательном OCR; screenshots_latest.pdf вне git}}
        |
verified GitHub delivery (основной канал: проекты ChatGPT читают main) + Google Drive sync (односторонняя копия main и выгрузки в нативных Docs/Sheets; allowlist-профили, docs/gdrive-sync.md) / manual transport fallback
        |
LLM (чат-ИИ): verify manifest -> read release -> visual context -> propose plans and events
```

Никакой сервисный процесс на постоянном сервере не требуется. Среда Antigravity/Codex/Claude управляет разработкой и запуском локального кода, **не становится** runtime-зависимостью чтения сейва.

## Владение данными

| Область | Автор изменений | Потребитель | Политика |
|---|---|---|---|
| Исходные сейвы и файлы игры | Kenshi, пользователь | нативный парсер | read-only, не в Git |
| Исходные скриншоты игры (`_screens`) | Kenshi, скриншоты F8 | screenshots collector | read-only, оригиналы никогда не удаляются и не изменяются |
| Импортированные JSON-выгрузки | внешний источник | нормализатор | неизменяемые входы, фиксировать хеш |
| `data/snapshots/` и `data/diffs/` | детерминированный pipeline | publisher | менять только инструментами, иммутабельность исторических снимков |
| `timeline/events.jsonl` | подтверждённые записи пользователя/импорт | publisher и чат-ИИ | append-only по event ID; изменение — отдельное корректирующее событие |
| `sessions/` | пользователь/чат-ИИ через подтверждённый импорт | planner/summary | планы и результаты без подмены игровых фактов |
| `published/` | publisher | GitHub / чат-ИИ | полностью генерируемый release bundle (включая `location_registry.json`, `unique_entities_registry.json` и `tables/unique_entities.csv`), предыдущий успешный release не портить; не коммитится в технический репозиторий, доставка через `deliver-companion` |
| Клон `Kenshi-Compain` при доставке | `deliver-companion` | чат-ИИ / GitHub | порядок: fetch -> fast-forward до `origin/main` -> наложение подтверждённого ручного слоя `locations_progress.json` на `location_registry.json` и `unique_entities_registry.json` (свидетельства зачистки локаций и боссов при наличии `personal_evidence`) с перегенерацией `tables/unique_entities.csv` -> при `invalid` ручном слое статус `degraded` и сохранение прежних реестров/таблиц в клоне без перезаписи -> запись `published/`, `docs/reference/encounters.md` и картографических производных (`regions_map.svg`, `regions_adjacency.json` — при совместимом `sites/map/index.html`) -> коммит -> push; грязный или расходящийся клон и незавершённый rebase/merge - отказ до записи; при отклонённом push - одна повторная попытка (доставочный коммит пересоздаётся поверх нового `origin/main`), конфликт отменяет rebase, `status=failed` |
| `docs/`, `contracts/` | разработчик и reviewer | все | изменения контрактов — через независимую проверку |

## Развилки и сравнение

- Один игровой сеанс может иметь несколько сохранений; session_id != snapshot_id.
- Идентичность snapshot — содержимое исходного входа и параметры разбора. Родитель — голова кампании в индексе на момент регистрации. Время файла само по себе не доказывает игровую последовательность.
- Загрузка раннего сейва распознаётся по откату игрового времени относительно родителя: более поздние снимки исключаются из цепочки, diff через перезагрузку не строится.
- Отсутствие поля означает «не получено», а не ноль. Невалидный diff не должен выглядеть как «изменений нет».

## Доступ чат-ИИ моделей (LLM ассистентов)

- Облачные чат-ИИ модели (LLM ассистенты) не читают локальную папку без поддерживаемого механизма соединения. `Project Sources` не являются двусторонней ФС.
- Выходной bundle должен быть небольшим, самодостаточным и пригодным для чтения как в GitHub, так и после ручной загрузки в чат.
- В запросах чат-ИИ моделей всегда указывать идентификатор и дату опубликованного снимка. Если загрузка не удалась — явная ошибка актуальности.
- Запись обратно в репозиторий — отдельная опциональная функция, не предполагать её наличие по факту чтения.
- **Визуальный контекст скриншотов**: доступен через прямые Raw-ссылки GitHub (`https://raw.githubusercontent.com/...`), ссылки на просмотр в GitHub blob, а также программный реестр `screenshots/index.json` и индекс `screenshots/index.md`. При содержательном машинном OCR добавляются `annotations.jsonl` и `feed.md`. Модели анализируют сами кадры, разметка служит навигацией.

## Выбор инструментов

Для вычислений использовать существующие модули `tools/` и файловые контракты; новые зависимости вводить только при необходимости. Параллельные агенты работают с независимыми задачами или worktree; один автор на раздел данных и контракта.

## Реализованная граница extract

`python -m tools.campaign extract` → `tools.config.Config` → `tools.extraction.extract` → нормализация → неизменяемый каталог снимка. Для `export` читаются только исходный JSON и проектные файлы, игра/движок сохранения не запускаются. Для `save` адаптер запускает нативный изолированный воркер `python -I -B tools/converter_worker.py`, передавая конфигурацию через UTF-8 JSON в stdin. Рабочий каталог процесса, `session_export.CACHE_DIR` и перенаправление поиска pycache находятся в `.extract-*` под выходным корнем. После завершения временный каталог удаляется.

Модули `session_export.build_snapshot`, `saves.read_quick_save`, `kenshi_gd.read_file`, `gamedb.load_index` интегрированы непосредственно в проектный код `tools/` как нативный движок извлечения данных. Внешний репозиторий конвертера выведен из эксплуатации. `session_export.run` и его publisher не вызываются. `collect_stable` заменён прямым `collect`: автоматический повтор на изменившемся источнике не скрывает изменение между проверками SHA-256. До запуска проверяются quick.save и активные platoon; после — исходники нативного движка (`ENGINE_FILES`), прочитанные моды и весь сейв. Неизвестные sid остаются диагностикой. Формулы характеристик и их точность сохраняют строгий паритет.

Доступны извлеченные движком состав, ID, принадлежность отрядам, позиция, характеристики, навыки, здоровье, экипировка, протезы, инвентарь, снабжение, время/деньги мира, исследования и собственность. Доступность конкретного поля зависит от источника и модов; отсутствие поля и пустой список различаются. `ps:*` использует portrait_serial; `h:*` — запасной handle с ограниченной устойчивостью. Географическое разрешение координат, события из diff и независимая сверка показателей с UI в этот этап не входят.

Выход, staging и кэш проверяются после нормализации `Path.resolve`, включая junctions: запрещено пересечение с источником, корнями сейвов, игрой и Workshop, в обе стороны вложенности. Внутренние ссылки в сейве отвергаются. Python audit hook дочернего процесса разрешает запись только в его временную папку и блокирует внешние процессы, создание ссылок, сеть и новую загрузку native-библиотек. Зафиксированная запрещённая попытка приводит к отказу даже при перехвате исключения. Это защита от файловых побочных эффектов используемого Python-кода, не полноценная OS sandbox для недоверенного произвольного native-кода. Права оригинальных файлов не меняются.

`current.json` и `provenance.json` сначала создаются в `.snapshot-*` на том же томе; готовый каталог регистрируется переименованием. Входы и метаданные проверяются до регистрации. Существующий ID сравнивается побайтово, не переписывается. Прерывание процесса до регистрации может оставить только временный каталог, не признанный снимком.

## Реализованная граница pipeline и атомарной публикации

Сквозной срез: `python -m tools.campaign pipeline` связывает `extract` -> `diff` -> `resolve_locations` -> `render` -> `collect_screenshots` -> `validate` -> `publish`.
- `tools.diff`: вычисление детерминированного diff по действующему контракту с сохранением устойчивого ID во всех категориях изменений, агрегацией transfers по ID и sid, запретом склеивания разных `ps:*` по имени, поддержкой baseline / non-baseline режимов и сохранением в `data/diffs/<diff_id>.json`.
- `tools.rendering`: генерация русскоязычных `brief.md` и `squad.md` строго из валидированных JSON без внешних зависимостей и wall-clock времени, обеспечивая 100% детерминизм побайтового совпадения при повторном рендере.
- `tools.screenshots`: безопасный сбор скриншотов из `<KENSHI_DIR>/_screens` (или `KENSHI_SCREENS_DIR`) за скользящее 7-дневное окно (`now - 7d`) без изменения оригиналов, защита от незавершённой записи, генерация `screenshots/index.json` (`kenshi-screenshots-index/1`) и `screenshots/index.md`, автоматическая ротация и очистка устаревших изображений. `tools.screenshot_publish`: уменьшение кадров до 1600 px, локальный архив `data/screenshots_archive/` и отбор 20–30 ключевых кадров для публикации.
- `tools.tables` (с `tools.gamedb` и `tools.itemstats`): `tables/` из снимка, `locations.json` и справочника игры (индекс и записи по файлам набора модов снимка, кэш `game_cache_dir`, по умолчанию `data/cache`); чистые функции без обращения к сейву и сети. Включает формирование `tables/unique_entities.csv` на основе реестра сущностей. Граница слоёв: конвертер извлекает и выгружает значения игры (сырые `relation`, `state_code`, шаблоны, базовые цены) и сверенные `calc_*`; оценочных классов и выводов нет, их делает потребитель. Без справочника игры таблицы на его данных пусты с предупреждением, значения не подставляются.
- `tools.unique_entities_registry`: детерминированное построение реестра уникальных сущностей (`published/unique_entities_registry.json` по схеме `kenshi-unique-entities-registry/2` с обратной совместимостью с `/1`) из текущего снимка, справочника мира `world_reference.json`, записей игры (`game_records`), индекса (`game_index`) и активного таймлайна (`timeline/events.jsonl`). Модуль разрешает привязку уникальных NPC к локациям по цепочке вложенности шаблонов FCS (`CHARACTER` → `SQUAD` → `TOWN` → `INSTANCE`), определяет динамическое состояние (`state_code`, `player_defeat_flag`, статус в отряде игрока по строгому 5-компонентному `handle` и сопоставлению имени), отделяет категорию сущности (`category`: `recruit`, `boss`, `world_leader`, `significant_npc`, `unique_npc`) от источника классификации (`origins`), извлекает подтверждённые персональные события взаимодействия `personal_evidence` по маркеру `[npc_sid=...]`, классифицирует боссов по происхождению (`game_bounty`, `world_state`, `meitou_holder`, `custom_catalog`) и формирует каталог 26 базовых моделей оружия Мейто (грейд `52293-rebirth.mod`, мастер Кросс `52288-rebirth.mod`) со статическими держателями, фактически наблюдаемыми экземплярами игрока и ортогональными статусами наблюдения (`observation_status`) и происхождения (`provenance_status`). Валидация выполняется через `validate_unique_entities_registry`.
- `tools.encounters`: чистая сборка `docs/reference/encounters.md` игрового репозитория из CSV справочника юнитов в `published/tables/`; вызывается только `deliver_companion` (файл попадает в коммит выгрузки), в `published/` не пишет.
- `tools.cartography`: проверка геометрии (`--verify-geometry`, локально `--local`) и пересборка таблицы соседства (`--build-adjacency`) по растру `data/world/<world_ref_id>.json`; проверка совместимости просмотрщика при доставке (`check_viewer_compat`). Сводку и SVG-экспорт формирует только просмотрщик. Подробно — `docs/cartography.md`.
- `tools.validation`: валидация пакета по схемам `Draft202012Validator`, проверка доступности и локальности артефактов внутри `published/`, проверка целостности и хешей скриншотов, семантическая проверка связи `snapshot_id`/`parent_snapshot_id`, проверка отсутствия персональных путей пользователя (`C:\Users\...`) и токенов/секретов во всех артефактах.
- `tools.publisher`: атомарная публикация release bundle на Windows с использованием протокола `staging -> backup -> switch -> cleanup`. Включает `unique_entities_registry.json` в release bundle и регистрирует его в `manifest.json` (`artifacts.unique_entities_registry`). Предыдущая успешная публикация сохраняется в `published.backup` до подтверждения валидности новой версии. При возникновении исключения или занятом файле выполняется автоматический откат к backup. Отслеживаемый файл `published/.gitkeep` переносится в staging и сохраняется побайтово. При аварийном завершении процесса самовосстановление выполняется при следующем запуске.
- `tools.deliver_companion`: доставка проверенного release bundle в игровой репозиторий. Интегрирует ручной слой прогресса кампании (`locations_progress.json`) через чистую функцию `apply_progress_to_unique_entities`, обогащая локации свидетельствами зачистки `cleared_evidence`, а боссов — строго при одновременном наличии зачищенной локации и персонального подтверждения `personal_evidence`. После обогащения JSON перегенерирует `tables/unique_entities.csv`. При невалидном ручном слое (`progress_status == "invalid"`) фиксирует статус доставки `degraded` и блокирует затронутые артефакты (`location_registry.json`, `unique_entities_registry.json`, `tables/unique_entities.csv`), сохраняя ранее подтверждённые данные клона без перезаписи.
- **Граница слоёв и инвариант зачистки**: конвертер извлекает и фиксирует исключительно объективные факты сохранений и статических баз данных игры, никогда не вынося самостоятельных суждений о победах или зачистках без подтверждённого ручного слоя кампании. Поле `cleared_evidence` у всех боссов в локальном артефакте `published/unique_entities_registry.json` конвертера всегда строго равно `null`. Оно обогащается исключительно в процессе доставки в игровой клон (`deliver-companion`) на основе подтверждённого авторского слоя `locations_progress.json` кампании при наличии персонального подтверждения в таймлайне.

Независимые проверки используют `unittest` и временные данные. `tests/check_converter.py` выполняет настоящую интеграцию парсера на синтетическом GameData; `tests/check_live.py` принимает явно указанный реальный вход, запускает CLI дважды и сохраняет хеши/коды/время. Синтетическая интеграция не заменяет приёмку на двух реальных сейвах. Команды и переменные окружения приведены в `README.md`.

## Кадры при пересборке старого снимка (ограничение, предложение)

Текущее поведение (`tools/publisher.py`, блок скриншотов; `screenshots.collect_recent_screenshots`): окно кадров — `[generated_at − 7 суток, generated_at + 5 минут]` по `st_mtime` файла. `generated_at` — аргумент `publish` либо текущее время; время снимка (`registered_at`, игровое время) не используется. При пересборке старого снимка окно привязано к дате пересборки: в выпуск попадают кадры новее снимка, а кадры, близкие к снимку, но старше 7 суток от пересборки, выпадают. Подтверждено чтением кода; прогон пересборки на кадрах не выполнялся.

Предложение (решение за пользователем, код не менялся): брать кадры не новее `registered_at` снимка: верхняя граница окна — `registered_at` (с допуском 5 минут), нижняя — верхняя − 7 суток. Место изменения — вычисление `cutoff_dt`/`gen_dt` перед вызовом `collect_recent_screenshots`, который уже принимает обе границы. До принятия решения пересборка старого снимка с каталогом скриншотов даёт ленту, зависящую от даты пересборки; для приёмки таблиц публикация выполняется без каталога скриншотов.

## Доставка нескольких кампаний (решение за пользователем)

`Kenshi-Compain/published/` хранит одну кампанию; схема для второй кампании не реализована. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Отдельный репозиторий или каталог доставки на кампанию (`--deliver-to`, `KENSHI_COMPANION_DIR`) | Нет изменения контракта потребителя; изоляция истории и прав | Дублирование инструкций чат-ИИ и канона; больше мест синхронизации (Диск) |
| Подкаталог `published/<campaign_id>/` в одном репозитории | Один репозиторий и общие инструкции | Меняется контракт потребителя (пути в инструкциях компаньона, `deliver_companion`, `gdrive_sync`); риск смешения кампаний |
| Ветка репозитория на кампанию | Пути не меняются | Переключение веток на одной машине; доставка и Диск зависят от текущей ветки; легко доставить не в ту |

Для любого варианта сохраняется проверка принадлежности сейва (раздел «Проверка принадлежности сейва кампании» в `docs/data-contract.md`). Папка сохранений Kenshi общая для всех прохождений, поэтому единственная защита от чужой игры - состав персонажей; неизменяющая команда `check-save` служит для автоматического выбора папки в `Initialize-Pipeline.ps1`.
