# Контракт данных и совместимость

## Обязательное исходное обследование

Внешний `session_export.py` формирует `kenshi-session/10`; `session_diff.py` — `kenshi-session-diff/5`. Известные поля см. `references/observed-export.md`. Реализован профиль нормализованного снимка; bundle публикации ниже пока проектируется. Полной JSON Schema бинарного GameData и legacy-экспорта нет.

`current.json` сохраняет `format="kenshi-session/10"`, игровые поля и доступную точность без дополнительного округления. Нормализатор проверяет обязательные объекты `save`, `world`, `meta`, списки `characters`, `squads`, `warnings`; неизвестные игровые поля сохраняет. Это структурная проверка профиля, не полная валидация игровых значений.

## Неизменяемый снимок: `kenshi-snapshot/1`

Один каталог `data/snapshots/<snapshot_id>/` содержит `current.json` и `provenance.json`. Метаданные происхождения имеют формат `kenshi-snapshot/1`; оба файла записываются через staging одного тома до регистрации каталога. Существующий каталог допускает только побайтовое совпадение обоих файлов. Неполный каталог или расхождение вызывает отказ, без перезаписи.

Канонический JSON: UTF-8 без BOM, ключи отсортированы, разделители `,` и `:`, один завершающий LF; `NaN`, бесконечности и повтор ключа запрещены. Персонажи сортируются по ID, отряды по `squad_id`, предупреждения сортируются с устранением точных повторов. Порядок массивов игровых данных без объявленной семантики множества сохраняется.

`source_sha256` для `export` — SHA-256 исходных байтов JSON до очистки. Для `save` — SHA-256 канонического отсортированного списка `[relative_path, sha256]` всех файлов каталога, включая не использованные парсером. Состав и хеши сравниваются до/после всего извлечения. Ссылки/junctions внутри сейва не поддерживаются и вызывают отказ. Сохранённый `source_files` позволяет проверить перечень; абсолютный путь источника не сохраняется.

`snapshot_id` имеет вид `sha256-<64 hex>`: хеш канонического объекта с `source_kind`, `source_sha256`, эффективным `faction_sid`, `converter_sha256`, `mods_sha256`, `transform_sha256`, `campaign_id`, `branch_id`, `parent_snapshot_id`. Отпечаток преобразования включает проектные `tools/*.py`; отпечаток нативного движка (`converter_sha256`) — отсортированные пары относительного пути и SHA-256 исходников из фиксированного списка `ENGINE_FILES` (`tools/*.py`). Внешний конвертер выведен из эксплуатации. Отпечаток модов включает порядок и SHA-256 реально прочитанных файлов данных и локализации, список и отсутствие модов. Метки времени кэша не являются версиями данных.

Для `export` конвертер не запускается: `converter=null`, версии исходного конвертера и байтов модов неизвестны. В `mods` сохраняются очищенные метаданные экспорта с `status="export_metadata_only"`; различающиеся исходные байты имеют разные source hash даже при одинаковых фактах. Отсутствующий контекст кампании/ветки явно отмечается; родитель не выводится из mtime. Полнота реестра и совместимость родителя здесь ещё не проверяются. `game_time` в provenance — объект `{day,time}` из `world`, допускающий null; он не берётся из файлового времени.

Удаляются `save.path`, файловые `save.name`, `save.kind`, `save.saved_at`, весь `changes`, а из `meta` рекурсивно — `exported_at`, `timings_ms`, `session_file`, `cache`, `cache_file`, `cache_path`. Файловое имя/тип и mtime исключены потому, что одинаковые байты сейва могут копироваться в другой каталог. Игровое время сохраняется в `world`.

Строки и вложенные метаданные очищаются от абсолютных Windows/UNC и пользовательских POSIX-путей, полей паролей/токенов/ключей, типовых строк авторизации и секретов в URL. Неизвестный произвольный текст невозможно классифицировать как секрет без правила; перед публикацией требуется проверка фактического пакета. Входной `changes.history` целиком исключён, он не является подтверждённым таймлайном.

Повтор непустого `characters[].id` всегда вызывает отказ, в том числе между отрядами. `ps:*` — предпочтительный ID; `h:*`, имя вместо ID или отсутствующий ID сохраняются с ограничением в `diagnostics.limitations`. Связывание участников по имени не выполняется. Отсутствующий ID не заменяется вымышленным.

Для `save` обязательны читаемый `quick.save` с записью мира типа 56, каталог `platoon/`, активные файлы отрядов игрока из реестра и полностью читаемые активные `.platoon`. Старые файлы вне реестра не определяют состав. Запись типа 56 содержит также параметры сложности кампании (`cod`, `gdm`, `ht` и др.) и тумблеры ИИ отряда (`share`, `heal`, `ditch` и др.), описанные в [документации настроек](kenshi-settings.md). Для `export` наличие бинарного сейва не требуется. Агрегатные расхождения `quick.save: members/squads` не заменяют фактический состав и сохраняются как предупреждения. Предупреждения по `player_towns`/`zone/`, исследованиям, неизвестным sid и модам не удаляются; `diagnostics.categories` отмечает `available`, `unavailable`, `incomplete` или `inconsistent`. Наличие данных не означает независимой сверки с UI.

## Реестр снимков и веток: `kenshi-index/1`

Проектный контракт `contracts/index.schema.json` (JSON Schema Draft 2020-12) фиксирует реестр снимков, отслеживание родительства и веток в `data/index.json`:
- Формат: `format: "kenshi-index/1"`.
- Метаданные: `updated_at` (UTC ISO-8601), `active_branch_id` (`string | null`).
- Ветки (`branches`): `{branch_id: {"name": ..., "head_snapshot_id": ..., "created_at": ...}}`.
- Записи снимков (`snapshots`): отображение `snapshot_id -> record`:
  - `snapshot_id`, `parent_snapshot_id` (или `null`), `branch_id`, `campaign_id`, `game_time` (`{"day": ..., "time": ...}` или `null`), `world_ref_id`, `source_kind` (`save`/`export`), `source_sha256`, `registered_at` (UTC ISO-8601).
- Инварианты целостности:
  - Атомарная запись через staging-файл и `replace` на одном томе под файловой блокировкой.
  - Защита от циклов в графе родительства ($A \to \dots \to A$) и защита от сирот (несуществующих родителей).
  - Уникальность `snapshot_id`: совпадение данных идемпотентно, конфликт вызывает отказ.
  - Восстановление `rebuild_index` из каталогов `data/snapshots/*/provenance.json` без автоматического назначения текущего снимка публикации.
- Семантика reload и хронологии:
  - Сравнение между параллельными ветками или ветками без связи предка блокируется: `diff.valid = false`, `reason = "different_branches"`. Синхронно `locations.movement.valid = false`, исключая ложные прямолинейные перемещения и потери ресурсов/навыков.
  - Обратное время (`to < from`) дает `valid: false`, `reason = "game_time_regression"`.
  - Возрастающее время ($game\_time(C) > game\_time(B)$) при общем родителе $A$ (reload) НЕ делает $C$ продолжением $B$.
  - Явный выбор ветки через CLI разрешает публикацию нового снимка $C$ от его легитимного предка $A$ (или как новый корень без предка).

## Контракт bundle: `kenshi-publication/1`

Реализованный release bundle в `published/`:

```text
published/
  manifest.json
  current.json
  changes.json
  brief.md
  squad.md
  locations.json
  world_reference.json
  timeline.jsonl
  .gitkeep
```

`manifest.json` содержит: `format: "kenshi-publication/1"`, `generated_at` (UTC ISO-8601), `snapshot_id`, `source_kind` (`save`/`export`), `source_format`, `source_sha256` (хеш именно указанного source_kind), `artifacts` (пути относительно `published/`), `validation` (`passed` или `failed`), а также `world_ref_id` (`sha256-...`), связывающий пакет с детерминированным справочником мира. При успешном выпуске `validation.status="passed"`; неуспешный bundle не публикуется как актуальный. `snapshot_id` однозначно связывает файлы; в `changes.json` должна быть явная пара `from`/`to` или `valid:false` с причиной.

Схема допускает необязательные `parent_snapshot_id`, `branch_id`, `game_time` (`string | number | null`, игровое время). Относительные пути `artifacts.locations` и `artifacts.world_reference` регистрируют географические артефакты в пакете публикации. Неизвестные свойства manifest запрещены.

Публичные данные не должны содержать абсолютных путей пользователя из `save.path`. Не публиковать сырые сейвы, произвольные большие текстовые поля, секреты или неразобранные бинарные блоки. Имена персонажей и числовые игровые показатели допустимы; автоматическая валидация проверяет публикуемый пакет на локальные пути пользователя (`C:\Users\...`, `/home/...`) и секреты.

`brief.md` — краткая сводка с `snapshot_id`, днём игры, составом, деньгами, структурированными географическими группами отряда, ключевыми изменениями и ссылками на детальные JSON. Все значения ссылаются на соответствующие поля JSON; при отсутствии сведений выводится «не получено».
`squad.md` — подробный структурированный состав по отрядам и участникам (ID, раса, состояние здоровья, характеристики, местоположение со статусом и расстоянием, экипировка, инвентарь).

## Совместимый diff: `kenshi-session-diff/5`

Сравнение двух неизменяемых снимков сохраняет совместимость с форматом `kenshi-session-diff/5` со следующими обязательными расширениями:
- Устойчивый `id` персонажа сохраняется во всех элементах изменений: `skills`, `equipment`, `prosthetics`, `inventory`, `health`, `roster.squad_changed`, `roster.status_changed`.
- Сортировка участников ведётся по строгому ключу `(name, id)` с детерминированным порядком пустых имён.
- `transfers` агрегируется по `(sid, char_id)`: имена участников служат метками, при совпадении имён к метке добавляется `[id]`, исключая потерю или склеивание передач.
- Запрещено склеивание разных `ps:*` по имени; смена устойчивого ID означает разные сущности (`joined`/`left`), а не `id_changed`.
- Baseline и Non-baseline режимы: при отсутствии предыдущего снимка `from: null`, `valid: false`, явный `reason` и список `problems`.
- Неотслеживаемые и неполные категории (`research`, `property`, `position`) выносятся в `not_compared` с указанием причины, исключая ложные нули изменений.
- Детерминированный результат сохраняется в `data/diffs/<diff_id>.json`.

## Идентичность и порядок

- Prefer ID из игры/экспортёра; имя — только метка отображения. Повторяющиеся имена допускаются.
- Контрольный снимок идентифицируется хешем источника плюс корректной информацией о кампании/ветке; если этих данных недостаточно, явно фиксировать ограничение.
- Проверить значение исходных `from/to`: файловое имя или timestamp не являются гарантией логического родительства.
- Diff по персонажам сравнивает ID и категории с одинаковой семантикой. Отсутствующие категории и невалидные пары получают отдельный статус.
- Округление значений применяется только для представления; сравнение ведётся на доступной исходной точности.
- Для idempotency сериализовать JSON детерминированно; временную метку сборки разрешено обновлять только при реальной публикации новой версии, не на каждом dry-run.

## Подтверждённые игровые события

Формат `kenshi-event/1` описан в `contracts/timeline-event.schema.json`. Обязательные поля: `event_id`, `format`, `session_id`, `recorded_at`, `kind`, `status`, `summary`, `evidence`. `game_day` и `snapshot_id` необязательны. `snapshot_id` при импорте должен существовать в индексе и быть связан с указанной сессией.

- `observed`: непосредственно наблюдаемое состояние со ссылкой на известный снимок или валидный diff. Оно не доказывает причину изменения.
- `confirmed`: явная запись пользователя (`user_note`) или проверенный скриншот (`screenshot`). Указание этого статуса — действие автора; импорт не интерпретирует текст и не подтверждает его истинность автоматически.
- `inferred`: гипотеза. Хранится в журнале, исключается из опубликованной фактической проекции. При отдельном рендере исходного журнала показывается только под заголовком «Неподтверждённые гипотезы (inferred)».

Источники задаются безопасными относительными POSIX-путями внутри корня кампании. Для `snapshot` допустим также известный ID; он разрешается в `data/snapshots/<id>/current.json`. `diff` ссылается на `data/diffs/<id>.json` с `valid=true` и известными `from`/`to`. Подтверждённая запись с недоступным источником отклоняется. Содержимое скриншота автоматически не распознаётся. Абсолютные пути, `..`, Windows-устройства, альтернативные потоки и выход через junction/symlink запрещены.

`tools.timeline.import_events` проверяет весь пакет под единой блокировкой writer (`msvcrt` в Windows). Запись выполняется заменой временного файла на том же томе после `flush`/`fsync`; прежние байты остаются точным префиксом. Повтор идентичного события — no-op; тот же ID с иным содержимым — `ValueError: Конфликт event_id`. Ошибка проверки или записи не меняет журнал. Повреждённые/пустые строки, повторные ID и незавершённая последняя строка блокируют импорт и публикацию. Восстановление выполняет владелец из проверенной копии; автоматическое отбрасывание строк запрещено. Файл блокировки остаётся на диске, занятость определяется ОС.

Коррекция — отдельное событие `kind="correction"` с обязательным `corrects_event_id`, собственными ID, статусом и источником. Ссылка должна существовать в объединённом журнале; самоссылки, циклы и несколько прямых коррекций одного события запрещены. Повторное уточнение ссылается на предыдущую коррекцию. Исходные записи сохраняются. `resolve_timeline` выбирает последнее `observed`/`confirmed` в каждой цепочке; `inferred`-коррекция не отменяет доказанный факт. Подтверждённая коррекция гипотезы становится действующим фактом. Порядок вывода — `game_day`, затем `event_id`; неизвестный день идёт последним. `recorded_at` фиксирует время записи, а не игровую последовательность.

### Авторские сессии и ветки

Команда `timeline session` создаёт `sessions/<session_id>/session.json` с полями `session_id`, `snapshot_ids` и `notes.md` по шаблону `templates/session-notes.md` либо из переданного Markdown. Привязка сессии неизменяема и может включать несколько снимков. Повтор создания той же привязки не переписывает заметки. Планы и результаты в заметках редактируются автором; текст заметок сам по себе не создаёт событий. `session_id` отличается от всех связанных `snapshot_id`.

`filter_events_by_branch(events, branch_id, index_data, sessions=None)` отбирает события по цепочке предков головы ветки, включая общего предка до reload. Publisher ограничивает эту цепочку выбранным `snapshot_id`, даже если голова ветки уже продвинулась дальше. Событие без `snapshot_id` включается только когда все явные снимки его сессии входят в выбранную цепочку. Без привязки или при сессии, пересекающей параллельные ветки, такое событие не публикуется. Коррекции, цель которых не попала в ветку, также исключаются. Индекс `kenshi-index/1` не расширяется полями сессий.

### Публикация таймлайна

Publisher читает журнал целиком, проверяет его, фильтрует ветку и строит `published/timeline.jsonl` из действующих фактов. Проекция сохраняет ID коррекции и `corrects_event_id`; оригинал остаётся в локальном журнале и может отсутствовать в проекции. Для чтения проекции используется `read_timeline(..., projection=True)`, для проверки — `validate_timeline(..., projection=True)`; отсутствие цели коррекции разрешено только в этом режиме. `inferred` в проекции запрещён.

`artifacts.timeline="timeline.jsonl"` регистрирует файл в manifest. Текущий снимок/diff в evidence заменяются на `current.json`/`changes.json`; прочие относительные ссылки получают пометку «Локальный источник; недоступен облачному читателю». Исходные заметки и скриншоты не копируются. Текст очищается штатным `scrub`, весь пакет проверяется `check_privacy`. `brief.md` воспроизводится из опубликованных JSON и содержит хронику с источниками, отметкой исправления и ссылкой на `timeline.jsonl`.

Повтор публикации неизменного содержимого сохраняет байты артефактов и `generated_at`, включая прежнее `locations.created_at`. Изменение фактической проекции при том же `snapshot_id` меняет `generated_at` и SHA-256 фактических байтов `timeline.jsonl`. Хеш возвращается CLI как `publish.timeline_sha256` для pipeline либо `timeline_sha256` для publish и вычисляется отдельно от manifest. Добавление только гипотезы не меняет фактическую публикацию. Хеш самого manifest и новые поля его схемы не вводятся.

Статический `world_reference` и пространственные статусы `in_location`/`near_location` не создают событий `World States` о захвате, разрушении или зачистке. События вводятся отдельно с источником и не изменяют справочник мира.

## Справочник мира: `kenshi-world-reference/1`

Проектный контракт `contracts/world-reference.schema.json` (JSON Schema Draft 2020-12) фиксирует статическую географию, радиусы застройки и карту регионов Kenshi, извлечённые read-only из установленной игры и активных модов:
- Формат: `format: "kenshi-world-reference/1"`.
- Метаданные: `world_ref_id` (`sha256-...`), `game_version`, `mods` (упорядоченный список активных модулей), `source_hashes` (хеши первичных файлов относительно каталога игры/модов без локальных путей пользователя), `created_at` (UTC ISO-8601), `meta` (счётчики локаций, зданий и отфильтрованных маркеров).
- Локации (`locations`): 261 подтверждённая географическая точка (`type in {1..7, 9}`). Технические маркеры `TOWN_NEST_MARKER` (`type == 8`) исключены. Каждая локация содержит устойчивый `instance_id`, `template_sid`, `name_en`, `name_ru` (null при отсутствии перевода), `kind` (`outpost`, `town`, `village`, `ruins`, `slave_camp`, `military`, `prison`, `poi`), точные координаты `x, y, z` в `[-147456, 147456)`, `zone` на сетке 64×64 (`"col.row"`), `region` (из `BIOME_GROUP`, null для зон 'NONE'), `coordinate_source` (`game_leveldata`), `radius_source` (`game_buildings` для 48 локаций с подтверждёнными зданиями, `template_parameter` для остальных 213), детерминированный `confirmed_radius` с гарантией попарного непересечения `r_i + r_j <= 0.95 * distance(i, j)`, статическую привязку зданий `static_buildings` (`[{"zone": "...", "building_id": ...}]`).
- Регионы (`regions`): палитра активных `BIOME_GROUP` (строго `type_id == 95`, `sid`, `name_en`, `name_ru`, RGB `index`).
- Карта регионов (`regions_map`): детерминированная RLE-сетка индексов 256×256 (сумма длин = 65536) с пикселем 1152 ед., bottom-up ориентацией TGA (`desc=0x00`) и пометкой приграничных пикселей `border`.
- Неизменяемые артефакты сохраняются в `data/world/<world_ref_id>.json`.

## Пространственное разрешение локаций: `kenshi-locations/1`

Проектный контракт `contracts/locations.schema.json` (JSON Schema Draft 2020-12) связывает персонажей и постройки с детерминированным справочником мира `kenshi-world-reference/1`:
- Формат: `format: "kenshi-locations/1"`.
- Метаданные: `snapshot_id`, `world_ref_id`, `created_at`, `meta` (счётчики персонажей и построек по статусам).
- Строгий разбор 3D-координат: `[x, y, z]` или `{"x": ..., "z": ...}` строго в полуинтервале `[-147456, 147456)`. Некорректные/усечённые/NaN/Inf значения приводят к `resolution_status = "unknown"`.
- Разрешение персонажей и животных строго по устойчивому `characters[].id` (без склеивания одноимённых).
- Разрешение построек `property.buildings` по составному ключу `(zone, id)`:
  - Дубликат составного ключа или пустой `id` блокирует выпуск как критическая ошибка идентичности.
  - При отсутствии `zone` постройка получает `building_key = "unknown:<id>"`, вычисляет клетку по координатам с предупреждением и исключается из статического поиска.
  - Привязка к `instance_id`: (а) статический индекс `world_reference.building_index` (`(zone, building_id) -> instance_id`); (б) при непустом `building.town` — однозначное совместное совпадение имени (`name_ru` или `name_en`) и попадание `(x, z)` в `confirmed_radius` локации. Пользовательские форпосты и неоднозначные имена не получают чужой `instance_id`.
- 4 статуса `resolution_status`:
  - `in_location`: внутри подтверждённого кругового `confirmed_radius` застройки (`radius_source = "game_buildings"` для персонажей, либо правила (а)/(б)/(в) для построек). Персонажам в локациях с `radius_source = "template_parameter"` статус `in_location` не присваивается (дается `near_location`).
  - `near_location`: `location: null`, ближайшие известные локации в радиусе окрестности (с указанием 2D евклидова расстояния и `instance_id`), отсортированные по `(distance, instance_id)`.
  - `in_region`: `location: null`, подтверждённый растром регион (с пометкой границы 1152 ед. `border: true`).
  - `unknown`: `location: null`, `region: null` с явной причиной.
  - Запрещён вывод фактов посещения, исследования или зачистки руин из координат.
- Пространственные группы `spatial_groups`: детерминированная кластеризация разделённых участников с сортировкой по `(name, id)`.
- Перемещение `movement`: прямолинейное 2D евклидово смещение в плоскости `(X, Z)` строго при `diff.valid == true`. При невалидном сравнении или отсутствии baseline — `movement.valid = false`.

## Дипломатия и состояние мира: геополитические структуры FCS

Извлечение данных геополитики и состояния мира из `quick.save` выполняется строго read-only без вымышленных значений:
- Дипломатия (`diplomacy`):
  - Отношения фракций мира к игроку сопоставляются по каноническому `gamedata stringID` из записей типа 37.
  - Значение `relation` — точное числовое значение `float` в диапазоне `[-100.0, 100.0]`.
  - При отсутствии записи связи между фракцией и игроком подстановка нулей запрещена: `relation = null`, `standing = "unknown"`.
  - Проектная классификация `standing` по порогам отношений:
    - `"ally"`: `relation >= 50.0` (союзнический статус).
    - `"friendly"`: `0.0 < relation < 50.0` (положительные отношения).
    - `"neutral"`: `relation == 0.0` (подтверждённый нейтралитет).
    - `"unfriendly"`: `-30.0 < relation < 0.0` (напряжённость).
    - `"hostile"`: `relation <= -30.0` (враждебность, автоматическая агрессия).
    - `"unknown"`: `relation is null` (связь не определена в сохранении).
- Состояние уникальных NPC (`world_state.unique_npcs`):
  - Читается из записи типа 56 (`usedUniques`).
  - Поле `player` читается строго из секции `bool` (`usedUniquesPlayer*`).
  - Числовой код `state_code` сохраняется без домысливания: 0, 1, 2.
  - Подтверждённое строковое состояние `state = "dead_or_captured"` присваивается только проверенному коду `state_code == 2` (соответствующему триггеру гибели/захвата в реакциях мира FCS). Для кодов 0 и 1 `state = null`.
  - Сводка `summary` ведётся по числовым кодам: `state_0_count`, `state_1_count`, `state_2_count`.
- Переопределения городов (`world_state.town_overrides`):
  - Читаются из записей типа 94 (`Town state <имя>`) при наличии ключа `replacementTown`.
  - Фиксируются `replacement_sid`, имя шаблона переопределения и текущая фракция поселения.

## Расширенные характеристики персонажей

Извлечение данных персонажей из записей типа 30, 36, 67 (`platoon/*.platoon`):
- Очередь назначенных работ (`jobs`):
  - Декодируется из записи типа 67 (`JobsState`) через перечисление `taskType` (`tools/task_types.py`, 289 задач из канонического `fcs_enums.def`).
  - Постоянные работы (`primary`): упорядоченный список задач (`pjob0`, `pjob1`, ...) с полями `index`, `task_code`, `task_name` (например `JOB_MEDIC`, `JOB_REPAIR_ROBOT`, `OPERATE_MACHINERY`, `OPERATE_STORAGE`, `JOB_BUILDER`) и 5-компонентным `target_handle` (`TYPE, C, S, I, CS`).
  - Правило очистки `clean_handle`: безадресные задачи (глобальные работы вроде `JOB_MEDIC`, `JOB_REPAIR_ROBOT` с `TYPE == 11` или нулевыми координатами `C, S, I, CS`) очищаются до `target_handle = null`.
  - Временные работы (`temporary`): упорядоченный список задач `tjob` с полями `index`, `task_code`, `task_name`, `target_handle`.
  - Флаг активности работ: `enabled` (`bool | null`).
  - `raw`: изолированная копия исходных словарей записи (`int`, `string`, `bool`).
- Физическая переноска (`carrying`):
  - Извлекается из записи типа 36 (`CharacterState`).
  - `is_carrying`: булев флаг (берётся строго из булевой секции `st_bool.get("carrying", False)`).
  - `target_handle`: 5-компонентный handle переносимого персонажа (при `is_carrying == true`), иначе `null`.
  - `carried_by`: 5-компонентный handle несущего персонажа (при `is_carrying == false` и наличии валидного ненулевого handle с `carryingTYPE == 1`), иначе `null`.
  - `raw`: сырой словарь компонентов `carryingS`, `carryingI`, `carryingC`, `carryingCS`, `carryingTYPE`.
  - Ограничение: `target_handle` и `carried_by` являются сырыми 5-компонентными handle FCS движка и на текущем этапе напрямую не связываются с `id` персонажа.
- Награды за голову (`bounties`):
  - Награды за голову персонажа декодируются по массивам с числовыми суффиксами `bountyfac0..N`, `bountyexp0..N`, `crimes0..N`.
  - `has_bounty`: булев флаг наличия хотя бы одной активной награды (`amount > 0`).
  - `total_amount`: суммарный размер всех наград в катах (`int`).
  - `entries`: упорядоченный список записей по фракциям:
    - `index`: порядковый номер записи в массиве FCS.
    - `faction_sid`: `sid` фракции, объявившей награду (`bountyfac<idx>`).
    - `amount`: сумма награды в катах (`bountyexp<idx>`, целое число).
    - `crimes`: сырой числовой код преступления из сейва (`crimes<idx>`, целое число; семантика кодов на текущем этапе не подтверждена).
- Боевые режимы (`combat_modes`):
  - Булевы флаги боевого ИИ персонажа, читаемые непосредственно из булевой секции записи 36:
    - `taunt` (`taunt mode`), `passive` (`passive mode`), `ranged` (`ranged mode`), `defensive` (`defensive mode`), `chase` (`chase mode`), `stealth` (`stealth`), `non_combat` (`non combat mode`).
    - При отсутствии соответствующего ключа в сохранении значение возвращается как `null` (без фиктивной подстановки `false`).
    - Режим удержания позиции (`hold`) в булевой секции типа 36 Kenshi отсутствует и в публичный словарь не включается.

## Валидация проектных схем

`tools.validation` использует `jsonschema.Draft202012Validator.check_schema` и `FormatChecker`, включая проверку `date-time`. Зависимость нужна для настоящей семантики Draft 2020-12, в частности условной обязательности коррекции; ручной smoke-check её не заменяет. `python -m tools.campaign check-schemas` проверяет все примеры. Unit-тесты отдельно отвергают неизвестные свойства, неправильные типы/даты, абсолютные пути/выход через `../` и коррекции без ссылки. Старые формы примеров остаются допустимыми.
