# Контракт данных и совместимость

## Обязательное исходное обследование

Нативный конвейер `extract --source-kind save` формирует `kenshi-session/11`. Импорт готовых выгрузок `extract --source-kind export` сохраняет исходный формат: `kenshi-session/10` или `kenshi-session/11`. Внутренний `session_export.build_snapshot` предоставляет совместимое представление v10; `converter_worker` дополняет его полями `save_reader` до v11. Внешний конвертер не запускается. Формат diff остаётся `kenshi-session-diff/5`. Контракт снимка сессии формализован в `contracts/session.schema.json` (JSON Schema Draft 2020-12).

`current.json` сохраняет `format` (`kenshi-session/10` либо `kenshi-session/11`), игровые поля и доступную точность без дополнительного округления. Нормализатор проверяет обязательные объекты `save`, `world`, `meta`, списки `characters`, `squads`, `warnings`; неизвестные игровые поля сохраняет. Схема `contracts/session.schema.json` валидирует как сырые (до нормализации, с метаданными пути и файла), так и нормализованные снимки (где `save` очищен до `{}`).

## Расширения `kenshi-session/11`

v11 сохраняет структуры характеристик, здоровья, экипировки, инвентаря, исследований и снабжения v10. Новые данные добавляются к тем же записям персонажей, без сопоставления по имени и без замены запасного ID `h:*`. При чтении отрядов принадлежность игроку определяется состоянием персонажа, включая участников в активном отряде другой фракции.

| Поле | Содержимое и ограничения |
|---|---|
| `diplomacy` | `player_faction_sid`, `player_faction_name`, `relations`, `summary`. Отношения идентифицируются по `faction_sid`; сохраняются сырые `relation`, `trust`, `trust_neg`. Отсутствующая связь даёт `relation=null`, а не нейтральное отношение. Классов отношений (союзник, враг и т. п.) нет. |
| `world_state` | `unique_npcs`, `town_overrides`, `summary`. Для NPC сохраняются `sid`, индекс записи, имена, `state_code`, признак игрока `player`, handle и носитель пленника `captured_by` (если пленник несётся отрядом игрока). Значения `state_code` — факт игры, описаны в разделе «Дипломатия и состояние мира». Города сохраняют `replacement_sid`, текущие сведения о фракциях и handle; причина смены состояния не выводится. |
| `characters[].jobs` | `enabled`, постоянная очередь `primary`, временная `temporary` и `raw`. Запись работы содержит исходный индекс, `task_code`, `task_name`, `target_handle` и обогащенное читаемое имя цели `target_name` (название станка с родительским зданием, хранилища или имя союзника). Порядок соответствует числовым индексам сохранения; отсутствие записи работ даёт `enabled=null` и пустые очереди. |
| `characters[].carrying` | `is_carrying`, `target_handle`, `target_name`, `carried_by`, `carried_by_name`, `raw`. При переноске handle и target_name относятся к переносимому объекту/персонажу; для переносимого персонажа carried_by/carried_by_name указывают носителя. Handle не подменяется, а дополняется разрешенным именем. |
| `characters[].bounties` | `has_bounty`, `total_amount`, `entries`. Записи сохраняют индекс, `faction_sid`, `amount`, `crimes`; сумма строится из извлечённых сумм наград. |
| `characters[].combat_modes` | `taunt`, `passive`, `ranged`, `defensive`, `chase`, `stealth`, `non_combat`: `true`, `false` либо `null`, если флаг не получен. |
| `characters[].items` | Поштучный учёт предметов персонажа без агрегации (Тип 42 сохранения Kenshi): `instance_id` (порядковый ID экземпляра из контейнера), `item_sid`, `base_data_sid`, `container`, `quality`, `level`, `quantity`, `charges`, `wear`, `dam`, `stun`, `material_sid`, `color_sid`, `company_sid`, `inventory_xy`, `item_function`, `unique`, `owned_by`. Сохраняет индивидуальные параметры каждого экземпляра (включая запасные протезы, Мейто и износ). |
| `research` | Исследования игрока (запись 21). Включает `completed`, `in_progress`, `queue`, `paid`, `level_upgrades_completed`, вычисленный эффективный технологический уровень `tech_level` (P1 #8, базовый 1, максимум по завершенным апгрейдам) и список изученных чертежей `blueprints_completed`. |
| `property.buildings[]` и вложенный `interior[]` | Производственные поля: `power_on`, `gets_battery`, `battery_charge`, `is_paused`, `is_repeat`, `production_progress`, `consumption`, `craft_queue`, `craft_partial_items`, `construction_deposited`, `broken`, `resource_mult`, `mining_resource_level`, `usage_nodes`; также сведения о замках, боезапасе и исходных предметах `storage_items`. Сохраняются прежние `storage`, имена, шаблоны и иерархия. Сопоставление выполняется рекурсивно по паре `(zone, id)` с наследованием зоны родительского здания для интерьера; складской diff (`_diff_base_storage`) учитывает как агрегированные `storage`, так и поштучные `storage_items` во всех интерьерных контейнерах. Сводный складской баланс по базам и поселениям агрегируется в `property.storage_by_location` (P1 #11). |

Оценочные поля прежних версий конвертера (класс отношения фракции, строковые интерпретации состояния NPC, расчётные показатели физики и боя) не формируются. В ранее извлечённых снимках они могут присутствовать: схема их допускает, чтение и diff их не используют.

Handle — JSON-массив `[TYPE, C, S, I, CS]` с возможными `null` в отдельных компонентах либо `null` целиком. Для ключей внутренних словарей используется tuple; в выходных данных остаётся list. Безадресные handles работ и переноски (`TYPE=11` либо нулевые компоненты адреса) нормализуются в `null`.

В `provenance.source_format` и `manifest.source_format` записывается фактический `current.format`. Поддержка v10 не означает наличия новых категорий: отсутствующие или `null` разделы не трактуются как пустые подтверждённые данные. Diff новых категорий выполняется для пары v11 с доступными разделами; ограничения записываются в `not_compared`. Изменение отношения с неизвестным исходным значением не имеет числового `delta`.

`brief.md` отображает доступную дипломатию (список «фракция: значение relation»), состояние мира и расширенные категории diff. Полный состав отряда, работы, боевые режимы, характеристики и экипировка публикуются в плоской таблице `tables/squad.csv` и связанных витринах `tables/` (раздел «Табличные выгрузки»). Состав `kenshi-publication/2` указан ниже; монолитный текстовый `squad.md` снят с публикации для экономии контекста моделей; отдельный артефакт `diplomacy.md` в bundle не входит.

## Неизменяемый снимок: `kenshi-snapshot/2`

Один каталог `data/snapshots/<snapshot_id>/` содержит `current.json` и `provenance.json`. Метаданные происхождения имеют формат `kenshi-snapshot/2` (`kenshi-snapshot/1` поддерживается при чтении старых снимков); оба файла записываются через staging одного тома до регистрации каталога. Существующий каталог допускает только побайтовое совпадение обоих файлов. Неполный каталог или расхождение вызывает отказ, без перезаписи.

Канонический JSON: UTF-8 без BOM, ключи отсортированы, разделители `,` и `:`, один завершающий LF; `NaN`, бесконечности и повтор ключа запрещены. Персонажи сортируются по ID, отряды по `squad_id`, предупреждения сортируются с устранением точных повторов. Порядок массивов игровых данных без объявленной семантики множества сохраняется.

`source_sha256` для `export` — SHA-256 исходных байтов JSON до очистки. Для `save` — SHA-256 канонического отсортированного списка `[relative_path, sha256]` всех файлов каталога, включая не использованные парсером. Состав и хеши сравниваются до/после всего извлечения. Ссылки/junctions внутри сейва не поддерживаются и вызывают отказ. Сохранённый `source_files` позволяет проверить перечень; абсолютный путь источника не сохраняется.

`snapshot_id` имеет вид `sha256-<64 hex>`: хеш канонического объекта с `source_kind`, `source_sha256`, эффективным `faction_sid`, `converter_sha256`, `mods_sha256`, `transform_sha256`. Кампания, родитель и другие внешние значения в идентичность не входят: одинаковый источник при одинаковых параметрах разбора даёт один `snapshot_id`. `provenance.json` имеет формат `kenshi-snapshot/2` и содержит только идентичность, отпечатки разбора и данные источника; `kenshi-snapshot/1` (с `campaign_id`, `branch_id`, `parent_snapshot_id`) читается для старых снимков. `snapshot_id` нигде не пересчитывается и используется как непрозрачная строка. Обоснование — [ADR одной линии кампании](adr/campaign-line.md). Отпечаток преобразования включает проектные `tools/*.py`; отпечаток нативного движка (`converter_sha256`) — отсортированные пары относительного пути и SHA-256 исходников из фиксированного списка `ENGINE_FILES` (`tools/*.py`). Внешний конвертер выведен из эксплуатации. Отпечаток модов включает порядок и SHA-256 реально прочитанных файлов данных и локализации, список и отсутствие модов. Метки времени кэша не являются версиями данных.

Для `export` конвертер не запускается: `converter=null`, версии исходного конвертера и байтов модов неизвестны. В `mods` сохраняются очищенные метаданные экспорта с `status="export_metadata_only"`; различающиеся исходные байты имеют разные source hash даже при одинаковых фактах. Извлечение не знает кампании и родителя: их назначает регистрация в индексе. `game_time` в provenance — объект `{day,time}` из `world`, допускающий null; он не берётся из файлового времени.

Удаляются `save.path`, файловые `save.name`, `save.kind`, `save.saved_at`, весь `changes`, а из `meta` рекурсивно — `exported_at`, `timings_ms`, `session_file`, `cache`, `cache_file`, `cache_path`. Файловое имя/тип и mtime исключены потому, что одинаковые байты сейва могут копироваться в другой каталог. Игровое время сохраняется в `world`.

Строки и вложенные метаданные очищаются от абсолютных Windows/UNC и пользовательских POSIX-путей, полей паролей/токенов/ключей, типовых строк авторизации и секретов в URL. Неизвестный произвольный текст невозможно классифицировать как секрет без правила; перед публикацией требуется проверка фактического пакета. Входной `changes.history` целиком исключён, он не является подтверждённым таймлайном.

Повтор непустого `characters[].id` всегда вызывает отказ, в том числе между отрядами. `ps:*` — предпочтительный ID; `h:*`, имя вместо ID или отсутствующий ID сохраняются с ограничением в `diagnostics.limitations`. Связывание участников по имени не выполняется. Отсутствующий ID не заменяется вымышленным.

Для `save` обязательны читаемый `quick.save` с записью мира типа 56, каталог `platoon/`, активные файлы отрядов игрока из реестра и полностью читаемые активные `.platoon`. Старые файлы вне реестра не определяют состав. Запись типа 56 содержит также параметры сложности кампании (`cod`, `gdm`, `ht` и др.) и тумблеры ИИ отряда (`share`, `heal`, `ditch` и др.), описанные в [документации настроек](kenshi-settings.md). Для `export` наличие бинарного сейва не требуется. Агрегатные расхождения `quick.save: members/squads` не заменяют фактический состав и сохраняются как предупреждения. Предупреждения по `player_towns`/`zone/`, исследованиям, неизвестным sid и модам не удаляются; `diagnostics.categories` отмечает `available`, `unavailable`, `incomplete` или `inconsistent`. Наличие данных не означает независимой сверки с UI.

## Реестр снимков: `kenshi-index/2`

Проектный контракт `contracts/index.schema.json` (JSON Schema Draft 2020-12) фиксирует реестр снимков и их связи в `data/index.json`:
- Формат: `format: "kenshi-index/2"`, `updated_at` (UTC ISO-8601).
- Головы кампаний (`campaigns`): `{campaign_id: {"head_snapshot_id": ...}}`. У каждой кампании из `snapshots` есть голова.
- Записи снимков (`snapshots`): отображение `snapshot_id -> record`: `snapshot_id`, `parent_snapshot_id` (или `null`), `campaign_id`, `game_time` (`{"day": ..., "time": ...}` или `null`), `world_ref_id`, `source_kind` (`save`/`export`), `source_sha256`, `registered_at` (UTC ISO-8601). Родитель — снимок той же кампании.
- Линия кампании: кампания ведётся одной линией. Родитель нового снимка — голова кампании, то есть последний зарегистрированный снимок этой кампании; регистрация делает снимок новой головой. Снимки того же исходного сейва (`source_sha256`) при выборе родителя пропускаются: повторный разбор сейва после обновления конвертера даёт новый `snapshot_id`, и его родителем становится ближайший предок с другим сейвом, а не прежний разбор того же сейва. Оператор родителя не задаёт. Повторная регистрация существующего снимка той же кампании не меняет ни запись, ни голову; `pipeline` сообщает `index.registration = "existing"` и `index.is_head`; для снимка, который не является головой, возвращает `pipeline_status = "skipped"` без публикации и доставки. Регистрация снимка в другой кампании отклоняется. Поскольку `snapshot_id` не зависит от кампании, сейв, уже зарегистрированный в одной кампании, не может начать другую: новая кампания начинается с нового сохранения.
- Цепочка снимка (`tools/index.py: campaign_chain`) — предки по `parent_snapshot_id` до корня или границы кампании без снимков, отменённых перезагрузкой. Её используют накопительный таймлайн, промежуточные дельты, первичная разметка скриншотов и отбор авторских событий.
- Перезагрузка — игровое время снимка меньше времени родителя. Предки с игровым временем больше времени более позднего снимка цепочки отменены и исключаются. Diff с родителем перезагрузки имеет `valid = false`, `reason = "game_time_regression"`; публикация не прерывается, только если других проблем сравнения нет (иначе — отказ, как для любого невалидного diff); переход через перезагрузку промежуточной дельты не даёт.
- Сравнимы только предок и потомок цепочки индекса. Иначе `diff.valid = false`, `reason = "not_in_chain"`; синхронно `locations.movement.valid = false`.
- Инварианты целостности: атомарная запись через staging-файл и `replace` на одном томе под файловой блокировкой; отсутствие циклов и сирот; уникальность `snapshot_id`.
- `index rebuild` восстанавливает записи из `data/snapshots/*/provenance.json`. Связи, кампании и `registered_at` берутся из существующего индекса, иначе из provenance `kenshi-snapshot/1`. Снимок `kenshi-snapshot/2` вне существующего индекса пропускается и перечисляется в `skipped_unindexed`.
- Миграция: `python -m tools.campaign index migrate` печатает план перехода `kenshi-index/1` -> `kenshi-index/2`, `--apply` выполняет его с резервной копией `index.json.v1-<UTC>.bak` и проверкой результата. Записи и связи сохраняются, ветки удаляются. Голова кампании — голова ветки, содержащей последний по `registered_at` снимок кампании. Запись без `campaign_id` отклоняется. Индекс `/1` остальными командами не читается: отказ с указанием на миграцию.

## Контракт bundle: `kenshi-publication/2`

Реализованный release bundle в `published/`:

```text
published/
  manifest.json
  extended/
    current.json        # очищенный полный срез; читать только выборочно
  changes.json
  changes.md
  brief.md
  locations.json
  world_reference.json
  location_registry.json
  unique_entities_registry.json
  timeline.jsonl
  tables/               # CSV и index.md, раздел «Табличные выгрузки»
    index.md, squad.csv, equipment.csv, inventory.csv, storage.csv, buildings.csv, research.csv,
    build_catalog.csv, biome_resources.csv, races.csv, item_prices.csv, trade_modifiers.csv,
    unique_npcs.csv, unique_entities.csv, town_overrides.csv, diplomacy.csv, world_reactions.csv, world_reaction_links.csv,
    unit_templates.csv, unit_template_gear.csv, squad_templates.csv, squad_members.csv,
    squad_spawns.csv, faction_relations.csv, faction_hostility.csv,
    skills_history.csv, campaign_history.csv, relations_history.csv
  screenshots/
    index.json
    index.md
    screenshot_*.jpg
  .gitkeep
```

`manifest.json` содержит: `format: "kenshi-publication/2"`, `generated_at` (UTC ISO-8601), `snapshot_id`, `campaign_id` (канонический `"hot-lon"` для релизной публикации), `source_kind` (`save`/`export`), `source_format`, `source_sha256` (хеш именно указанного source_kind), `artifacts` (пути относительно `published/`; `artifacts.tables` — `tables/index.md`, необязательный ключ), `validation` (`passed` или `failed`), а также `world_ref_id` (`sha256-...`), связывающий пакет с детерминированным справочником мира. При успешном выпуске `validation.status="passed"`; неуспешный bundle не публикуется как актуальный. `snapshot_id` однозначно связывает файлы; в `changes.json` должна быть явная пара `from`/`to` или `valid:false` с причиной.

Схема допускает необязательные `parent_snapshot_id` (родитель из индекса), `campaign_id`, `game_time` (`string | number | null`, игровое время) и `reload` (`from_snapshot`, `from_game_time` в виде `Day N HH:MM`) у снимка перезагрузки. Выпуски `kenshi-publication/1` содержали `branch_id` и `branch_switch`; читатели старых выпусков (`tools/cartography.py`, просмотрщик карты) принимают оба формата и поле ветки игнорируют. Определение принадлежности публикации ведётся строго по `campaign_id` (по умолчанию `"hot-lon"`); публикация в канонический `published/` с другим `campaign_id` блокируется с ошибкой `PublisherError`, а валидатор `validate_publication` сверяет `campaign_id` манифеста с записью в `data/index.json`. Относительные пути `artifacts.locations`, `artifacts.world_reference`, `artifacts.location_registry` (`"location_registry.json"`), `artifacts.unique_entities_registry` (`"unique_entities_registry.json"`) и `artifacts.screenshots` (`"screenshots/index.json"`) регистрируют соответствующие артефакты в пакете публикации. Ключи `artifacts.location_registry` и `artifacts.unique_entities_registry` могут отсутствовать у прежних выпусков. Неизвестные свойства manifest запрещены.

Публичные данные не должны содержать абсолютных путей пользователя из `save.path`. Не публиковать сырые сейвы, произвольные большие текстовые поля, секреты или неразобранные бинарные блоки. Скриншоты игры из каталога `_screens` публикуются конвейером автоматически за 7-дневное окно (`now - 7d`) без ручного отбора в `published/screenshots/`; исходный каталог является read-only. Имена персонажей и числовые игровые показатели допустимы; автоматическая валидация проверяет публикуемый пакет на локальные пути пользователя (`C:\Users\...`, `/home/...`) и секреты.

`brief.md` — краткая сводка с `snapshot_id`, днём игры, составом, деньгами, структурированными географическими группами отряда, ключевыми изменениями и ссылками на детальные JSON. Все значения ссылаются на соответствующие поля JSON; при отсутствии сведений выводится «не получено».
Монолитный `squad.md` снят с публикации; полный состав отряда по участникам (ID, раса, состояние здоровья, характеристики, местоположение со статусом и расстоянием, экипировка, работы, боевые режимы) публикуется в плоской таблице `tables/squad.csv` (и витринах `tables/equipment.csv`, `tables/inventory.csv`).

### Публикационная проекция `current`

Файл `extended/current.json` строится из снимка в `data/snapshots/` только при публикации (`tools/current_layers.py`); исходные снимки и расчёт разниц сохраняют все поля. Из проекции исключаются каждое поле `raw`, `hidden_stats_raw` и навыки в `skills_base` со значением строго `1.0`. Нормативное правило для потребителей: навык, отсутствующий в `skills_base`, имеет значение `1.0`; навыки `< 1.0` (штрафы, травмы) и `> 1.0` сохраняются. Признак кражи предмета `is_stolen: bool` (`raw.int.ownedbyTYPE == 1`) формируется при чтении сохранения до исключения `raw`; в снимках, извлечённых до его введения, поля нет, а `raw` из публикации исключён, поэтому признак кражи для них недоступен.

`artifacts.current` указывает на `extended/current.json` (обязательный ключ). Каталог `current/` (шарды и `current/index.json`) из публикации и доставки удалён: конвейер его не создаёт, `deliver-companion` удаляет его в `Kenshi-Compain`. Ключ `artifacts.current_index` устарел: он необязателен и допускается только в манифестах прежних выпусков (такие манифесты остаются валидными). Валидатор требует суммарного объёма `manifest.json`, `brief.md`, `changes.md` не более 140 000 символов (стартовый набор выгрузки). Полный `changes.json` в стартовый набор не входит: его объём растёт с промежутком игрового времени между сейвами (очереди задач, состояние частей тела, навыки всего состава).

Снимки, созданные до удаления аналитики, не переписываются: `standing`, `*_calculated` и `state_detail` в них сохраняются и при пересборке публикации попадают в `extended/current.json`; чтение и diff их терпят; актуальные выпуски (новые извлечения) этих полей не содержат.

### Накопительный таймлайн и перезагрузка

К событиям авторского журнала добавляются события, восстановленные детерминированно из дельт между последовательными снимками цепочки (`tools/chain_timeline.py`): вступление и уход бойцов, смена отряда, изменение протезов, изменение казны. Статус таких событий `observed` (факты вычислены по данным сохранений), `session_id` — `auto-chain`, `evidence` — `diff`. В `timeline.jsonl` попадает окно из последних 20 переходов цепочки снимка (снимки, отменённые перезагрузкой, и переход через перезагрузку не участвуют); полная цепочка остаётся в `data/`. Схема события допускает необязательное `game_time` (`Day N HH:MM`).

Для снимка перезагрузки в `manifest.json` записывается объект `reload`, а в таймлайн добавляется событие `kind: "reload"` со статусом `observed`.

### Предупреждения валидации и заголовки

`manifest.validation.warnings` (необязательный массив строк) переносит предупреждения, не блокирующие публикацию: пустой `timeline.jsonl` даёт `"artifact:timeline: empty"` при `validation.status == "passed"`. Утилита доставки выводит предупреждения в stderr. Заголовок `brief.md` строится по игровому времени (`# Краткая сводка: День 131, 15:06`) и не содержит хешей снимков.

## Контракт ленты скриншотов: `kenshi-screenshots-index/1`

Проектный контракт `contracts/screenshots-index.schema.json` (JSON Schema Draft 2020-12) фиксирует структуру реестра визуальной ленты скриншотов в `published/screenshots/index.json`:
- `format`: `"kenshi-screenshots-index/1"`.
- `generated_at`: метка времени генерации (UTC ISO-8601).
- `count`: количество опубликованных ключевых кадров окна 7 суток (целое число $\ge 0$).
- `window_days`: размер скользящего окна в сутках (целое число, по умолчанию 7).
- `window_start`: начало интервала выборки (UTC ISO-8601, `now - 7d`).
- `window_end`: конец интервала выборки (UTC ISO-8601).
- `screenshots[]`: упорядоченный список изображений в хронологическом порядке:
  - `order`: порядковый номер (1, 2, ...).
  - `filename`: имя файла (например, `screenshot_393-1a2b3c4d.jpg`).
  - `path`: относительный путь в пакете (`screenshots/screenshot_393-1a2b3c4d.jpg`); `sha256` и `size_bytes` относятся к опубликованному уменьшенному файлу.
  - `source_sha256` (необязательное): SHA-256 оригинала; `is_keyframe` (необязательное, boolean): признак ключевого кадра.
  - `modified_at`: файловое время изменения `mtime` в UTC ISO-8601.
  - `size_bytes`: размер файла в байтах.
  - `sha256`: контрольная сумма содержимого файла (SHA-256).
  - `url_raw`: прямой Raw-URL GitHub для программного скачивания чат-моделями (`https://raw.githubusercontent.com/...`).
  - `url_blob`: ссылка на просмотр страницы изображения в GitHub Web UI (`https://github.com/...`).

`new_frames` в `index.json` перечисляет файлы кадров дельты: кадры с `modified_at` позже `registered_at` ближайшего предка с другим `source_sha256`: повторный запуск на том же сейве дельту не обнуляет. Без такого предка список пуст. Кадры дельты занимают выпуск первыми; при дельте больше 30 кадров лишние сохраняются в локальном архиве.

`published/screenshots/index.md` публикуется всегда и содержит группы «А. Новые кадры текущего снимка» и «Б. Архивный хвост» (последние 12 кадров выпуска вне дельты). Таблица кадра: ID, файл, sha256 опубликованного уменьшенного файла (суффикс имени — хеш оригинала), `modified_at`, интервал между снимками, первичная разметка, raw-ссылка и относительный путь в публикации. Та же таблица группы А входит в секцию `## Скриншоты снимка` файла `brief.md`.

Первичная разметка собирается из расположения групп по ближайшему снимку, значимых изменений дельты интервала и машинного OCR интерфейса (`OCR: День N, ЧЧ:ММ, выбранный персонаж, задачи`); кадры дельты вне выпуска берут OCR из локального индекса. Это ориентиры, а не подтверждённые события; день и время OCR показывают экран кадра и могут отличаться от `game_time` сейва. Активный отряд конвертер не извлекает.
- Исходный каталог игры `<KENSHI_DIR>/_screens` (или `KENSHI_SCREENS_DIR`) строго read-only.
- Скользящее 7-дневное окно: изображения старше 7 суток исключаются из актуальной публикации и удаляются из рабочего дерева Git; пограничное время ровно 7 суток включается. Из кадров окна публикуются 20–30 ключевых, уменьшенных до 1600 px по длинной стороне; полный уменьшенный набор хранится в `data/screenshots_archive/` вне git.
- Защита от поврежденных файлов: пустые (0 байт) файлы, файлы с невалидными сигнатурами (magic bytes) и файлы, модифицируемые игрой во время чтения, отбрасываются.
- Идемпотентность: повторный запуск без изменений состава изображений сохраняет метки времени и не порождает диффов.

## Контракт технического экстракта скриншотов: `kenshi-screenshot-annotation/1`

Ключи `screenshot_annotations` и `screenshot_feed` в `manifest.json` необязательны: при пустом OCR во всех кадрах аннотации и лента не публикуются, `index.json` публикуется всегда.

Проектный контракт `contracts/screenshot-annotations.schema.json` (JSON Schema Draft 2020-12) фиксирует структуру машиночитаемого технического экстракта в `published/screenshots/annotations.jsonl` (один JSON-объект на строку) для контекстного поиска игровым компаньоном:
- `format`: `"kenshi-screenshot-annotation/1"`.
- `sha256`: контрольная сумма изображения (SHA-256, regex `^[0-9a-f]{64}$`).
- `filename`: имя файла скриншота.
- `order`: порядковый номер кадра в скользящем окне.
- `modified_at`: время изменения файла (UTC ISO-8601).
- `meta`:
  - `dhash`: 16-символьный шестнадцатеричный перцептивный разностный хэш кадра (`string` или `null`).
  - `scene_group_id`: устойчивый ID технической серии похожих кадров (`seq_XXX`).
  - `is_exact_duplicate`: флаг точного дубликата по содержимому SHA-256 (bool).
  - `duplicate_of`: SHA-256 оригинального кадра при дублировании (string или null).
- `ocr`:
  - `game_day`: игровой день из UI (int или null).
  - `game_time`: игровое время из UI ("HH:MM" или null).
  - `location`: название зоны/города из интерфейса (string или null).
  - `characters[]`: список имен персонажей и NPC, распознанных в UI.
  - `dialogues[]`: список реплик в speech bubbles (`speaker`, `text`, `confidence`).
  - `notifications[]`: системные сообщения и уведомления интерфейса.
  - `items_or_tasks[]`: активные действия, работы или предметы из интерфейса.
- `provenance`:
  - `source`: источник происхождения экстракта (`"gemini-3.8-flash"`, `"ocr"`, `"metadata"`, `"cache"`); `"ocr"` — машинный Windows OCR (`docs/screenshots.md`).
  - `confidence`: степень уверенности (число от 0.0 до 1.0) или `null`, если источник её не отдаёт.
  - `extracted_at`: время формирования экстракта (UTC ISO-8601).

Инварианты технической экстракции:
1. **Только распознанные поля**: контракт описывает распознанный текст; блоков описания сцены (`visual`, `scene_type`, `summary`, `actions`) в нём нет. Наблюдения модели хранятся отдельно от этих полей.
2. **Сохранение неопределенности**: при отсутствии распознавания или текста в интерфейсе поля остаются строгими `null` (или пустыми массивами `[]`); запрещена подстановка фиктивных или дефолтных значений.
3. **Разделение ответственности**: интерпретация происходящего на скриншотах принадлежит LLM-компаньону, работающему с оригинальными кадрами.

Техническая хронологическая лента `published/screenshots/feed.md` строится на базе экстракта и группирует кадры в связные серии со ссылками на опубликованные кадры в GitHub.

## Совместимый diff: `kenshi-session-diff/5`

Сравнение двух неизменяемых снимков сохраняет совместимость с форматом `kenshi-session-diff/5` со следующими обязательными расширениями:
- Устойчивый `id` персонажа сохраняется во всех элементах изменений: `skills`, `equipment`, `prosthetics`, `inventory`, `health`, `roster.squad_changed`, `roster.status_changed`.
- Сортировка участников ведётся по строгому ключу `(name, id)` с детерминированным порядком пустых имён.
- `transfers` агрегируется по `(sid, char_id)`: имена участников служат метками, при совпадении имён к метке добавляется `[id]`, исключая потерю или склеивание передач.
- Запрещено склеивание разных `ps:*` по имени; смена устойчивого ID означает разные сущности (`joined`/`left`), а не `id_changed`.
- Baseline и Non-baseline режимы: при отсутствии предыдущего снимка `from: null`, `valid: false`, явный `reason` и список `problems`.
- Неотслеживаемые и неполные категории (`research`, `property`, `position`) выносятся в `not_compared` с указанием причины, исключая ложные нули изменений.
- Детерминированный результат сохраняется в `data/diffs/<diff_id>.json`.

## Идентичность и порядок

- Prefer ID из игры/экспортёра; имя — только метка отображения. Повторяющиеся имена допускаются.
- Контрольный снимок идентифицируется хешем источника и параметрами разбора; кампания и родитель — атрибуты индекса.
- Проверить значение исходных `from/to`: файловое имя или timestamp не являются гарантией логического родительства.
- Diff по персонажам сравнивает ID и категории с одинаковой семантикой. Отсутствующие категории и невалидные пары получают отдельный статус.
- Округление значений применяется только для представления; сравнение ведётся на доступной исходной точности.
- Для idempotency сериализовать JSON детерминированно; временную метку сборки разрешено обновлять только при реальной публикации новой версии, не на каждом dry-run.

## Подтверждённые игровые события

Формат `kenshi-event/1` описан в `contracts/timeline-event.schema.json`. Обязательные поля: `event_id`, `format`, `session_id`, `recorded_at`, `kind`, `status`, `summary`, `evidence`. `game_day` и `snapshot_id` необязательны. `snapshot_id` при импорте должен существовать в индексе и быть связан с указанной сессией.

- `observed`: непосредственно наблюдаемое состояние со ссылкой на известный снимок или валидный diff. Оно не доказывает причину изменения.
- `confirmed`: явная запись пользователя (`user_note`) или проверенный скриншот (`screenshot`). Указание этого статуса — действие автора; импорт не интерпретирует текст и не подтверждает его истинность автоматически.
- `inferred`: гипотеза. Хранится в журнале, исключается из опубликованной фактической проекции. При отдельном рендере исходного журнала показывается только под заголовком «Неподтверждённые гипотезы (inferred)».

Источники задаются безопасными относительными POSIX-путями внутри корня кампании. Для `snapshot` допустим также известный ID; он разрешается в `data/snapshots/<id>/current.json`. `diff` ссылается на `data/diffs/<id>.json` с `valid=true` и известными `from`/`to`. Подтверждённая запись с недоступным источником отклоняется. Содержимое скриншота автоматически не распознаётся. Абсолютные пути, `..`, Windows-устройства, альтернативные потоки и выход через junction/symlink запрещены.

`tools.timeline.import_events` проверяет весь пакет под единой блокировкой writer (`msvcrt` в Windows). Запись выполняется заменой временного файла на том же томе после `flush`/`fsync`; прежние байты остаются точным префиксом. Повтор идентичного события — no-op; тот же ID с иным содержимым — `ValueError: Конфликт event_id`. Ошибка проверки или записи не меняет журнал. Повреждённые/пустые строки, повторные ID и незавершённая последняя строка блокируют импорт и публикацию. Восстановление выполняет владелец из проверенной копии; автоматическое отбрасывание строк запрещено. Файл блокировки остаётся на диске, занятость определяется ОС.

Коррекция — отдельное событие `kind="correction"` с обязательным `corrects_event_id`, собственными ID, статусом и источником. Ссылка должна существовать в объединённом журнале; самоссылки, циклы и несколько прямых коррекций одного события запрещены. Повторное уточнение ссылается на предыдущую коррекцию. Исходные записи сохраняются. `resolve_timeline` выбирает последнее `observed`/`confirmed` в каждой цепочке; `inferred`-коррекция не отменяет доказанный факт. Подтверждённая коррекция гипотезы становится действующим фактом. Порядок вывода — `game_day`, затем `event_id`; неизвестный день идёт последним. `recorded_at` фиксирует время записи, а не игровую последовательность.

### Авторские сессии

Команда `timeline session` создаёт `sessions/<session_id>/session.json` с полями `session_id`, `snapshot_ids` и `notes.md` по шаблону `templates/session-notes.md` либо из переданного Markdown. Привязка сессии неизменяема и может включать несколько снимков. Повтор создания той же привязки не переписывает заметки. Планы и результаты в заметках редактируются автором; текст заметок сам по себе не создаёт событий. `session_id` отличается от всех связанных `snapshot_id`.

`filter_events_by_chain(events, snapshot_id, index_data, sessions=None)` отбирает события цепочки выбранного снимка, даже если голова кампании уже продвинулась дальше. События снимков, отменённых перезагрузкой, исключаются. Событие без `snapshot_id` включается только когда все явные снимки его сессии входят в цепочку. Без привязки такое событие не публикуется. Коррекции, цель которых не попала в цепочку, также исключаются. Индекс не расширяется полями сессий.

### Читаемые зеркала

`changes.md` (`artifacts.changes_md`) — структурированная сводка `changes.json` и раздел «Промежуточные снимки» с событиями предыдущих переходов окна цепочки. `brief.md` начинается с шапки манифеста: `snapshot_id`, `previous_snapshot_id`, `campaign_id`, `reload` (у снимка перезагрузки), `game_time`, `generated_at`. `artifacts.screenshot_index_md` указывает на `screenshots/index.md`.

### Публикация таймлайна

Publisher читает журнал целиком, проверяет его, отбирает цепочку снимка и строит `published/timeline.jsonl` из действующих фактов. Проекция сохраняет ID коррекции и `corrects_event_id`; оригинал остаётся в локальном журнале и может отсутствовать в проекции. Для чтения проекции используется `read_timeline(..., projection=True)`, для проверки — `validate_timeline(..., projection=True)`; отсутствие цели коррекции разрешено только в этом режиме. `inferred` в проекции запрещён.

`artifacts.timeline="timeline.jsonl"` регистрирует файл в manifest. Текущий снимок/diff в evidence заменяются на `current.json`/`changes.json`, остальные дельты — на раздел `changes.md#snapshot-<12 символов id>`; валидация отклоняет `data/diffs/` в `brief.md`, `changes.md` и `timeline.jsonl`; прочие относительные ссылки получают пометку «Локальный источник; недоступен облачному читателю». Публикация таймлайна не копирует локальные заметки и изображения, указанные в `evidence`; независимо от неё сборщик скриншотов публикует изображения из `_screens` за последние 7 суток в `published/screenshots/`. Текст очищается штатным `scrub`, весь пакет проверяется `check_privacy`. `brief.md` воспроизводится из опубликованных JSON и содержит хронику с источниками, отметкой исправления и ссылкой на `timeline.jsonl`.

Повтор публикации неизменного содержимого сохраняет байты артефактов, `generated_at` и прежнее `locations.created_at`. Сдвиг на одну микросекунду применяется только при изменении содержимого, если исходная метка сборки совпадает с меткой предыдущего выпуска. `generated_at` показывает время сборки. Выпуски различают по `snapshot_id` и хешам артефактов, а компаньон сверяет свежесть по `snapshot_id` и `game_time`. SHA-256 фактических байтов `timeline.jsonl` возвращается CLI как `publish.timeline_sha256` для pipeline либо `timeline_sha256` для publish. Добавление только гипотезы не меняет фактическую публикацию. Хеш самого manifest и новые поля его схемы не вводятся.

Статический `world_reference` и пространственные статусы `in_location`/`near_location` не создают событий `World States` о захвате, разрушении или зачистке. События вводятся отдельно с источником и не изменяют справочник мира.

## Справочник мира: `kenshi-world-reference/1`

Проектный контракт `contracts/world-reference.schema.json` (JSON Schema Draft 2020-12) фиксирует статическую географию, радиусы застройки и карту регионов Kenshi, извлечённые read-only из установленной игры и активных модов:
- Формат: `format: "kenshi-world-reference/1"`.
- Метаданные: `world_ref_id` (`sha256-...`), `game_version`, `mods` (упорядоченный список активных модулей), `source_hashes` (хеши первичных файлов относительно каталога игры/модов без локальных путей пользователя), `created_at` (UTC ISO-8601), `meta` (счётчики локаций, зданий и отфильтрованных маркеров).
- Локации (`locations`): 261 подтверждённая географическая точка (`type in {1..7, 9}`). Технические маркеры `TOWN_NEST_MARKER` (`type == 8`) исключены. Каждая локация содержит устойчивый `instance_id`, `template_sid`, `name_en`, `name_ru` (null при отсутствии перевода), `kind` (`outpost`, `town`, `village`, `ruins`, `slave_camp`, `military`, `prison`, `poi`), точные координаты `x, y, z` в `[-147456, 147456)`, `zone` на сетке 64×64 (`"col.row"`), `region` (из `BIOME_GROUP`, null для зон 'NONE'), `coordinate_source` (`game_leveldata`), `radius_source` (`game_buildings` для 48 локаций с подтверждёнными зданиями, `template_parameter` для остальных 213), детерминированный `confirmed_radius` с гарантией попарного непересечения `r_i + r_j <= 0.95 * distance(i, j)`, статическую привязку зданий `static_buildings` (`[{"zone": "...", "building_id": ...}]`).
- Регионы (`regions`): палитра активных `BIOME_GROUP` (строго `type_id == 95`, `sid`, `name_en`, `name_ru`, RGB `index`).
- Карта регионов (`regions_map`): детерминированная RLE-сетка индексов 256×256 (сумма длин = 65536) с пикселем 1152 ед., bottom-up ориентацией TGA (`desc=0x00`) и пометкой приграничных пикселей `border`.
- Публикационная проекция: в `published/world_reference.json` поля `regions_map` и `source_hashes` отсутствуют (около 207 тыс. символов вместо 650 тыс.), в схеме `contracts/world-reference.schema.json` они необязательны; валидатор проверяет сумму RLE-сегментов только при наличии `regions_map`. Полный справочник хранится в `data/world/` и используется локатором и проверкой геометрии картографии (`docs/cartography.md`).
- Неизменяемые артефакты сохраняются в `data/world/<world_ref_id>.json`.

## Пространственное разрешение локаций: `kenshi-locations/1`

Проектный контракт `contracts/locations.schema.json` (JSON Schema Draft 2020-12) связывает персонажей и постройки с детерминированным справочником мира `kenshi-world-reference/1`:
- Формат: `format: "kenshi-locations/1"`.
- Метаданные: `snapshot_id`, `world_ref_id`, `created_at`, `meta` (счётчики персонажей и построек по статусам).
- Строгий разбор 3D-координат: `[x, y, z]` или `{"x": ..., "z": ...}` строго в полуинтервале `[-147456, 147456)`. Некорректные/усечённые/NaN/Inf значения приводят к `resolution_status = "unknown"`.
- Разрешение персонажей и животных строго по устойчивому `characters[].id` (без склеивания одноимённых).
- Разрешение построек `property.buildings` по составному ключу `(zone, id)`:
  - Дубликат составного ключа или пустой `id` блокирует выпуск как критическая ошибка идентичности.
  - При отсутствии `zone` постройка получает `building_key = "unknown:<id>"`, вычисляет клетку по координатам с предупреждением и исключается из статического поиска.
  - Привязка к `instance_id`: (а) статический индекс `world_reference.building_index` (`(zone, building_id) -> instance_id`); (б) при непустом `building.town` — однозначное совместное совпадение имени (`name_ru` или `name_en`) и попадание `(x, z)` в `confirmed_radius` локации. Пользовательские форпосты и неоднозначные имена не получают чужой `instance_id`.
- 4 статуса `resolution_status`:
  - `in_location`: внутри подтверждённого кругового `confirmed_radius` застройки (`radius_source = "game_buildings"` для персонажей, либо правила (а)/(б)/(в) для построек). Персонажам в локациях с `radius_source = "template_parameter"` статус `in_location` не присваивается (дается `near_location`).
  - `near_location`: `location: null`, ближайшие известные локации в радиусе окрестности (с указанием 2D евклидова расстояния и `instance_id`), отсортированные по `(distance, instance_id)`.
  - `in_region`: `location: null`, подтверждённый растром регион (с пометкой границы 1152 ед. `border: true`).
  - `unknown`: `location: null`, `region: null` с явной причиной.
  - Пространственная привязка фиксирует положение в текущем снимке и не создаёт отметок в реестре локаций.
- Пространственные группы `spatial_groups`: детерминированная кластеризация разделённых участников с сортировкой по `(name, id)`.
- Перемещение `movement`: прямолинейное 2D евклидово смещение в плоскости `(X, Z)` строго при `diff.valid == true`. При невалидном сравнении или отсутствии baseline — `movement.valid = false`.

## Реестр локаций и ручные отметки

`publish` формирует `published/location_registry.json` по схеме [kenshi-location-registry/3](../contracts/location-registry.schema.json). Корневые `snapshot_id`, `campaign_id`, `game_time` и `world_ref_id` совпадают с манифестом. `locations` содержит по одной записи на каждый `instance_id` справочника. Статика копируется из справочника. `template_faction` появляется при однозначной ссылке шаблона `TOWN` на фракцию в проверенных исходных файлах мира. Поле описывает шаблонного владельца.

`discovered` и `discovered_source` отражают флаг `Town state.discovered` выбранного сейва: `true` — место открыто на игровой карте, `false` — не открыто. Сопоставление выполняется по `instance_id`. Если флаг недоступен, поля отсутствуют и место считается неизвестным. Новые снимки содержат исходный флаг в `world_state.town_discovery`, публичная проекция переносит его в реестр. `publish --discovery-save <каталог сейва>` восстанавливает флаг для старого снимка только при совпадении полного хеша каталога с `source_sha256` до и после чтения. Флаг `Town state.explored` не используется: игра ставит его при приближении камеры.

Ручной слой кампании `hot-lon` — `Campaign/Хроники Хот Лон/locations_progress.json` игрового репозитория по схеме [kenshi-location-progress/3](../contracts/location-progress.schema.json). Он содержит только отметки зачистки, подтверждённые при `[итог]`. В корне указаны `campaign_id`, `world_ref_id` и `locations`. Запись содержит `instance_id`, свидетельство `evidence` (ссылка на сессию `S-…`) и установленное `game_time` (`Day N HH:MM`), если оно известно. Ключ `instance_id` уникален. Отметка применяется к выпуску той же кампании, датированная отметка позже игрового времени выпуска исключается. Версии `kenshi-location-progress/1` и `/2`, в том числе из истории Git, читаются: отметкой зачистки становится запись `explored`, записи `visited` снимаются.

Перед коммитом `python -m tools.campaign check-location-progress --companion-dir <игровой клон> [--published-dir <выпуск>]` проверяет схему, справочник и дубли. Отметка, зафиксированная в истории Git по первым родителям, не удаляется. При смене `world_ref_id` совпавшие `instance_id` переносятся напрямую. Прежние несопоставленные отметки сохраняются без изменений и возвращаются в диагностике. Новые и изменённые отметки требуют действующего ID. Команда завершается кодом `1`, если ручной слой отсутствует или не проходит проверку.

`deliver-companion` проверяет ручной слой после подготовки игрового клона и до записи выпуска и добавляет применимые отметки в поле `cleared` записи реестра (`evidence`, `game_time`). Локальный реестр конвертера отметок не содержит. Размер реестра ограничен 150 000 символов. [Решение о реестре](adr/location-registry.md).

Отчёт доставки содержит `location_progress` (`ok`, `invalid`, `absent`) и `location_progress_reason` (`null` при `ok`). При отсутствующем или невалидном ручном слое доставляется реестр без отметок. Превышение лимита размера при наложении отметок даёт `invalid` и тот же результат. `status=failed` относится к сбою доставки выпуска `published/`.

## Реестр уникальных сущностей: kenshi-unique-entities-registry/2

`publish` формирует `published/unique_entities_registry.json` по схеме [kenshi-unique-entities-registry/2](../contracts/unique-entities-registry.schema.json) (с полной поддержкой обратной совместимости с версией `/1`). Модуль построения — `tools.unique_entities_registry` (`build_unique_entities_registry`). Назначение артефакта — единый детерминированный реестр уникальных NPC, боссов и оружия Мейто со статической привязкой к локациям игрового мира, динамическим состоянием из текущего снимка сохранения и подтверждёнными свидетельствами из активного таймлайна и ручного слоя прогресса.

### Корневые поля

- `format`: константа `"kenshi-unique-entities-registry/2"`.
- `campaign_id`: строковый идентификатор кампании (`string | null`, канонический `"hot-lon"`).
- `snapshot_id`: идентификатор публикуемого снимка (`sha256-...`).
- `world_ref_id`: идентификатор справочника мира (`sha256-...`), связывающий реестр со статическими данными мира.
- `game_time`: игровое время снимка (`string | number | null`, например `"Day 136 20:21"`).
- `generated_at`: дата и время генерации (UTC ISO-8601).
- `unique_npcs`: массив объектов уникальных NPC.
- `bosses`: массив объектов боссов и мировых лидеров.
- `meitou_weapons`: массив объектов базовых моделей оружия Мейто.

### Группа `unique_npcs`

Содержит всех уникальных персонажей Kenshi, определяемых по флагу `bool.unique` в FCS, записям `usedUniques` сохранения, базовым наградам или участию в реакциях мира:
- `npc_sid`: устойчивый `sid` шаблона персонажа (FCS `CHARACTER`, тип 1).
- `name_en`: каноническое английское имя персонажа из шаблона данных игры или индекса.
- `name_ru`: локализованное русское имя (`string | null`) из словарей перевода (`gamedata.po`) или модов.
- `category`: категория уникального NPC (`"recruit" | "boss" | "world_leader" | "significant_npc" | "unique_npc"`):
  - `recruit`: уникальные потенциальные рекруты (`NPC class == 9` либо размещение в барах `link_type == "bar_squad"`).
  - `world_leader`: лидеры мировых фракций (`NPC class == 5`).
  - `boss`: боссы с высокой базовой наградой (`bounty amount >= 10000`), либо боссы из специального каталога (`custom_catalog`), либо обладатели Мейто (`meitou_holder`).
  - `significant_npc`: значимые NPC с меньшей наградой (`bounty amount < 10000`) или уникальные NPC, участвующие исключительно в мировых реакциях/триггерах (`world_state`).
  - `unique_npc`: прочие уникальные персонажи мира.
- `locations`: список статических привязок к локациям мира по цепочке вложенности FCS-шаблонов (`CHARACTER` → `SQUAD` → `TOWN` → `INSTANCE`):
  - `instance_id`: устойчивый ID экземпляра локации из `world_reference.json` (пустая строка при отсутствии).
  - `template_sid`: `sid` шаблона поселения или города (FCS `TOWN`, тип 13).
  - `location_name_ru`: русское наименование локации (`string | null`).
  - `location_name_en`: английское наименование локации.
  - `region`: регион мира (`string | null`).
  - `link_type`: тип связи отряда с городом (`"resident"` — постоянные жители, `"bar_squad"` — посетители баров/рекруты, `"roaming"` — городские патрули, `"homeless"` — бездомные отряды).
  - `resolution`: точность пространственного разрешения локации (`"unique" | "ambiguous" | "unresolved"`):
    - `unique`: шаблон однозначно соответствует ровно одному экземпляру поселения в справочнике мира.
    - `ambiguous`: шаблону соответствует несколько экземпляров поселений в мире.
    - `unresolved`: экземпляр локации в справочнике мира не найден.
  - `source_chain`: цепочка шагов разрешения (`["CHARACTER:<sid>", "SQUAD:<sid>", "TOWN:<sid>", "INSTANCE:<id>"]`).
  - `cleared_evidence`: свидетельство зачистки конкретной локации (`{"location_instance_id": string, "cleared_at": string, "source": string}`) или `null`, обогащаемое при доставке в игровой репозиторий (`deliver-companion`, `apply_progress_to_unique_entities`) из ручного слоя `locations_progress.json`.
- `personal_evidence`: объект подтверждения персонального взаимодействия (`{"event_id": string, "day": int | null, "summary": string}`) или `null`, извлекаемый из активного таймлайна по маркеру `[npc_sid=...]`.
- `dynamic`: динамическое состояние персонажа в сохранении:
  - `state_code`: числовой код состояния из `world_state.unique_npcs` (`integer | null`): 0 — мёртв, 1 — жив и свободен, 2 — в плену (`null` — персонаж в сохранении не встречался).
  - `player_defeat_flag`: булев флаг победы игрока над персонажем (`usedUniquesPlayer*`).
  - `squad_status`: статус нахождения в отряде игрока (`"confirmed_in_squad" | "confirmed_not_in_squad" | "unresolved"`):
    - `confirmed_in_squad`: персонаж подтверждённо принят в отряд игрока (сопоставление строго по 5-компонентному `handle`).
    - `confirmed_not_in_squad`: персонаж имеет валидный `handle`, но в составе отрядов игрока отсутствует.
    - `unresolved`: `handle` отсутствует или не валиден.
  - `character_id`: постоянный идентификатор персонажа в отряде игрока (`ps:...` или `null`).
  - `handle`: строгий 5-компонентный кортеж `[TYPE, C, S, I, CS]` (целые числа, ненулевой массив) или `null`.
  - `captured_by`: имя или идентификатор пленителя из отряда игрока, несущего пленника (`string | null`).
  - `snapshot_id`: идентификатор текущего снимка (`string | null`).
  - `game_time`: игровое время снимка (`string | null`).

### Группа `bosses`

Выделенный реестр боссов, мировых лидеров и ключевых фигур Kenshi:
- Классификация происхождения босса `classification_origin` (`"game_bounty" | "world_state" | "meitou_holder" | "custom_catalog"`):
  - `game_bounty`: назначена базовая награда за голову в характеристиках FCS (`bounty amount > 0`).
  - `world_state`: NPC участвует в условиях триггеров переопределения мира или городов (`reactions/world_states`, условия `NPC is` / `NPC is NOT`).
  - `meitou_holder`: обладание оружием Мейто по базовым шаблонам снаряжения (производитель Кросс `52288-rebirth.mod`, уровень `52293-rebirth.mod`).
  - `custom_catalog`: боссы, подтверждённые предметным заданием (`50519-rebirth.mod`, `96407-rebirth.mod`, `96409-rebirth.mod`).
- Категория `category`: `"boss" | "world_leader" | "significant_npc" | "recruit" | "unique_npc"`. Отделена от источников классификации: при `NPC class == 5` категория — `world_leader`; при награде `>= 10000`, `custom_catalog` или `meitou_holder` — `boss`; при меньшей награде или участии только в триггерах мира — `significant_npc`.
- Поля объекта босса:
  - `npc_sid`: строковый `sid` шаблона персонажа.
  - `name_en`: каноническое английское имя.
  - `name_ru`: локализованное русское имя (`string | null`).
  - `classification_origin`: источник классификации босса.
  - `category`: категория сущности.
  - `bounty`: объект награды за голову (`{"amount": int, "factions": [string]}`) или `null`, если награда не назначена.
  - `associated_world_states`: список связанных триггеров состояния мира с полями `state_sid`, `state_name`, `value` (`null` для статических условий шаблона).
  - `static_locations`: список привязок к локациям (объекты `location_link` с полем `cleared_evidence`).
  - `personal_evidence`: объект подтверждения персонального события взаимодействия (`{"event_id": string, "day": int | null, "summary": string}`) или `null` по маркеру `[npc_sid=...]` в активном таймлайне.
  - `observed_state`: снимок наблюдаемого состояния (`state_code`, `player_defeat_flag`, `captured_by`).
  - `cleared_evidence`: свидетельство победы/зачистки (`{"location_instance_id": string, "cleared_at": string, "source": string}`) или `null`.
- **Инвариант зачистки**: конвертер (`tools.unique_entities_registry`) при локальной сборке реестра в `published/` **никогда не выставляет `cleared_evidence` самостоятельно** (значение строго `null`). Конвертер извлекает объективные факты сохранений и статических баз данных и не выносит суждений о победах над боссами.
- **Двухфакторное подтверждение победы над боссом при доставке**: поле `cleared_evidence` босса обогащается **исключительно при доставке в игровой репозиторий** (`deliver-companion`, функция `apply_progress_to_unique_entities`) и только при одновременном выполнении двух условий:
  1. Хотя бы одна статическая локация босса отмечена как зачищенная (`cleared`) в ручном слое `Campaign/<кампания>/locations_progress.json` формата `kenshi-location-progress/3`.
  2. Зафиксировано личное подтверждение взаимодействия с боссом (`personal_evidence is not None`).
  При отсутствии личного подтверждения зачистка локации фиксируется только на самой локации (`static_locations[].cleared_evidence`), а `cleared_evidence` босса остаётся `null`.

### Группа `meitou_weapons`

Каталог всех 26 базовых моделей оружия Мейто высшего ранга Cross (грейд `52293-rebirth.mod` / `19-gamedata.base`, производитель Кросс `52288-rebirth.mod` / `17-gamedata.base`):

- `manufacturer_sid`: константа `"52288-rebirth.mod"`.

- `name_en`: английское наименование оружия.

- `static_holders`: список потенциальных статических владельцев (1:N) по шаблонам игры:
  - `npc_sid`: `sid` NPC-владельца.
  - `npc_name`: имя владельца.
  - `town_instance_id`: идентификатор поселения владельца (`string | null`).
  - `town_name`: наименование поселения (`string | null`).
- `observed_instances`: фактически наблюдаемые экземпляры у игрока в текущем сохранении (экипировка, инвентарь, рюкзак персонажей или контейнеры на складах баз):
  - `item_sid`: динамический идентификатор экземпляра оружия в сохранении.

  - `carrier_name`: имя несущего персонажа или `null`.
  - `carrier_squad`: название отряда или `null`.
  - `storage_location_key`: ключ локации хранилища (поселение или зона) или `null`.

  - `observation_status`: `"observed" | "not_observed"`. Отражает факт физического присутствия хотя бы одного экземпляра модели оружия у игрока (`observed_instances` не пуст).

Отражает документальное подтверждение получения трофея: `confirmed_trophy` — наличие связанного события с маркером `[base_sid=...]` в активном таймлайне (`timeline/events.jsonl`, статус `confirmed`, не отменённого перезагрузкой или коррекцией); иначе — `unconfirmed`.

## Дипломатия и состояние мира: геополитические структуры FCS

Извлечение данных геополитики и состояния мира из `quick.save` выполняется строго read-only без вымышленных значений:
- Дипломатия (`diplomacy`):
  - Отношения фракций мира к игроку сопоставляются по каноническому `gamedata stringID` из записей типа 37.
  - Значение `relation` — точное числовое значение `float` в диапазоне `[-100.0, 100.0]`.
  - При отсутствии записи связи между фракцией и игроком подстановка нулей запрещена: `relation = null`.
  - Сохраняются сырые `relation`, `trust`, `trust_neg`; классификации по порогам нет.
- Состояние уникальных NPC (`world_state.unique_npcs`):
  - Читается из записи типа 56 (`usedUniques`).
  - Поле `player` читается строго из секции `bool` (`usedUniquesPlayer*`).
  - Числовой код `state_code` сохраняется без интерпретаций. Значения (факт игры, `Kenshi/fcs.def:1884-1885`, поле `NPC is` записей WORLD_EVENT_STATE): 0 — мёртв, 1 — жив и свободен, 2 — в плену. Строковых состояний и их вариантов в контракте нет.
  - Носитель пленника фиксируется в `captured_by`, когда пленник несётся отрядом игрока.
  - Сводка `summary` ведётся по числовым кодам: `state_0_count`, `state_1_count`, `state_2_count`.
- Переопределения городов (`world_state.town_overrides`):
  - Читаются из записей типа 94 (`Town state <имя>`) при наличии ключа `replacementTown`.
  - Фиксируются `replacement_sid`, имя шаблона переопределения и текущая фракция поселения.

## Расширенные характеристики персонажей

Извлечение данных персонажей из записей типа 30, 36, 67 (`platoon/*.platoon`):
- Очередь назначенных работ (`jobs`):
  - Декодируется из записи типа 67 (`JobsState`) через перечисление `taskType` (`tools/task_types.py`, 289 задач из канонического `fcs_enums.def`).
  - Постоянные работы (`primary`): упорядоченный список задач (`pjob0`, `pjob1`, ...) с полями `index`, `task_code`, `task_name` (например `JOB_MEDIC`, `JOB_REPAIR_ROBOT`, `OPERATE_MACHINERY`, `OPERATE_STORAGE`, `JOB_BUILDER`) и 5-компонентным `target_handle` (`TYPE, C, S, I, CS`).
  - Правило очистки `clean_handle`: безадресные задачи (глобальные работы вроде `JOB_MEDIC`, `JOB_REPAIR_ROBOT` с `TYPE == 11` или нулевыми координатами `C, S, I, CS`) очищаются до `target_handle = null`.
  - Временные работы (`temporary`): упорядоченный список задач `tjob` с полями `index`, `task_code`, `task_name`, `target_handle`.
  - Флаг активности работ: `enabled` (`bool | null`).
  - `raw`: изолированная копия исходных словарей записи (`int`, `string`, `bool`).
- Физическая переноска (`carrying`):
  - Извлекается из записи типа 36 (`CharacterState`).
  - `is_carrying`: булев флаг (берётся строго из булевой секции `st_bool.get("carrying", False)`).
  - `target_handle`: 5-компонентный handle переносимого персонажа (при `is_carrying == true`), иначе `null`.
  - `carried_by`: 5-компонентный handle несущего персонажа (при `is_carrying == false` и наличии валидного ненулевого handle с `carryingTYPE == 1`), иначе `null`.
  - `raw`: сырой словарь компонентов `carryingS`, `carryingI`, `carryingC`, `carryingCS`, `carryingTYPE`.
  - Ограничение: `target_handle` и `carried_by` являются сырыми 5-компонентными handle FCS движка и на текущем этапе напрямую не связываются с `id` персонажа.
- Награды за голову (`bounties`):
  - Награды за голову персонажа декодируются по массивам с числовыми суффиксами `bountyfac0..N`, `bountyexp0..N`, `crimes0..N`.
  - `has_bounty`: булев флаг наличия хотя бы одной активной награды (`amount > 0`).
  - `total_amount`: суммарный размер всех наград в катах (`int`).
  - `entries`: упорядоченный список записей по фракциям:
    - `index`: порядковый номер записи в массиве FCS.
    - `faction_sid`: `sid` фракции, объявившей награду (`bountyfac<idx>`).
    - `amount`: сумма награды в катах (`bountyexp<idx>`, целое число).
    - `crimes`: сырой числовой код преступления из сейва (`crimes<idx>`, целое число; семантика кодов на текущем этапе не подтверждена).
- Боевые режимы (`combat_modes`):
  - Булевы флаги боевого ИИ персонажа, читаемые непосредственно из булевой секции записи 36:
    - `taunt` (`taunt mode`), `passive` (`passive mode`), `ranged` (`ranged mode`), `defensive` (`defensive mode`), `chase` (`chase mode`), `stealth` (`stealth`), `non_combat` (`non combat mode`).
    - При отсутствии соответствующего ключа в сохранении значение возвращается как `null` (без фиктивной подстановки `false`).
    - Режим удержания позиции (`hold`) в булевой секции типа 36 Kenshi отсутствует и в публичный словарь не включается.

## Инфраструктура и производство баз: объекты `zone/*.zone`

Извлечение данных недвижимости, энергетики, крафта и складских запасов из записей типа 35 (`BuildingState`), типа 41 (`StorageState`) и типа 42 (`ItemState`):
- Иерархия построек (`property.buildings`):
  - Постройки разделяются на верхнеуровневые здания и вложенные объекты интерьера (`interior`) с номером этажа `floor`.
  - Имя постройки (`name`): читается непосредственно из строковой секции записи 35 (`b_str["name"]`), где хранятся локализованные и пользовательские имена игры («Хранение: доспехи», «Хранение: еда», «Campfire» и т.д.). Технический инстанс `r["name"] == "0"` отсекается. При пустом строковом имени используется локализованное имя шаблона из GameDB.
  - Имя шаблона (`template_name`): выносится в отдельное поле из справочника GameDB по `template_sid`.
  - Энергетика:
    - `power_on`: тумблер питания постройки (`bool | null`).
    - `gets_battery`: подключение к аккумуляторной сети (`bool | null`).
    - `battery_charge`: текущий фактический заряд аккумулятора (`float | null`, например 120.0 ед емкости). У не-аккумуляторных построек значение `0.0` является штатным числовым полем движка Kenshi и не означает разряженный аккумулятор.
  - Производство и крафт:
    - `is_paused`: флаг паузы производства (`pause`, `bool | null`).
    - `is_repeat`: флаг бесконечного повторения очереди крафта (`repeat`, `bool | null`).
    - `production_progress`: накопленный прогресс крафта текущего изделия (`production amount`, `float | null`).
    - `consumption`: словарь затраченного сырья станка (`consumption amount-*`, `float`).
    - `craft_queue`: упорядоченная очередь крафта станка (`current0..N`, `current prog0..N`, `crit0..N`) со списками объектов `{"item_sid", "item_name", "progress", "crit"}`.
    - `craft_partial_items`: задел незавершённых предметов крафта (`craft partial item sid/val 0..N`) со списками `{"item_sid", "item_name", "amount"}`.
    - `resource_mult`: множитель эффективности добычи ресурсов (`float | null`).
    - `mining_resource_level`: уровень истощения жил (`float | null`).
    - `usage_nodes`: имена узлов 3D-модели Kenshi для взаимодействия персонажей с постройкой (`usagenode_*`, например `usenode004`).
  - Состояние и оборона:
    - `complete`: подтверждённая готовность постройки (`is complete`, `bool | null`).
    - `destroyed`: признак разрушения (`bool | null`).
    - `broken`: признак поломки здания/двери (`broken`, `bool | null`).
    - `construction_progress_raw`: сырой показатель вложенных стройматериалов (`float | null`; у завершённых объектов больше 1.0, равный сумме материалов; статус готовности определяется строго флагом `complete: true`).
    - `construction_deposited`: массив по-слотно внесённых стройматериалов (`0construction mats`, `1construction mats`, `2construction mats`, `list[float]` в порядке слотов `refs["construction"]` шаблона постройки).
    - `current_shots`: остаток зарядов станковых турелей и гарпунов (`int | null`).
    - `is_locked`: статус замка дверей и контейнеров (`locked`, `bool | null`).
    - `lock_level`: уровень сложности взлома замка (`int | null`).
    - `hardness`: прочность объекта (`float | null`).
- Складские запасы и свойства предметов (`storage_items`):
  - Извлекаются из всех контейнеров типа 41, привязанных к зданиям и сундукам.
  - Сохранение качественных характеристик без схлопывания:
    - `quality`: числовой уровень качества оружия и брони (`float | null`). Округляется штатным `_r()`.
    - `charges`: остаток зарядов аптечек, шин и ремнаборов (`float | null`). Округляется штатным `_r()`.
    - `wear`, `dam`, `stun`: опциональные показатели износа и повреждений (`float | null`). Присутствуют только у повреждённых экземпляров экипировки; у стандартных предметов и сырья хранилищ равны `null`.
    - `quantity`: количество предметов в стаке для сырья и расходников (`int`).
    - `material_sid`: устойчивый `sid` материала оружия (определяет грейд, например Catun No 1, Edge Type 1, Meitou).
    - `company_sid`: изготовитель/бренд брони (Specialist, Masterwork).
    - `unique`: признак уникального/квестового предмета (`bool | null`).
    - `owned_by`: 5-компонентный handle законного владельца (`ownedbyTYPE..CS`). Пометка о краже на уровне хранилищ игрой не выставляется и не валидируется; поле документируется нейтрально как «handle владельца».
    - `raw`: изолированная копия исходных секций FCS.
- Границы контракта: расширенные поля зафиксированы в контракте `kenshi-session/11` и схеме `contracts/session.schema.json`. Схема валидирует и исторический `kenshi-session/10`, и расширенный `kenshi-session/11`.

## Табличные выгрузки: `published/tables/`

Каталог строится при публикации из снимка, `locations.json` и справочника игры (индекс и записи игры из файлов набора модов снимка, `tools/gamedb.py`, кэш `data/cache`); код — `tools/tables.py`. Манифест ссылается на `tables/index.md` (`artifacts.tables`); валидатор проверяет snapshot_id в `index.md`, существование перечисленных CSV, совпадение числа строк с `index.md`, отсутствие BOM и CR и отсутствие неперечисленных CSV. Без справочника игры (игра или моды недоступны) таблицы цен, торговли, реакций и справочника юнитов пусты, причина указана в `index.md` и в `manifest.validation.warnings` (`tables: ...`); значения не подставляются.

**Артефакт доставки `docs/reference/encounters.md`.** Не входит в `published/`: `deliver-companion` генерирует его в `Kenshi-Compain` из таблиц `squad_spawns`, `squad_templates`, `squad_members`, `faction_relations`, `faction_hostility` (код `tools/encounters.py`, без LLM) и включает в тот же коммит, что и выгрузку. Состав: регионы (группы биомов `biome_homeless`; доля — `ref_v0` к сумме по региону, округление half-even; отряды с долей < 3% сворачиваются в «Прочие (k)»; `¹` — отряд с `world_state_sids`; состав по `squad_members`, не более 4 позиций, затем «…»; пары `v0 = v1 = 0` пропускаются; гендерные формы `/кца1/` и подобные приводятся к мужской), бродячие отряды городов (`town_roaming`) и отношения фракций (минимум 3 заданных `relation`; «нападает при встрече» — значение не выше `enemy_classification`). Сортировка и формат детерминированы (UTF-8, LF); повторная доставка тех же таблиц файл не меняет. Если в выпуске нет какой-либо из пяти таблиц, файл не затрагивается и выводится предупреждение.

**Артефакты доставки картографии.** Не входят в `published/`: `deliver-companion` копирует в `docs/reference/` игрового репозитория производные от растра регионов файлы `regions_map.svg` (контуры регионов) и `regions_adjacency.json` (`kenshi-region-adjacency/2`: граф `adjacency`, `border_lengths` — число пар пикселей 4-связности для пары `A|B`, хеши растра, ячеек и таблицы, `world_ref_id`) из `assets/cartography/`. Запись выполняется только при совместимом просмотрщике `sites/map/index.html` клона. Растр (`regions_map`) не попадает ни в `published/`, ни в `docs/`. Правила совместимости, команды проверки геометрии и пересборки таблицы — `docs/cartography.md`.

**Отчёт доставки.** `status` описывает доставку `published/` (`failed` — только её сбой). Картография отражается отдельно: `cartography` = `ok` | `incompatible` | `skipped`, `cartography_reason`, `cartography_changed`; `incompatible` и `skipped` доставку `published/` не блокируют.

Остальные файлы `docs/` игрового репозитория доставка не меняет.

### Правила формата

- UTF-8 без BOM, переводы строк LF, RFC 4180 (запятая; поля с запятой, кавычкой или переводом строки — в двойных кавычках), первая строка — заголовок.
- Строки отсортированы по ключу таблицы; меток времени в содержимом нет; повторная публикация одного снимка побайтно идентична.
- Пустая ячейка — значение отсутствует или не применимо. Числа — с точкой, без разделителей разрядов, не более 6 знаков после точки без хвостовых нулей; булевы — `true`/`false`; списки в ячейке разделены `; `.
- Связи между таблицами — по идентификаторам (`sid`, `id`), а не по именам: имена могут совпадать.
- Словари колонок каждой таблицы вынесены в отдельные файлы `tables/dict/<таблица>.md`; `tables/index.md` служит компактным оглавлением со ссылками на словари.

### Исторические витрины отряда и кампании

Исторические витрины формируются модулем `tools.skills_history` по хронологической цепочке дней кампании (`campaign_chain`), отсекающей откаты игрового времени при перезагрузках:

#### 1. Динамика навыков и атрибутов `skills_history.csv`
- **Назначение**: длинный формат дельта-трекинга целочисленных уровней характеристик участников отряда игрока по дням кампании. Охватывает 4 базовых атрибута (`Strength`, `Toughness`, `Dexterity`, `Perception` из `ATTRIBUTES`) и 33 навыка (`SKILL_LABELS`), всего 37 характеристик, представленных в `squad.csv`.
- **Логика фиксации**: при первом появлении персонажа в цепочке фиксируется срез всех его непустых характеристик; на последующих днях строка формируется строго при изменении целой части уровня (`int(current) != int(previous)`) в любую сторону (как рост, так и снижение).
- **Ключ сортировки**: `day, character_id, skill` (по возрастанию кортежа `(int(day), str(character_id), str(skill))`).
- **Ключ соединения**: `character_id` (связь с `squad.csv`, `inventory.csv`, `equipment.csv`).
- **Колонки** (5 колонок):
  1. `day`: игровой день фиксации (целое число).
  2. `character_id`: постоянный идентификатор персонажа в сохранении (`ps:...`).
  3. `character_name`: имя персонажа.
  4. `skill`: каноническое английское название характеристики или навыка (из `squad.csv`).
  5. `level`: целочисленный уровень характеристики (`int(level)`).

#### 2. Динамика казны и отряда `campaign_history.csv`
- **Назначение**: макро-состояние казны и численности состава игрока по дням кампании (срез на момент строго последнего сохранённого снимка каждого игрового дня).
- **Ключ сортировки**: `day` (по возрастанию `int(day)`).
- **Ключ соединения**: `day`.
- **Колонки** (4 колонки):
  1. `day`: игровой день (целое число).
  2. `game_time`: строковое игровое время последнего снимка дня (`Day N HH:MM`).
  3. `cats`: баланс казны игрока (целое число или пусто/null).
  4. `squad_size`: общее количество участников в отрядах игрока (целое число).

#### 3. Дипломатическая история `relations_history.csv`
- **Назначение**: история изменений дипломатических отношений фракций мира к игроку в длинном формате по дням кампании.
- **Логика фиксации**: строка фиксируется при первом появлении фракции с известным отношением в цепочке дней, а в последующие дни — только при изменении числового показателя `relation`.
- **Ключ сортировки**: `day, faction_sid` (по возрастанию кортежа `(int(day), str(faction_sid))`).
- **Ключ соединения**: `faction_sid` (связь с `diplomacy.csv`, `faction_relations.csv`, `faction_hostility.csv`).
- **Колонки** (4 колонки):
  1. `day`: игровой день фиксации (целое число).
  2. `faction_sid`: идентификатор шаблона фракции (FCS `FACTION`, тип 10).
  3. `faction_name`: наименование фракции.
  4. `relation`: числовой показатель отношений (число с плавающей точкой в диапазоне `[-100.0, 100.0]`).

### Таблица уникальных сущностей `unique_entities.csv`

Таблица `tables/unique_entities.csv` формируется модулем `tools.tables` (`unique_entities_table`) на основе артефакта `published/unique_entities_registry.json` (с возможным наложением ручного слоя `entities_progress.json`) и служит плоской аналитической витриной реестра для анализа и фильтрации (17 колонок):
1. `entity_kind`: вид сущности (`npc` — уникальный персонаж, включая рекрутов, боссов и мировых лидеров; `meitou` — оружие Мейто). Категория персонажа передаётся через `category`.
2. `category`: категория сущности (`recruit`, `world_leader`, `boss`, `significant_npc`, `unique_npc`, `meitou`). Для персонажей транслируется из `category` (по умолчанию `unique_npc`); для боссов при отсутствии категории в NPC — из записи босса; для Мейто — всегда `meitou`.
3. `sid`: строковый идентификатор шаблона (`npc_sid` для персонажей, `base_sid` для оружия Мейто).
4. `name_ru`: русскоязычное наименование или имя.
5. `name_en`: англоязычное наименование или имя.
6. `state_code`: числовой код состояния NPC (0 — мёртв, 1 — свободен, 2 — в плену; для meitou — пусто).
7. `squad_status`: статус в отряде игрока (`confirmed_in_squad`, `confirmed_not_in_squad`, `unresolved`; для meitou — пусто).
8. `character_id`: постоянный идентификатор персонажа игрока (`ps:...`), если завербован (для meitou — пусто).
9. `primary_location_instance_id`: идентификатор основной локации (поселения/города) из справочника мира. Заполняется только при однозначной привязке (ровно 1 локация); при множественной привязке (1:N, например бродячие рекруты) или отсутствии — пусто. Для оружия Мейто — всегда пусто.
10. `location_resolution`: точность привязки к локации (`unique` при ровно 1 локации, `ambiguous` при нескольких привязках 1:N, `unresolved` при неразрешённой локации; для meitou — пусто).
11. `carrier_or_storage`: для оружия Мейто — носитель или хранилище фактически наблюдаемого экземпляра в формате `<вид>:<имя>` (например, `equipped:Хот Лон` или `storage:Оружейный шкаф`); для персонажей — пусто.
12. `observation_status`: статус наблюдения в сохранении (`observed` если сущность наблюдалась в динамике сейва или среди экземпляров, иначе `not_observed`). Для персонажей: `observed`, если `state_code` не пуст, иначе `not_observed`. Для оружия Мейто: транслируется из `observation_status` (либо `observed` при наличии найденных экземпляров, иначе `not_observed`).
13. `provenance_status`: статус происхождения или подтверждения для оружия Мейто (`confirmed_trophy` при наличии подтверждённого трофея, иначе `unconfirmed`); для персонажей — пусто.
14. `location_cleared`: место персонажа отмечено зачищенным: true при зачистке основного места (`primary_location_instance_id`), false если основное место не зачищено, пусто при `ambiguous` или отсутствии локации, для meitou — пусто.
15. `outcome`: исход взаимодействия из ручного слоя или персонального свидетельства (`outcome` из `personal_evidence` для персонажей; `outcome` из `trophy_evidence` для оружия Мейто; при отсутствии — пусто).
16. `evidence`: текст подтверждения/свидетельства исхода (`evidence` из `personal_evidence` для персонажей; `evidence` из `trophy_evidence` для оружия Мейто; при отсутствии — пусто).
17. `game_time`: игровое время подтверждения события (`game_time` из `personal_evidence` для персонажей; `game_time` из `trophy_evidence` для оружия Мейто; при отсутствии — пусто).

### Значения `state_code` и отношения

`unique_npcs.csv.state_code`: 0 — мёртв, 1 — жив и свободен, 2 — в плену (факт игры: `Kenshi/fcs.def:1884-1885`, поле `NPC is`). `diplomacy.csv` содержит сырые `relation` (−100…100), `trust`, `trust_neg`; классов нет.

### Колонки `calc_*` и `calc_status`

- `calc_status`: `verified` — все публикуемые `calc_*` строки сверены с карточкой игры; `unverified_class` — сочетание без сверки (броня: класс × материал; оружие ближнего боя: класс × производитель; протез не на ноге); `unknown_level` — `level` предмета не определён; `unknown_template` — шаблон или константы игры не найдены в справочнике. При любом статусе, кроме `verified`, все `calc_*` пусты.
- Сверенные сочетания задаёт код (`itemstats.CONFIRMED_ARMOUR_COMBOS`, `CONFIRMED_MELEE_COMBOS`, `CONFIRMED_PROSTHETIC_LIMBS`); арбалеты считаются для всех. Актуальный перечень — в `CALC_NOTE` и `index.md`.
- `calc_*` публикуются без округления. Совпадение с карточкой игры — равенство после округления до точности интерфейса: нижняя граница урона усекается, верхняя округляется, скорость выстрела округляется, проценты и вес усекаются.
- Параметры шаблонов берутся после применения модов снимка (порядок загрузки определяет итоговое значение).
- Цены оружия и брони с уровнем и производителем не вычисляются; базовые цены — `item_prices.csv`.

## Проверка принадлежности сейва кампании

`pipeline` перед регистрацией в индексе и публикацией сравнивает состав персонажей сейва с родительским снимком (головой кампании `head_snapshot_id` в `data/index.json`) по устойчивым `characters[].id` (`ps:...`); имена не используются. Признак: общие id родителя и сейва. Доля = общие id / размер состава родителя (сколько персонажей родителя осталось); рост состава доли не снижает. Решение «относится» при доле >= 0,3 (`MIN_SHARED_SHARE`) и общих id >= 9 (`MIN_SHARED_IDS`, больше максимума общих id у чужих игр с общим стартом) (`tools/campaign_check.py`). Деление на меньший состав не применяется: ранняя чужая игра с тем же стартом давала бы 2 из 2 = 1,00.

Отказ: `сейв не относится к кампании <campaign_id>`, код возврата 1; `published/`, индекс и доставка не затрагиваются (снимок остаётся в `data/snapshots/` как неиндексированный). Проверка пропускается с явным `campaign_check.status = skipped` и причиной: нет родительского снимка (первая публикация кампании), родитель недоступен или без `ps:*`-id, задан `--allow-new-campaign` (осознанный новый старт или смена кампании, потеря более 70 % состава родителя или менее 9 общих id у молодой кампании; `Initialize-Pipeline.ps1 -AllowNewCampaign`).

`python -m tools.campaign check-save --source <папка сейва> [--campaign-id --index-file --snapshots-dir]` выполняет ту же проверку без изменений: извлекает сейв во временный каталог, сравнивает с головой кампании из индекса и печатает JSON (`status`: `checked` | `skipped`, `belongs`, `shared`, `parent_size`, `candidate_size`, `share`, `min_shared_share`, `min_shared_ids`, `reason` при `skipped`). Код возврата: 0 - относится (включая `skipped`: первая публикация кампании, родитель недоступен), 1 - не относится, 2 - ошибка. `data/`, индекс и `published/` не пишутся. `Initialize-Pipeline.ps1` без явного выбора папки перебирает свежие папки сохранений этой командой.

Обоснование порогов (измерение на 77 локальных сейвах игрока против опубликованного состава hot-lon, 30 персонажей; фракция игрока `204-gamedata.base` одинакова у всех, как признак не используется):

| Класс | Сейвов | Доля от родителя (min / медиана / max) | Общих id (min / медиана / max) | Решение |
|---|---|---|---|---|
| продолжения hot-lon (текущие, старые стадии, перезагрузки; состав 11-30) | 25 | 0,37 / 1,00 / 1,00 | 11 / 30 / 30 | относятся |
| другие игры с общим стартовым ядром (состав 18-30) | 25 | 0,17 / 0,27 / 0,27 | 5 / 8 / 8 | отказ |
| несвязанные сейвы (состав 0-53) | 27 | 0,00 / 0,00 / 0,03 | 0 / 0 / 1 | отказ |

Общее ядро всех сейвов второго класса — 5 id (в объединении 8). Порог доли 0,3 лежит в зазоре 0,27-0,37, минимум 9 id — в зазоре 8-11. Самые ранние чужие сейвы (состав 0, 1, 2, 2, 6 персонажей) имеют 0 общих id и отклоняются. Цепочка из 26 снимков hot-lon с родителем в `data/snapshots/` (30 из 30, доля 1,00) проходит. Порог 0,5 отклонял бы реальные старые стадии (`hot lon 9`: 11 из 30). Ложный пропуск публикует чужую игру в `published/` (исправление требует отката выпуска), ложный отказ снимается флагом `--allow-new-campaign`. Кампания с родителем менее 9 персонажей всегда требует флага: признак неотличим от общего стартового ядра.

## Валидация проектных схем

`python -m tools.campaign check-schemas` проверяет проектные примеры, включая `session-11.example.json`, и определения схем реестра и ручных отметок. Unit-тесты отдельно отвергают неизвестные свойства, неправильные типы/даты, абсолютные пути/выход через `../` и некорректные поля новых разделов v11. Старые формы примеров и все 53 исторических снимка остаются полностью валидными.
