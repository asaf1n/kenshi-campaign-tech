# Контракт данных и совместимость (проектирование)

## Обязательное исходное обследование

Ранее реально встречались файлы с `format="kenshi-session/10"` и вложенным `changes.format="kenshi-session-diff/5"`. Известные поля см. `references/observed-export.md`. Это **существующий формат**, а предложенные ниже обёртки **ещё не реализованы**. Исполнитель обязан сверить полную схему с настоящими данными, выяснить происхождение ID, проверить сбор изменений и **не проводить silent migration**.

Допускается прямое использование `kenshi-session/10` как `current.json`, если формат пригоден к публикации после удаления локальных путей и других нежелательных полей. В противном случае сделать узкий адаптер, сохранив source format/version и ссылку на исходный снимок. Преобразование должно иметь тесты обратного соответствия полей.

## Контракт bundle: `kenshi-publication/1` (draft)

Публикуемые артефакты:

```text
published/
  manifest.json
  current.json
  changes.json
  brief.md
  squad.md
```

`manifest.json` содержит: `format`, `generated_at` (UTC ISO-8601), `snapshot_id`, `source_kind` (`save`/`export`), `source_format`, `source_sha256` (хеш именно указанного source_kind), `artifacts` (пути относительно `published/`), `validation` (`passed` или `failed`). При успешном выпуске `validation.status="passed"`; неуспешный bundle не публикуется как актуальный. `snapshot_id` однозначно связывает файлы; в `changes.json` должна быть явная пара `from`/`to` или `valid:false` с причиной. Для удалённой ссылки можно добавить `git_commit`, но циклическая зависимость между commit SHA и зафиксированным файлом недопустима; commit сверяется снаружи.

Публичные данные не должны содержать абсолютных путей пользователя из `save.path`. Не публиковать сырые сейвы, произвольные большие текстовые поля, секреты или неразобранные бинарные блоки. Имена персонажей и числовые игровые показатели допустимы; явно проверяй внешний JSON на локальные персональные строки.

`brief.md` — краткая сводка с `snapshot_id`, днём игры, составом, деньгами, доступными местоположениями, ключевыми изменениями и ссылками на детальные JSON. Все значения должны ссылаться на соответствующие поля JSON; при отсутствии сведений ставить «не получено».

## Идентичность и порядок

- Prefer ID из игры/экспортёра; имя — только метка отображения. Повторяющиеся имена допускаются.
- Контрольный снимок идентифицируется хешем источника плюс корректной информацией о кампании/ветке; если этих данных недостаточно, явно фиксировать ограничение.
- Проверить значение исходных `from/to`: файловое имя или timestamp не являются гарантией логического родительства.
- Diff по персонажам сравнивает ID и категории с одинаковой семантикой. Отсутствующие категории и невалидные пары получают отдельный статус.
- Округление значений применяется только для представления; сравнение ведётся на доступной исходной точности.
- Для idempotency сериализовать JSON детерминированно; временную метку сборки разрешено обновлять только при реальной публикации новой версии, не на каждом dry-run.

## Подтверждённые игровые события

Проектный формат `kenshi-event/1` описан в `contracts/timeline-event.schema.json`. Минимальные поля: `event_id`, `format`, `session_id`, `recorded_at`, `kind`, `status`, `summary`, `evidence`.

- `observed`: факт непосредственно обнаружен в сейве/выгрузке; он не доказывает причину.
- `confirmed`: пользователь явно сообщил или подтверждённый скриншот однозначно указывает событие; источник должен быть указан.
- `inferred`: интерпретация модели, которая не становится фактом и не включается в подтверждённую хронику без подтверждения.
- Коррекция события — отдельная запись `kind="correction"` со ссылкой `corrects_event_id` после уточнения контракта агентом.

`timeline/events.jsonl` append-only. Одинаковый `event_id` не вставляется дважды; порядок события в игровом мире может отличаться от `recorded_at`. Ретроспективные события допускаются. Идентификатор источника должен открывать локальную заметку/снимок/скриншот либо опубликованный артефакт.

## Контракт ещё необходимо проверить

Схемы в `contracts/` — стартовые предложения для **manifest и event**, не утверждённая спецификация сохранения или конвертера. Агент сначала сопоставляет предложения с реальными примерами, затем уточняет и фиксирует совместимость; до этого не объявляет файл `current.json` валидным по несуществующей схеме.
