# Задание агенту: проектирование и подготовка реализации Kenshi Campaign

Ты работаешь **в корне новой локальной папки `kenshi-campaign-tech`**. Цель — подготовить и затем реализовать технический конвейер для личной кампании Kenshi с минимальной зависимостью от LLM в runtime.

## 1. Контекст и целевая модель

- **Чат-ИИ модели (LLM ассистенты)** — основной интерактивный интерфейс пользователя: посмотреть актуальный состав и экипировку, сравнить снимки, оценить прогресс, выбрать маршрут и задачи, сформировать подтверждённый таймлайн. Чат-ИИ модели читают *сгенерированные проверенные файлы*, а не вычисляют игровой state из переписки. Начать с обычного диалога/таблиц; полноценный веб-интерфейс и Sites не нужны для MVP.
- **Локальный Python + существующий конвертер** — извлечение сведений из сохранений Kenshi, нормализация, сравнение, расчёты, валидация, публикация. Результаты должны воспроизводиться без вызова модели.
- **Claude Code / Codex на ПК** — разработка, исследование текущей выгрузки, тесты и аудит. Кто именно реализует каждый этап, выбирается по фактической доступности; предпочитаем Codex для реализации и Claude для независимого review.
- **Google Antigravity** — основной управляющий интерфейс, если доступны нужные интеграции. Используй имеющиеся глобальные skills `orchestrate`, `planner`, `implementer`, `reviewer` из `asaf1n/AI-Orchestrated-Workflow` (`main`) **только после проверки фактического обнаружения**. Не копируй skills/протокол в проект, не создавай собственный мультиагентный движок. Если навыки недоступны, честно фиксируй это и выполняй эквивалентные предметные шаги локально по явному плану.
- **Git** — воспроизводимая история версий и потенциальный канал чтения чат-ИИ моделями из GitHub. Реальную читаемость чат-ИИ моделями, приватный/публичный доступ, синхронизацию и запись обратно проверяй, не считай готовыми. Push, создание удалённого репозитория, изменение разрешений/секретов — только после отдельного согласования.
- **Литературная хроника вторична:** главное — сохранять события, доказательства, порядок и таймлайн, не дописывать непроверенные игровые факты.

## 3. Обязательное исследование на этом ПК

**Не начинай писать новый парсер**, пока не проведена инвентаризация существующих реализаций.

Определи:

- Есть ли работающие программы, скрипты, проекты или репозитории Kenshi, которые создают `kenshi-session/10`, `kenshi-session-diff/5`? Где исходники и инструкции запуска? Реально ли они работают на текущем ПК?
- Какие форматы файлов берутся на вход и с какими гарантиями поддерживаются моды? Входное сохранение всегда read-only.
- Какие поля извлекаются: день/время/деньги, члены отряда, устойчивый ID, группировка, навыки, экипировка, инвентарь, протезы, здоровье, запасы, позиции, состояние мира?
- Как устроен diff: по каким ID сопоставление, как считаются числовые дельты, откуда берутся `from/to`, `valid`, `compared`, как отличают неизвестные данные от нулевых изменений и как обрабатывают reload?
- Что содержат локальные тесты и насколько они покрывают существующие выгрузки? Каковы воспроизводимые команды?
- Можно ли безопасно подключать текущий конвертер как CLI/библиотеку без переписывания? Если нет — докажи ограничение.

В ранее предоставленных пользователем экспортных файлах наблюдались `format="kenshi-session/10"`, `changes.format="kenshi-session-diff/5"`, `save`, `world`, `changes`. Это **существующая версия**, а не требование заменить её придуманной схемой. Среди членов отряда встречаются **повторяющиеся имена** («Вьючный бык»); строго проверь стабильные ID.

Если сохранения/конвертер недоступны в workspace — не угадывай путь и не заявляй об успешной работе с сейвом. Заверши доступные этапы (анализ contracts, tests на синтетике, документация) и явно назови блокирующие доступы. Если возможен безопасный поиск на ПК, проведи его без изменений входных файлов и без чтения чужих каталогов вне разумной области проекта.

## 4. Подготовь проектное решение

Сначала предъяви:

1. **AS-IS:** найденные реальные файлы, команды, форматы, известные дефекты, тесты, карта полей, покрытие и источники наблюдений.
2. **Gap-analysis:** что из P0 уже реализовано, что отсутствует, где адаптер достаточен, где нужен новый код; отдели подтверждение от предположений.
3. **Целевая минимальная архитектура:** read-only extract → normalize → diff → validate → render → atomic publish; неизменяемые snapshots/ветки; простой Git transport и fallback ручной загрузки.
4. **Контракт файлов:** сначала сохрани `kenshi-session/10` и `kenshi-session-diff/5`, затем обоснуй предлагаемый publication bundle. Приведи примеры полной версии `manifest.json`, `brief.md` и события; проектные схемы из `contracts/` скорректируй только при обнаружении фактических несовместимостей.
5. **Тестовый план:** список real/synthetic fixtures, сравнений с игрой, негативных сценариев из `docs/acceptance.md`, методы доказательства read-only и атомарности публикации.
6. **Риски/ограничения:** GitHub → чат-ИИ модели (реальный доступ и свежесть), локальные пути, одноимённые сущности, история reload/веток, устаревший state чат-ИИ, несоответствие игровых данных.
7. **План реализации по этапам** с задачами, зависимостями, файлами, проверками и критериями выхода. Предпочти инкрементальный end-to-end вертикальный срез, а не универсальный framework.

Если установлен навык `/orchestrate`: создай план по его актуальному протоколу (`orchestrate_workflow/plans/...`), отдельно проведи независимый review плана и выдай его на утверждение. **Сам факт этого задания не означает утверждение созданного плана**. Не запускай реализацию до утверждения, кроме read-only разведки и создания материалов планирования/документации, допускаемых workflow.

## 5. После явного утверждения плана реализуй

Следуй `prompts/02-EXECUTE-APPROVED.md` и установленному workflow. Минимальный выход:

- документированная конфигурация путей Windows, без жёстко прошитого имени пользователя;
- преобразование существующего export в проверенный и компактный bundle;
- проверка двух реальных сейвов, негативные тесты, сохранение последнего удачного bundle при ошибке;
- генерация читаемых `brief.md`, `squad.md` на русском;
- минимальный журнал событий и sessions, подтверждения, недопущение выдуманных причин изменений;
- проверка каналов чат-ИИ моделей или честно описанный ручной сценарий;
- README для ежедневного обновления после игровой сессии.

Не внедряй Docker Agent, сервер, БД, сайт, RAG, сложный агентский контроллер или массовую разметку скриншотов без доказанной пользы и разрешённого изменения рамок.

## 6. Разделение ролей и безопасность

Проектный workflow из `asaf1n/AI-Orchestrated-Workflow` используем как внешний установленный инструмент; владелец каждого этапа и заключение другого исполнителя фиксируются. Для значимых изменений контрактов, ID, diff, веток и публикации один агент реализует, другой независимо проверяет **итоговую** версию. Не подменяй формальные `result.md/review.md` собственными словами. Git-коммиты принятых этапов делает orchestrator в границах разрешений; **push и внешние изменения запрещены до согласия**.

Запрещены перезапись/правка сейвов, удаление уже имеющихся данных и ложное подтверждение проверки. Сырой save, персональные абсолютные пути, токены и случайные скриншоты не попадают в публичный Git.
